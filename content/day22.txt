title: 服务的骨架：启动时加载一次
--- body
把模型做成服务（service），就是让别的程序通过 HTTP 发来输入，拿回预测结果。一个最小的模型服务有三部分：

1. **启动**：加载权重，`model.eval()`，预热（下一张卡片讲），然后才开始接请求。
2. **`/health`**：健康检查。负载均衡器（load balancer，把流量分给多台服务器的程序）和 Kubernetes 会定时访问它，只把请求发给回答「ok」的服务器。
3. **`/predict`**：接收输入，检查，跑模型，返回 JSON。

最重要的一条：**模型在启动时加载一次，之后所有请求共用它。** 加载要读权重文件（几百 MB 到几十 GB）、建模型、搬到 GPU，要几秒到几分钟。写进 handler（处理一个请求的函数）里，每个请求都要付一遍这个钱。

今天的写法是一个「工厂函数」`create_app(load_model)`：先调用 `load_model()` 拿到模型，再建 app。handler 是写在 `create_app` 里面的函数，可以直接用外层的变量 `model`（这叫闭包）。好处是测试时能传一个假的 `load_model` 进去，数它被调用了几次。FastAPI 也有官方的启动钩子 `lifespan`，做的是同一件事。

还有一条：**一个进程一个模型。** `uvicorn --workers 4` 会起 4 个进程，每个进程都加载一遍模型。在 GPU 上，这就是 4 份显存，还抢同一块卡。常见做法是一块 GPU 配一个进程、一个模型，请求在进程里排队（后面的卡片讲）。

下面用一个约 4 MB 的小模型，比一比「加载一次」和「预测一次」各花多久。
--- code
import io
import time

def build():
    return nn.Sequential(*[nn.Linear(512, 512) for _ in range(4)])

weights = io.BytesIO()
torch.save(build().state_dict(), weights)       # 假装这是硬盘上的权重文件

def load_model():
    weights.seek(0)
    m = build()
    m.load_state_dict(torch.load(weights, weights_only=True))
    return m.eval()

t0 = time.perf_counter()
model = load_model()
t_load = time.perf_counter() - t0

x = torch.randn(1, 512)
with torch.inference_mode():
    model(x)                                     # 先跑一次（预热）
    t0 = time.perf_counter()
    model(x)
    t_pred = time.perf_counter() - t0
print(f"加载一次: {t_load * 1000:.2f} ms")
print(f"预测一次: {t_pred * 1000:.3f} ms")
print(f"加载是预测的 {t_load / t_pred:.0f} 倍。真实模型比它大几千倍，加载要几秒到几分钟。")

title: 预热：准备好了再接请求
ref: day22
--- body
模型的第一次 forward 常常比后面慢得多，因为很多一次性的准备工作拖到了第一次调用才做：

- 第一次用 GPU 时要建立 CUDA context，几百毫秒到几秒；
- 设置了 `torch.backends.cudnn.benchmark = True` 时，cuDNN 会为每一种新的输入形状试几种算法，挑最快的；
- `torch.compile` 第一次调用时要编译（几秒到几十秒），形状变了还可能再编译一次；
- 显存分配器第一次向 GPU 要内存。

不处理的话，第一个用户替你付这笔钱，每出现一种新的 batch 大小，又有一个用户要付。

预热（warm-up）：启动后、接请求之前，用假数据把模型跑几遍，而且要覆盖线上会遇到的形状（比如 batch 大小 1、8、32）。预热也按推理的规矩来：`model.eval()`，`torch.inference_mode()`。

预热做完之前，服务「活着」但「还没准备好」。所以健康检查常分两种：

- liveness（活着吗）：进程没卡死就回 200；
- readiness（准备好了吗）：加载和预热都做完了才回 200，之前回 **503**。负载均衡器只把请求发给 ready 的服务器。

在 CPU 上这个效应很小，不好演示。下面用今天准备好的 `SlowStartModel` 来模拟：每遇到一种新的 batch 大小，第一次 forward 多花 500 ms，平时花 2 + 0.25·B ms。时间记在假时钟 `FakeClock` 上（单位毫秒，只有调用 `advance` 才会走），所以不用真的等。
--- code
def serve(request_sizes, warm_sizes):
    clock = FakeClock()
    model = SlowStartModel(clock).eval()
    with torch.inference_mode():
        for b in warm_sizes:                     # 预热：上线前先把会遇到的形状跑一遍
            model(torch.zeros(b, 4))
        took = []
        for b in request_sizes:                  # 真实的请求
            t0 = clock()
            model(torch.randn(b, 4))
            took.append(clock() - t0)
    return took

reqs = [1, 1, 8, 8, 32]
print("请求的 batch 大小:     ", reqs)
print("不预热，每个请求的 ms: ", serve(reqs, warm_sizes=[]))
print("预热 1/8/32 后的 ms:   ", serve(reqs, warm_sizes=[1, 8, 32]))

title: pydantic：把坏输入挡在门外
--- body
线上的请求什么样的都有：少一个数，多一个数，字符串，`null`，NaN，一次塞十万行。不检查就直接变成 tensor，结果是 shape 报错（服务回 500），一个 NaN 让整个 batch 的输出都变成 NaN，或者一个超大请求把显存吃光。

pydantic 让你用类型写出「合格的输入长什么样」，不合格的它替你挡掉。比如一个处理 3D 点的服务，每个点 3 个坐标，一次 1 到 8 个点：

```
from typing import Annotated
from pydantic import BaseModel, Field, FiniteFloat

Point = Annotated[list[FiniteFloat], Field(min_length=3, max_length=3)]

class PointsRequest(BaseModel):
    points: list[Point] = Field(min_length=1, max_length=8)
```

一个一个看：

- `BaseModel`：继承它，类里写的字段就会被检查。
- `FiniteFloat`：有限的浮点数，NaN 和 inf 都不行。普通的 `float` 会放过它们。
- `Annotated[类型, Field(...)]`：给一个类型加限制。`min_length` / `max_length` 限制列表的长度。这里是：每个点正好 3 个数。
- `points: list[Point] = Field(min_length=1, max_length=8)`：1 到 8 个点。上限挡住超大请求。

`PointsRequest.model_validate(一个 dict)` 做检查：合格就返回对象，不合格就抛 `ValidationError`，里面写着哪个位置（loc）出了什么错。

注意，pydantic 默认是「宽松模式」：字符串 `"1.5"` 会被转成 `1.5`，整数 `3` 会被转成 `3.0`。想拒绝 `"1.5"` 这样的字符串，就用 strict 模式（比如 `model_validate(..., strict=True)`）。整数在 strict 模式下也照样被当成 float 收下。

放进 FastAPI 以后，检查不通过会自动变成 **422** 响应（Unprocessable Entity：JSON 能读，但内容不合格），你的 handler 根本不会被调用。
--- code
from typing import Annotated
from pydantic import BaseModel, Field, FiniteFloat, ValidationError

Point = Annotated[list[FiniteFloat], Field(min_length=3, max_length=3)]

class PointsRequest(BaseModel):
    points: list[Point] = Field(min_length=1, max_length=8)

for payload in [{"points": [[0.5, 1.0, 2.0]]},
                {"points": [[0.5, 1.0]]},
                {"points": [[0.5, 1.0, float("nan")]]},
                {"points": [["1.5", 3, 2.0]]},
                {"points": []}]:
    try:
        req = PointsRequest.model_validate(payload)
        print("通过:", req.points)
    except ValidationError as e:
        err = e.errors()[0]
        print("拒绝:", err["loc"], err["msg"])

title: FastAPI 和 TestClient：不开端口也能测
ref: day22
--- body
FastAPI 用几行代码就能把 Python 函数变成 HTTP 接口：

```
app = FastAPI()

@app.get("/health")
def health():
    return {"status": "ok"}

@app.post("/predict")
def predict(req: PredictRequest):
    ...
    return {"labels": [...], "probs": [...]}
```

- `@app.get(路径)` / `@app.post(路径)`：这个函数处理哪个路径、哪种请求方法。只读取用 GET，发数据过来计算用 POST。
- 参数写成 `req: PredictRequest`：FastAPI 把请求的 JSON body 交给 pydantic 检查，通过了才调用你的函数，不通过直接回 422。
- 返回一个 dict，自动变成 JSON。里面只能放 Python 的数字、字符串、列表；tensor 要先 `.tolist()`。
- 路径不存在回 404；路径存在但方法不对（比如对只收 POST 的路径发 GET）回 405。

测试不用真的开服务器。`TestClient(app)` 在同一个 Python 进程里模拟 HTTP 请求：

```
client = TestClient(app)
r = client.post("/predict", json={"rows": [[5.1, 3.5, 1.4, 0.2]]})
r.status_code     # 200
r.json()          # 解析好的 dict
```

有一个细节后面会用到：用 `def`（不是 `async def`）写的 handler，FastAPI 会放到另一个线程（线程池）里去跑。
--- code
from fastapi import FastAPI
from fastapi.testclient import TestClient
from pydantic import BaseModel

class Pair(BaseModel):
    a: float
    b: float

app = FastAPI()

@app.get("/health")
def health():
    return {"status": "ok"}

@app.post("/mul")
def mul(req: Pair):
    return {"product": req.a * req.b}

client = TestClient(app)
for method, path, body in [("GET", "/health", None), ("POST", "/mul", {"a": 3, "b": 4}),
                           ("POST", "/mul", {"a": 3}), ("GET", "/mul", None), ("GET", "/nope", None)]:
    r = client.request(method, path, json=body)
    detail = r.json().get("detail")
    short = detail[0]["msg"] if isinstance(detail, list) else r.json()
    print(f"{method:4s} {path:7s} {str(body):16s} -> {r.status_code} {short}")

@@ concept
title: handler 里的推理：eval() 和 inference_mode
--- body
推理的两条规矩，第 18 天讲过：

- `model.eval()`：关掉 Dropout，BatchNorm 改用存下来的统计量。不关的话，同一个请求发两次，结果不一样。
- `torch.inference_mode()`：不记录计算图，更省内存，也更快。

放进服务里，这两条的写法不一样。

`model.eval()` 改的是模型对象本身。所有线程用的都是同一个模型，所以**加载完调用一次**就够了。

梯度开关却是**按线程**算的。FastAPI 在线程池里跑 `def` handler。你在启动时（主线程）写的 `torch.set_grad_enabled(False)`，管不到 handler 所在的线程。所以要在 handler **里面**写：

```
with torch.inference_mode():
    probs = model(x).softmax(-1)
```

最后用 `.tolist()` 把 tensor 变成 Python 列表，再放进返回的 dict。

下面的代码在主线程里关掉梯度，再开一个线程模拟 handler，看看那边的梯度开关。
--- code
import threading

torch.manual_seed(0)
model = nn.Sequential(nn.Linear(4, 8), nn.Dropout(0.5), nn.Linear(8, 3))
x = torch.randn(1, 4)
print("train 模式，两次一样吗:", torch.equal(model(x), model(x)))
model.eval()
print("eval 模式，两次一样吗: ", torch.equal(model(x), model(x)))

torch.set_grad_enabled(False)                    # 在主线程里关掉梯度
seen = {}

def handler():                                   # 模拟 FastAPI 在另一个线程里跑 handler
    seen["没写 inference_mode"] = model(x).requires_grad
    with torch.inference_mode():
        seen["写了 inference_mode"] = model(x).requires_grad

t = threading.Thread(target=handler)
t.start()
t.join()
torch.set_grad_enabled(True)
print("主线程关了梯度；另一个线程里，输出的 requires_grad:", seen)

title: 状态码、队列上限和超时
ref: day22
--- body
HTTP 状态码告诉客户端（还有监控系统）这个请求怎么样了。出错了还回 200，客户端以为成功了，监控里的错误率永远是 0。

今天用到这些：

- **200**：成功。
- **422**：输入不合格（pydantic 挡下的）。是客户端的错，原样重试没用。
- **404 / 405**：路径不存在 / 请求方法不对。
- **500**：服务器内部出错（bug，模型崩了）。只回一句「internal error」；异常的细节（文件路径、显存信息）写进服务器日志，不发给客户端。
- **503**：暂时没法服务：还在加载 / 预热，或者队列满了。加一个 `Retry-After` 响应头，告诉客户端过几秒再试。
- **504**：超时：请求等得太久，服务器不管它了。
- 另外还有 429：某一个客户端请求太频繁，被限流。它是按客户端算的，今天不写。

记法：4xx 是客户端的问题，5xx 是服务器的问题。

在 FastAPI 里，抛一个 `HTTPException` 就回对应的状态码：

```
raise HTTPException(status_code=503, detail="model is loading", headers={"Retry-After": "5"})
```

**一块 GPU，一个模型，一个队列。** 请求来得比模型算得快，就得排队。队列要有**上限**：满了立刻回 503，比让队列无限变长好。队列越长，每个请求等得越久，最后大家一起超时。

**超时**：客户端通常只等几秒。一个请求在队列里等了太久，客户端早就放弃了，这时再算它是浪费 GPU。所以轮到它时，先看它等了多久，超过上限就直接回 504，不跑模型。

测这些不用真的等：把「现在几点」做成一个参数 `clock`，测试时传一个假时钟 `FakeClock`，想让时间走多少，就 `advance` 多少。
--- code
from fastapi import FastAPI, HTTPException
from fastapi.testclient import TestClient

state = {"ready": False}
app = FastAPI()

@app.get("/health")
def health():
    if not state["ready"]:
        raise HTTPException(status_code=503, detail="loading", headers={"Retry-After": "5"})
    return {"status": "ok"}

client = TestClient(app)
r = client.get("/health")
print("加载中:", r.status_code, r.json(), "Retry-After =", r.headers["retry-after"])
state["ready"] = True
r = client.get("/health")
print("好了:  ", r.status_code, r.json())

clock = FakeClock()                              # 假时钟，单位毫秒
arrived = clock()                                # 请求进了队列
clock.advance(150)                               # 前面的请求一共算了 150 ms（不真的等）
waited = clock() - arrived
print(f"这个请求等了 {waited} ms，上限 100 ms ->", "回 504，不跑模型" if waited > 100 else "交给模型")

title: 延迟百分位数：p50、p95、p99
--- body
「平均延迟 20 ms」听着不错，可能其实是 98 个请求 10 ms、2 个请求 500 ms。那 2 个用户等了半秒。平均数把尾巴藏起来了。

所以要看百分位数（percentile）：

- **p50**（中位数）：一半的请求比它快。代表典型体验。
- **p95**：95% 的请求不比它慢。
- **p99**：100 个请求里最慢的那一个左右。服务的承诺（SLO，比如「p99 < 200 ms」）通常写的就是它。

算法有好几种，今天用最简单的 **nearest-rank**（最近秩）：

1. 从小到大排好序，一共 n 个。
2. k = ⌈q × n / 100⌉（⌈⌉ 是向上取整，`math.ceil`）。
3. 答案是第 k 小的那个（从 1 数，也就是 `s[k - 1]`）。

它返回的永远是真实出现过的一个延迟。`numpy.percentile` 和 `torch.quantile` 默认用**线性插值**：在相邻两个数之间按比例取一个值，结果可能不是任何一个真实的延迟。两种都有人用，报告里写清楚用的哪一种。

写 `q * n / 100`，不要写 `q / 100 * n`。前者先乘后除，碰到能整除的情况结果是精确的；后者可能带一点浮点误差，向上取整就多出 1。

几条经验：

- 样本要够多。只有 20 个数时，p99 就是最大值。p99 至少要几百个样本才有意义。
- 预热之后再测。失败的请求单独数（错误率），不要混进延迟里。
--- code
import math

times = [12, 11, 13, 12, 250, 11, 12, 14, 12, 13, 11, 12, 900, 12, 13, 12, 11, 12, 13, 12]
s = sorted(times)
n = len(s)
print("排好序:", s)
print(f"平均: {sum(s) / n:.1f} ms  <- 被两个慢请求拉高了，却看不出它们有多慢")
for q in (50, 95, 99):
    k = math.ceil(q * n / 100)
    lin = torch.quantile(torch.tensor(s, dtype=torch.float64), q / 100).item()
    print(f"p{q}: nearest-rank 取第 {k} 个 = {s[k - 1]} ms；线性插值 = {lin:.1f} ms")
print("p99.9、n = 1000 时，先除后乘:", 99.9 / 100 * 1000, "-> 向上取整", math.ceil(99.9 / 100 * 1000))
print("                 先乘后除:", 99.9 * 1000 / 100, "-> 向上取整", math.ceil(99.9 * 1000 / 100))

title: 吞吐和延迟：微批处理
ref: day22
--- body
有两个指标经常被混在一起：

- **延迟**（latency）：一个请求从发出到拿到结果花了多久。这是用户感受到的。
- **吞吐**（throughput）：一秒钟能处理多少个请求。它决定要买几台机器。

GPU 算一个 batch 的时间，大约是「固定开销 + 每行的开销」。假设一批 B 行要 10 + 1 × B 毫秒：

- B = 1：一批 11 ms，一秒约 91 个请求；
- B = 8：一批 18 ms，一秒约 444 个；
- B = 32：一批 42 ms，一秒约 762 个。

batch 越大，吞吐越高（固定开销被分摊了）。但每一批也更慢，而且吞吐有上限：这里一秒最多 1000 个。

线上的请求是一个一个来的。**微批处理**（micro-batching，也叫 dynamic batching）就是先把请求放进队列，凑成一批再跑：

- 凑满 `max_batch` 个，马上跑；
- 没凑满，但**最早**进队列的那个已经等了 `max_wait_ms`，也跑，有几个跑几个。

`max_wait_ms` 是给延迟定的上限：流量小的时候，一个请求最多多等这么久。流量大的时候，批很快就满了，基本不用等。

等待时间一定要从**最早**的请求算。如果从最新的请求算，只要请求不断地来，计时就不断被重置，最早的请求可能一直等下去。

下面先打印上面那张表，再用今天准备好的 `MicroBatcher` 模拟 8 个请求：max_batch = 4，max_wait_ms = 5。
--- code
print("  B   一批 ms   每秒请求数")
for B in [1, 2, 8, 32, 128]:
    ms = 10 + 1 * B
    print(f"{B:3d}   {ms:6d}   {B * 1000 / ms:8.0f}")

clock = FakeClock()
rec = BatchRecorder(lambda xb: xb * 2)           # 记下每一批的大小
batcher = MicroBatcher(rec, max_batch=4, max_wait_ms=5, clock=clock)
for t in [0, 1, 2, 3, 4, 20, 30, 31]:            # 8 个请求到达的时刻（毫秒）
    clock.now = t
    batcher.poll()                               # 服务器的循环：先看看有没有该跑的
    batcher.submit(torch.tensor([float(t)]))
clock.now = 40
batcher.poll()
print("请求到达的时刻: [0, 1, 2, 3, 4, 20, 30, 31]")
print("每一批的大小:", rec.sizes)

def warm_up(model, batch_sizes, clock):
    """对每个 batch 大小跑一次全 0 的假数据，返回 {B: 这一次用了多少毫秒}。"""
    model.eval()
    took = {}
    with torch.inference_mode():
        for b in batch_sizes:
            t0 = clock()
            model(torch.zeros(b, FEATURES))
            took[b] = clock() - t0              # 这一次 forward 花的毫秒数
    return took

def create_status_app(state):
    app = FastAPI()

    @app.get("/health")
    def health():
        if not state.ready:                      # readiness：没准备好就别让负载均衡器发流量过来
            raise HTTPException(status_code=503, detail="loading", headers={"Retry-After": "5"})
        return {"status": "ok"}

    @app.post("/predict")
    def predict(req: PredictRequest):
        if not state.ready:
            raise HTTPException(status_code=503, detail="model is loading", headers={"Retry-After": "5"})
        try:
            probs = state.predict(req.rows)
        except Exception:
            # 真实的服务在这里写日志：logger.exception("predict failed")，细节留在服务器上
            raise HTTPException(status_code=500, detail="internal error")
        return {"probs": probs}

    return app

补全 `RequestQueue` 的两个方法。GPU 上只有一个模型 `model_fn`，一次算一个请求；请求先进 `self.waiting` 列表排队。

每个请求用一个 `Ticket` 表示（已经准备好了）：`Ticket(x, arrived)`，有 `.x`、`.arrived`（到达的时刻，毫秒）、`.status`（None 表示还在排队）、`.result`。

class RequestQueue:
    def __init__(self, model_fn, clock, max_waiting=4, timeout_ms=100):
        self.model_fn = model_fn
        self.clock = clock              # clock() 返回现在的时刻（毫秒）
        self.max_waiting = max_waiting
        self.timeout_ms = timeout_ms
        self.waiting = []               # 排队中的 Ticket，最早的在最前面

    def submit(self, x):
        t = Ticket(x, self.clock())
        if len(self.waiting) >= self.max_waiting:
            t.status = 503              # 队列满了：马上拒绝，不让队列无限变长
        else:
            self.waiting.append(t)
        return t

    def run_next(self):
        if not self.waiting:
            return None
        t = self.waiting.pop(0)         # 先来先服务
        if self.clock() - t.arrived > self.timeout_ms:
            t.status = 504              # 客户端早就放弃了：不浪费 GPU
            return t
        try:
            t.result = self.model_fn(t.x)
            t.status = 200
        except Exception:
            t.status = 500              # 这一个失败了，队列照常往下走
        return t

import math

def latency_report(times_ms):
    s = sorted(times_ms)                 # sorted 返回一个新列表，不改动传进来的那个
    n = len(s)

    def pick(q):
        k = math.ceil(q * n / 100)       # 先乘后除，避开浮点误差
        return s[max(k, 1) - 1]          # 第 k 个（从 1 数）

    return {"p50": pick(50), "p95": pick(95), "p99": pick(99)}

class MicroBatcher:
    def __init__(self, run_batch, max_batch, max_wait_ms, clock):
        self.run_batch = run_batch      # (B, 4) -> B 行输出，一次处理一整批
        self.max_batch = max_batch
        self.max_wait_ms = max_wait_ms
        self.clock = clock              # clock() 返回现在的时刻（毫秒）
        self.pending = []               # 等着凑批的 Ticket，最早的在最前面

    def submit(self, x):
        t = Ticket(x, self.clock())
        self.pending.append(t)
        if len(self.pending) >= self.max_batch:
            self.flush()                # 凑满了：马上跑
        return t

    def poll(self):
        # 从「最早」的请求算等待时间；从最新的算，请求不断时就永远不跑
        if self.pending and self.clock() - self.pending[0].arrived >= self.max_wait_ms:
            self.flush()

    def flush(self):
        if not self.pending:
            return
        batch, self.pending = self.pending, []
        out = self.run_batch(torch.stack([t.x for t in batch]))   # 一整批只跑一次模型
        for t, y in zip(batch, out):
            t.result = y                # 第 i 行交还给第 i 个请求
            t.status = 200

--- prompt
一个微批处理器设置为 `max_batch = 16`，`max_wait_ms = 20`。下面哪些说法是**对的**？（可多选）
--- options
- 流量很小（每 100 ms 来一个请求）时，几乎每批只有 1 个请求，而且每个请求都白等了约 20 ms。
- 流量很大（每 0.5 ms 来一个请求）时，16 个请求约 7.5 ms 就凑满了，`max_wait_ms` 基本用不上。
- 把 `max_wait_ms` 调大，吞吐一定会变高。
- 等待时间从队列里最新的请求算起，对所有请求更公平。
- 流量小、又很在乎延迟时，可以把 `max_wait_ms` 调小，甚至调成 0。
answer: 1,2,5
--- explain
第 1 个对：100 ms 才来一个，20 ms 内等不到第二个，只能 1 个成一批，还多等了 20 ms。

第 2 个对：第 1 个请求到了之后，再来 15 个要 15 × 0.5 = 7.5 ms，批在等满 20 ms 之前就满了。

第 3 个错：流量小时，吞吐就是请求到达的速度，GPU 本来就闲着，多等只会让延迟变高；流量大时，批本来就是满的，多等也没用。只有 GPU 忙不过来、批又凑不满的时候，多等一点才能提高吞吐。

第 4 个错：从最新的算，请求不断时计时一直被重置，最早的请求可能一直等下去。

第 5 个对：`max_wait_ms = 0` 时，队列里一有请求就跑，延迟最低；代价是批更小，GPU 效率更低。流量小时这个代价不重要。

- 想一想：在 20 ms 里，能等来几个请求？
- 吞吐不会超过请求到达的速度。

def create_app(load_model):
    model = load_model()                         # 启动时加载一次
    model.eval()                                 # 关掉 Dropout
    with torch.inference_mode():                 # 预热：别让第一个用户等
        model(torch.zeros(1, FEATURES))
    app = FastAPI()

    @app.get("/health")
    def health():
        return {"status": "ok"}

    @app.post("/predict")
    def predict(req: PredictRequest):            # pydantic 检查不通过，FastAPI 自动回 422
        x = torch.tensor(req.rows, dtype=torch.float32)
        with torch.inference_mode():             # handler 在别的线程里跑：在这里关梯度
            probs = model(x).softmax(-1)
        return {"labels": [LABELS[i] for i in probs.argmax(-1).tolist()], "probs": probs.tolist()}

    return app

import math

def latency_report(times_ms):
    s = sorted(times_ms)                 # sorted 返回一个新列表，不改动传进来的那个
    n = len(s)

    def pick(q):
        k = math.ceil(q * n / 100)       # 先乘后除，避开浮点误差
        return s[max(k, 1) - 1]          # 第 k 个（从 1 数）

    return {"p50": pick(50), "p95": pick(95), "p99": pick(99)}

def _shuffled(values):
    return [values[i] for i in torch.randperm(len(values)).tolist()]

def _expect(times, want, why=""):
    got = latency_report(times)
    true(isinstance(got, dict), f"应该返回 dict，你返回的是 {type(got).__name__}")
    for key in ("p50", "p95", "p99"):
