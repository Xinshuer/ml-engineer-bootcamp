@@ concept
title: Service skeleton: load the model once at start-up
--- body
Serving a model means other programs send inputs over HTTP and get predictions back. A minimal model service has three parts:

1. **Start-up**: load the weights, call `model.eval()`, warm up (next card). Only then start taking requests.
2. **`/health`**: the health check. Load balancers (programs that spread traffic over several servers) and Kubernetes call it regularly and only send requests to servers that answer "ok".
3. **`/predict`**: take the input, check it, run the model, return JSON.

The most important rule: **load the model once at start-up; every request shares it.** Loading means reading the weight file (hundreds of MB to tens of GB), building the model and moving it to the GPU. That takes seconds to minutes. Put it in the handler (the function that handles one request) and every request pays that price again.

Today we use a "factory function" `create_app(load_model)`. It calls `load_model()` first, then builds the app. The handlers are functions defined inside `create_app`, so they can use the outer variable `model` (this is called a closure). The benefit: a test can pass in a fake `load_model` and count how often it is called. FastAPI also has an official start-up hook, `lifespan`, that does the same job.

One more rule: **one model per process.** `uvicorn --workers 4` starts 4 processes, and each one loads the model. On a GPU that is 4 copies in GPU memory, all fighting over the same card. The usual setup is one process and one model per GPU, with requests waiting in a queue inside that process (later cards).

The code below compares "load once" with "predict once" for a small model of about 4 MB.
--- code
import io
import time

def build():
    return nn.Sequential(*[nn.Linear(512, 512) for _ in range(4)])

weights = io.BytesIO()
torch.save(build().state_dict(), weights)       # pretend this is the weight file on disk

def load_model():
    weights.seek(0)
    m = build()
    m.load_state_dict(torch.load(weights, weights_only=True))
    return m.eval()

t0 = time.perf_counter()
model = load_model()
t_load = time.perf_counter() - t0

x = torch.randn(1, 512)
with torch.inference_mode():
    model(x)                                     # run once first (warm-up)
    t0 = time.perf_counter()
    model(x)
    t_pred = time.perf_counter() - t0
print(f"load once:    {t_load * 1000:.2f} ms")
print(f"predict once: {t_pred * 1000:.3f} ms")
print(f"Loading takes {t_load / t_pred:.0f}x as long as a prediction. Real models are thousands of times bigger and take seconds to minutes to load.")

@@ concept
title: Warm-up: be ready before taking requests
ref: day22
--- body
A model's first forward pass is often much slower than the ones after it. A lot of one-time set-up work is delayed until the first call:

- the first use of the GPU creates the CUDA context (hundreds of milliseconds to seconds);
- with `torch.backends.cudnn.benchmark = True`, cuDNN tries several algorithms for every new input shape and keeps the fastest;
- `torch.compile` compiles on the first call (seconds to tens of seconds) and may compile again when the shape changes;
- the memory allocator asks the GPU for memory for the first time.

If you do nothing, your first user pays for all of this. And every new batch size makes another user pay.

Warm-up: after start-up and before taking requests, run the model a few times on fake data, covering the shapes you will see in production (for example batch sizes 1, 8 and 32). Warm-up follows the inference rules too: `model.eval()` and `torch.inference_mode()`.

Until warm-up is done, the service is "alive" but "not ready". So there are usually two kinds of health check:

- liveness (is it alive?): answer 200 as long as the process is not stuck;
- readiness (is it ready?): answer 200 only when loading and warm-up are done, and **503** before that. Load balancers only send requests to ready servers.

On a CPU the effect is small and hard to show. So the code below simulates it with today's `SlowStartModel`: the first forward for each new batch size costs an extra 500 ms, a normal one costs 2 + 0.25·B ms. The time goes onto a fake clock, `FakeClock` (in milliseconds; it only moves when you call `advance`), so nothing really waits.
--- code
def serve(request_sizes, warm_sizes):
    clock = FakeClock()
    model = SlowStartModel(clock).eval()
    with torch.inference_mode():
        for b in warm_sizes:                     # warm-up: run the shapes you will see before going live
            model(torch.zeros(b, 4))
        took = []
        for b in request_sizes:                  # the real requests
            t0 = clock()
            model(torch.randn(b, 4))
            took.append(clock() - t0)
    return took

reqs = [1, 1, 8, 8, 32]
print("batch size of each request:", reqs)
print("no warm-up, ms per request:", serve(reqs, warm_sizes=[]))
print("after warming 1/8/32, ms:  ", serve(reqs, warm_sizes=[1, 8, 32]))

title: pydantic: keep bad input out
--- body
Production requests contain everything: a number missing, a number too many, strings, `null`, NaN, a hundred thousand rows at once. Turn that into a tensor without checking and you get a shape error (the service answers 500), one NaN that turns the whole batch's output into NaN, or one huge request that eats all the GPU memory.

With pydantic you write down, as types, what valid input looks like. It rejects everything else for you. For example, a service for 3D points, with 3 coordinates per point and 1 to 8 points per request:

```
from typing import Annotated
from pydantic import BaseModel, Field, FiniteFloat

Point = Annotated[list[FiniteFloat], Field(min_length=3, max_length=3)]

class PointsRequest(BaseModel):
    points: list[Point] = Field(min_length=1, max_length=8)
```

Piece by piece:

- `BaseModel`: inherit from it and the fields you declare get checked.
- `FiniteFloat`: a finite float; NaN and inf are rejected. A plain `float` lets them through.
- `Annotated[type, Field(...)]`: adds limits to a type. `min_length` / `max_length` limit the length of a list. Here: exactly 3 numbers per point.
- `points: list[Point] = Field(min_length=1, max_length=8)`: 1 to 8 points. The upper limit stops huge requests.

`PointsRequest.model_validate(a dict)` does the check. Valid input returns an object; invalid input raises `ValidationError`, which says at which position (loc) what went wrong.

Note that pydantic is "lax" by default: the string `"1.5"` becomes `1.5` and the integer `3` becomes `3.0`. To reject strings like `"1.5"`, use strict mode (for example `model_validate(..., strict=True)`). Even in strict mode, an integer is still accepted as a float.

Inside FastAPI, a failed check automatically becomes a **422** response (Unprocessable Entity: the JSON can be read, but its content is not valid). Your handler is never called.
--- code
from typing import Annotated
from pydantic import BaseModel, Field, FiniteFloat, ValidationError

Point = Annotated[list[FiniteFloat], Field(min_length=3, max_length=3)]

class PointsRequest(BaseModel):
    points: list[Point] = Field(min_length=1, max_length=8)

for payload in [{"points": [[0.5, 1.0, 2.0]]},
                {"points": [[0.5, 1.0]]},
                {"points": [[0.5, 1.0, float("nan")]]},
                {"points": [["1.5", 3, 2.0]]},
                {"points": []}]:
    try:
        req = PointsRequest.model_validate(payload)
        print("accepted:", req.points)
    except ValidationError as e:
        err = e.errors()[0]
        print("rejected:", err["loc"], err["msg"])

@@ concept
title: FastAPI and TestClient: test without opening a port
ref: day22
--- body
FastAPI turns Python functions into HTTP endpoints in a few lines:

```
app = FastAPI()

@app.get("/health")
def health():
    return {"status": "ok"}

@app.post("/predict")
def predict(req: PredictRequest):
    ...
    return {"labels": [...], "probs": [...]}
```

- `@app.get(path)` / `@app.post(path)`: which path and which request method this function handles. Use GET to read, POST to send data to be computed on.
- A parameter written as `req: PredictRequest`: FastAPI hands the request's JSON body to pydantic, calls your function only if the check passes, and answers 422 otherwise.
- Return a dict and it becomes JSON. It may only contain Python numbers, strings and lists; call `.tolist()` on tensors first.
- An unknown path gets 404. A known path with the wrong method (for example GET on a POST-only path) gets 405.

Tests do not need a real server. `TestClient(app)` simulates HTTP requests inside the same Python process:

```
client = TestClient(app)
r = client.post("/predict", json={"rows": [[5.1, 3.5, 1.4, 0.2]]})
r.status_code     # 200
r.json()          # the parsed dict
```

One detail you will need later: a handler written with `def` (not `async def`) runs in another thread (a thread pool).
--- code
from fastapi import FastAPI
from fastapi.testclient import TestClient
from pydantic import BaseModel

class Pair(BaseModel):
    a: float
    b: float

app = FastAPI()

@app.get("/health")
def health():
    return {"status": "ok"}

@app.post("/mul")
def mul(req: Pair):
    return {"product": req.a * req.b}

client = TestClient(app)
for method, path, body in [("GET", "/health", None), ("POST", "/mul", {"a": 3, "b": 4}),
                           ("POST", "/mul", {"a": 3}), ("GET", "/mul", None), ("GET", "/nope", None)]:
    r = client.request(method, path, json=body)
    detail = r.json().get("detail")
    short = detail[0]["msg"] if isinstance(detail, list) else r.json()
    print(f"{method:4s} {path:7s} {str(body):16s} -> {r.status_code} {short}")

@@ concept
title: Inference in the handler: eval() and inference_mode
--- body
The two inference rules from day 18:

- `model.eval()`: turns Dropout off and makes BatchNorm use its stored statistics. Without it, the same request sent twice gives two different answers.
- `torch.inference_mode()`: records no computation graph, so it uses less memory and runs faster.

In a service, the two rules are written in different places.

`model.eval()` changes the model object itself. Every thread uses the same model, so **calling it once after loading** is enough.

The autograd switch, however, is **per thread**. FastAPI runs `def` handlers in a thread pool. A `torch.set_grad_enabled(False)` at start-up (in the main thread) does not reach the thread the handler runs in. So write it **inside** the handler:

```
with torch.inference_mode():
    probs = model(x).softmax(-1)
```

Finally, turn tensors into Python lists with `.tolist()` before putting them in the returned dict.

The code below switches autograd off in the main thread, then starts another thread that plays the handler, and looks at the switch over there.
--- code
import threading

torch.manual_seed(0)
model = nn.Sequential(nn.Linear(4, 8), nn.Dropout(0.5), nn.Linear(8, 3))
x = torch.randn(1, 4)
print("train mode, same result twice?", torch.equal(model(x), model(x)))
model.eval()
print("eval mode, same result twice? ", torch.equal(model(x), model(x)))

torch.set_grad_enabled(False)                    # autograd off in the main thread
seen = {}

def handler():                                   # plays FastAPI running a handler in another thread
    seen["without inference_mode"] = model(x).requires_grad
    with torch.inference_mode():
        seen["with inference_mode"] = model(x).requires_grad

t = threading.Thread(target=handler)
t.start()
t.join()
torch.set_grad_enabled(True)
print("autograd is off in the main thread; requires_grad of the output in the other thread:", seen)

@@ concept
title: Status codes, queue limits and timeouts
ref: day22
--- body
The HTTP status code tells the client (and the monitoring system) what happened to a request. Answer 200 on errors and the client thinks it worked, and the error rate on your dashboard stays at 0 forever.

The ones we use today:

- **200**: success.
- **422**: invalid input (stopped by pydantic). The client's fault; retrying the same request will not help.
- **404 / 405**: unknown path / wrong request method.
- **500**: something broke inside the server (a bug, the model crashed). Answer only "internal error"; the details of the exception (file paths, GPU memory) go into the server's log, not to the client.
- **503**: cannot serve right now: still loading / warming up, or the queue is full. Add a `Retry-After` header to tell the client how many seconds to wait before trying again.
- **504**: timeout: the request waited too long and the server gave up on it.
- There is also 429: one particular client sends too many requests and gets rate-limited. It is counted per client; we do not write it today.

A way to remember: 4xx means the client has a problem, 5xx means the server has a problem.

In FastAPI you raise an `HTTPException` to answer with a status code:

```
raise HTTPException(status_code=503, detail="model is loading", headers={"Retry-After": "5"})
```

**One GPU, one model, one queue.** When requests arrive faster than the model can compute, they have to wait. The queue needs a **limit**: when it is full, answer 503 at once. That is better than a queue that keeps growing: the longer the queue, the longer every request waits, until they all time out.

**Timeouts**: clients usually wait only a few seconds. If a request has waited in the queue too long, its client has already given up, and computing it wastes the GPU. So when its turn comes, check how long it has waited; over the limit, answer 504 and do not run the model.

Testing this needs no real waiting: make "what time is it" a parameter `clock`, pass a fake clock `FakeClock` in the test, and `advance` it by as much time as you like.
--- code
from fastapi import FastAPI, HTTPException
from fastapi.testclient import TestClient

state = {"ready": False}
app = FastAPI()

@app.get("/health")
def health():
    if not state["ready"]:
        raise HTTPException(status_code=503, detail="loading", headers={"Retry-After": "5"})
    return {"status": "ok"}

client = TestClient(app)
r = client.get("/health")
print("loading:", r.status_code, r.json(), "Retry-After =", r.headers["retry-after"])
state["ready"] = True
r = client.get("/health")
print("ready:  ", r.status_code, r.json())

clock = FakeClock()                              # a fake clock, in milliseconds
arrived = clock()                                # the request enters the queue
clock.advance(150)                               # the requests ahead of it took 150 ms (no real waiting)
waited = clock() - arrived
print(f"this request waited {waited} ms, the limit is 100 ms ->", "answer 504, do not run the model" if waited > 100 else "hand it to the model")

title: Latency percentiles: p50, p95, p99
--- body
"Average latency 20 ms" sounds fine. It could be 98 requests at 10 ms and 2 requests at 500 ms. Those 2 users waited half a second. The average hides the tail.

So we look at percentiles:

- **p50** (the median): half of the requests are faster. The typical experience.
- **p95**: 95% of the requests are not slower than this.
- **p99**: roughly the slowest request out of 100. Service promises (SLOs, such as "p99 < 200 ms") are usually written in terms of it.

There are several ways to compute a percentile. Today we use the simplest one, **nearest-rank**:

1. Sort from small to large; there are n values.
2. k = ⌈q × n / 100⌉ (⌈⌉ means round up, `math.ceil`).
3. The answer is the k-th smallest value (counting from 1, so `s[k - 1]`).

It always returns a latency that really happened. `numpy.percentile` and `torch.quantile` use **linear interpolation** by default: they take a value in between two neighbouring numbers, which may not be any real latency. Both methods are in use; say in your report which one you used.

Write `q * n / 100`, not `q / 100 * n`. The first multiplies before dividing, so when the division comes out even, the result is exact. The second can carry a tiny floating-point error, and rounding up then adds 1.

Some practical rules:

- Collect enough samples. With only 20 values, p99 is simply the maximum. p99 needs at least a few hundred samples to mean anything.
- Measure after warm-up. Count failed requests separately (the error rate); do not mix them into the latencies.
--- code
import math

times = [12, 11, 13, 12, 250, 11, 12, 14, 12, 13, 11, 12, 900, 12, 13, 12, 11, 12, 13, 12]
s = sorted(times)
n = len(s)
print("sorted:", s)
print(f"mean: {sum(s) / n:.1f} ms  <- pulled up by two slow requests, yet it does not show how slow they were")
for q in (50, 95, 99):
    k = math.ceil(q * n / 100)
    lin = torch.quantile(torch.tensor(s, dtype=torch.float64), q / 100).item()
    print(f"p{q}: nearest-rank takes value number {k} = {s[k - 1]} ms; linear interpolation = {lin:.1f} ms")
print("p99.9 with n = 1000, divide first:  ", 99.9 / 100 * 1000, "-> rounded up", math.ceil(99.9 / 100 * 1000))
print("                     multiply first:", 99.9 * 1000 / 100, "-> rounded up", math.ceil(99.9 * 1000 / 100))

@@ concept
title: Throughput vs latency: micro-batching
ref: day22
--- body
Two measures often get mixed up:

- **Latency**: how long one request takes from sending it to getting the result. This is what users feel.
- **Throughput**: how many requests are handled per second. This decides how many machines you need.

The time a GPU needs for a batch is roughly "fixed cost + cost per row". Suppose a batch of B rows takes 10 + 1 × B milliseconds:

- B = 1: 11 ms per batch, about 91 requests per second;
- B = 8: 18 ms per batch, about 444 per second;
- B = 32: 42 ms per batch, about 762 per second.

Bigger batches give higher throughput (the fixed cost is shared). But each batch takes longer, and throughput has a ceiling: here at most 1000 per second.

In production, requests arrive one at a time. **Micro-batching** (also called dynamic batching) puts them in a queue first and runs them as a batch:

- when `max_batch` requests are waiting, run them at once;
- when fewer are waiting, but the **oldest** one has waited `max_wait_ms`, run what is there.

`max_wait_ms` is a cap on the extra latency: with little traffic, a request waits at most this long. With heavy traffic, batches fill up quickly and hardly anyone waits.

Always measure the wait from the **oldest** request. If you measure from the newest one, the timer restarts with every new arrival, and as long as requests keep coming, the oldest one may wait forever.

The code below prints the table above, then uses today's `MicroBatcher` to simulate 8 requests with max_batch = 4 and max_wait_ms = 5.
--- code
print("  B   ms/batch   requests/s")
for B in [1, 2, 8, 32, 128]:
    ms = 10 + 1 * B
    print(f"{B:3d}   {ms:6d}   {B * 1000 / ms:8.0f}")

clock = FakeClock()
rec = BatchRecorder(lambda xb: xb * 2)           # records the size of every batch
batcher = MicroBatcher(rec, max_batch=4, max_wait_ms=5, clock=clock)
for t in [0, 1, 2, 3, 4, 20, 30, 31]:            # arrival times of 8 requests (ms)
    clock.now = t
    batcher.poll()                               # the server loop: first see if anything is due
    batcher.submit(torch.tensor([float(t)]))
clock.now = 40
batcher.poll()
print("arrival times: [0, 1, 2, 3, 4, 20, 30, 31]")
print("batch sizes:", rec.sizes)

--- code
from fastapi import FastAPI
from fastapi.testclient import TestClient
from pydantic import BaseModel, Field

class AddRequest(BaseModel):
    x: list[float] = Field(min_length=2, max_length=2)

app = FastAPI()

@app.post("/add")
def add(req: AddRequest):
    return {"sum": req.x[0] + req.x[1]}

client = TestClient(app)
print(client.post("/add", json={"x": [1, 2]}).json())
print(client.post("/add", json={"x": [1, 2, 3]}).status_code)
print(client.post("/add", json={"x": ["1.5", 2]}).json())

print(client.post("/add", json={"y": [1, 2]}).status_code)
print(client.get("/add").status_code)
--- explain
1. `{'sum': 3.0}`: pydantic turned both integers into floats, 1.0 + 2.0 = 3.0. It prints a Python dict, hence the single quotes.
2. `422`: 3 numbers break `max_length=2`. The handler is never called.
3. `{'sum': 3.5}`: the string `"1.5"` can be read as a number, so pydantic's default lax mode turns it into 1.5. To reject it, use strict mode.
4. `422`: `"one"` is not a number and cannot be converted.
5. `422`: the required field `x` is missing. The extra `y` is ignored by default.
6. `405`: the path `/add` exists but only accepts POST, and this is a GET (Method Not Allowed). An unknown path would be 404.
--- hints
- 422 means "the JSON can be read, but the content is invalid": when pydantic's check fails, FastAPI answers 422 automatically.
- By default pydantic converts strings that look like numbers into numbers.
- "Wrong method" and "unknown path" are two different status codes.

FEATURES = 4
MAX_ROWS = 32

# one row: exactly 4 finite numbers
Row = Annotated[list[FiniteFloat], Field(min_length=FEATURES, max_length=FEATURES)]

class PredictRequest(BaseModel):

        return True

def warm_up(model, batch_sizes, clock):
    """Run all-zero fake data once per batch size; return {B: milliseconds that run took}."""
    model.eval()
    took = {}
    with torch.inference_mode():
        for b in batch_sizes:
            t0 = clock()
            model(torch.zeros(b, FEATURES))
            took[b] = clock() - t0              # milliseconds this forward pass took
    return took

    app = FastAPI()

    @app.get("/health")
    def health():
        if not state.ready:                      # readiness: not ready, so the load balancer must not send traffic
            raise HTTPException(status_code=503, detail="loading", headers={"Retry-After": "5"})
        return {"status": "ok"}

    @app.post("/predict")
    def predict(req: PredictRequest):
        if not state.ready:
            raise HTTPException(status_code=503, detail="model is loading", headers={"Retry-After": "5"})
        try:
            probs = state.predict(req.rows)
        except Exception:
            # a real service logs here: logger.exception("predict failed"); the details stay on the server
            raise HTTPException(status_code=500, detail="internal error")
        return {"probs": probs}

    return app

class RequestQueue:
    def __init__(self, model_fn, clock, max_waiting=4, timeout_ms=100):
        self.model_fn = model_fn
        self.clock = clock              # clock() returns the current time (ms)
        self.max_waiting = max_waiting
        self.timeout_ms = timeout_ms
        self.waiting = []               # waiting Tickets, oldest first

    def submit(self, x):
        t = Ticket(x, self.clock())
        if len(self.waiting) >= self.max_waiting:
            t.status = 503              # queue full: reject at once, never let the queue grow without limit
        else:
            self.waiting.append(t)
        return t

    def run_next(self):
        if not self.waiting:
            return None
        t = self.waiting.pop(0)         # first come, first served
        if self.clock() - t.arrived > self.timeout_ms:
            t.status = 504              # the client gave up long ago: do not waste the GPU
            return t
        try:
            t.result = self.model_fn(t.x)
            t.status = 200
        except Exception:
            t.status = 500              # this one failed; the queue carries on
        return t

import math

def latency_report(times_ms):
    s = sorted(times_ms)                 # sorted returns a new list and leaves the given one alone
    n = len(s)

    def pick(q):
        k = math.ceil(q * n / 100)       # multiply first, then divide: avoids floating-point error
        return s[max(k, 1) - 1]          # value number k (counting from 1)

    return {"p50": pick(50), "p95": pick(95), "p99": pick(99)}

class MicroBatcher:
    def __init__(self, run_batch, max_batch, max_wait_ms, clock):
        self.run_batch = run_batch      # (B, 4) -> B output rows; handles a whole batch at once
        self.max_batch = max_batch
        self.max_wait_ms = max_wait_ms
        self.clock = clock              # clock() returns the current time (ms)
        self.pending = []               # Tickets waiting for a batch, oldest first

    def submit(self, x):
        t = Ticket(x, self.clock())
        self.pending.append(t)
        if len(self.pending) >= self.max_batch:
            self.flush()                # the batch is full: run it now
        return t

    def poll(self):
        # measure the wait from the OLDEST request; measured from the newest, a steady stream never runs
        if self.pending and self.clock() - self.pending[0].arrived >= self.max_wait_ms:
            self.flush()

    def flush(self):
        if not self.pending:
            return
        batch, self.pending = self.pending, []
        out = self.run_batch(torch.stack([t.x for t in batch]))   # one model call for the whole batch
        for t, y in zip(batch, out):
            t.result = y                # row i goes back to request i
            t.status = 200

def create_app(load_model):
    model = load_model()                         # load once at start-up
    model.eval()                                 # Dropout off
    with torch.inference_mode():                 # warm-up: do not make the first user wait
        model(torch.zeros(1, FEATURES))
    app = FastAPI()

    @app.get("/health")
    def health():
        return {"status": "ok"}

    @app.post("/predict")
    def predict(req: PredictRequest):            # if pydantic's check fails, FastAPI answers 422 by itself
        x = torch.tensor(req.rows, dtype=torch.float32)
        with torch.inference_mode():             # the handler runs in another thread: switch autograd off here
            probs = model(x).softmax(-1)
        return {"labels": [LABELS[i] for i in probs.argmax(-1).tolist()], "probs": probs.tolist()}

    return app

import math

def latency_report(times_ms):
    s = sorted(times_ms)                 # sorted returns a new list and leaves the given one alone
    n = len(s)

    def pick(q):
        k = math.ceil(q * n / 100)       # multiply first, then divide: avoids floating-point error
        return s[max(k, 1) - 1]          # value number k (counting from 1)

    return {"p50": pick(50), "p95": pick(95), "p99": pick(99)}
