@@ concept
title: How many bytes a tensor takes
--- body
GPU memory and RAM are counted in bytes. A tensor takes (number of elements) × (bytes per element). In code that is `t.numel() * t.element_size()`, or simply `t.nbytes`.

Bytes per element for the common dtypes:

- float32 (fp32): 4
- bfloat16 (bf16), float16 (fp16): 2
- int8: 1
- int64 (also called long, e.g. class labels): 8

A model's memory = **parameters** + **buffers**. A buffer is a tensor the model saves with itself and moves with `.to(device)`, but does not train, for example BatchNorm's `running_mean` and `running_var`. Loop over them with `model.parameters()` and `model.buffers()`.

Two easy mistakes:

- A frozen parameter (`requires_grad=False`) is not trained, but it still takes memory.
- A shared weight takes memory only once. Many language models use the same matrix for the input embedding and the output layer. `model.parameters()` removes duplicates for you; `model.state_dict()` lists the matrix twice.
--- code
for dt in [torch.float32, torch.bfloat16, torch.int64]:
    print(dt, "per element:", torch.zeros(1, dtype=dt).element_size(), "bytes")

model = nn.Sequential(nn.Linear(512, 512), nn.BatchNorm1d(512))
for name, t in model.named_parameters():
    print("param ", name, tuple(t.shape), t.dtype, t.numel() * t.element_size(), "bytes")
for name, t in model.named_buffers():
    print("buffer", name, tuple(t.shape), t.dtype, t.numel() * t.element_size(), "bytes")

emb = nn.Embedding(100, 16)
head = nn.Linear(16, 100, bias=False)
head.weight = emb.weight                     # the output layer shares the embedding matrix
tied = nn.ModuleDict({"emb": emb, "head": head})
print("parameters() has", len(list(tied.parameters())), "tensor(s); state_dict() has", len(tied.state_dict()))

@@ concept
title: The four parts of training memory
--- body
During training, GPU memory goes to four places:

1. **Weights**: one number per parameter.
2. **Gradients**: after `backward()`, every parameter has a `.grad` of the same size.
3. **Optimizer states**: Adam keeps two numbers per parameter, the first moment m and the second moment v, usually in fp32, 4 bytes each. Plain SGD keeps nothing; SGD with momentum keeps one.
4. **Activations**: intermediate results saved in the forward pass for the backward pass. They change with batch size and sequence length; the next card is about them.

The first three depend only on the number of parameters. Remember them as bytes per parameter:

- fp32 training + Adam: weights 4 + grads 4 + Adam 8 = **16 bytes**
- mixed precision + Adam: bf16 weights 2 + bf16 grads 2 + fp32 master weights 4 + Adam 8 = **still 16 bytes**
- pure bf16 (weights, grads and Adam states all bf16): 2 + 2 + 4 = **8 bytes**

Master weights are an extra fp32 copy of the weights that mixed-precision training keeps. The optimizer updates this copy, because bf16 is so coarse that a tiny update would round to zero. So mixed precision mainly saves activation memory and compute time, not these three parts. (PyTorch's own `torch.autocast` works differently: weights and grads stay fp32 and are cast to bf16 only for the computation. That is also 4 + 4 + 8 = 16 bytes.)

Let's do a 7B (7 billion parameter) model. To keep the sums simple, this course uses 1 GB = 10⁹ bytes:

- Inference only, bf16 weights: 7×10⁹ × 2 = 14 GB
- Full training in fp32 + Adam: 7×10⁹ × 16 = 112 GB. That is before activations, and it already does not fit on one 80 GB GPU.

This is why people fine-tune large models with LoRA (day 6), split these states across several GPUs (ZeRO / FSDP), or use 8-bit optimizers. (A GPU sold as "24 GB" really has 24×2³⁰ ≈ 25.8×10⁹ bytes; for estimates you can ignore that 7%.)
--- code
model = nn.Linear(1000, 1000)
opt = torch.optim.Adam(model.parameters())
model(torch.randn(8, 1000)).sum().backward()
opt.step()                                   # Adam creates m and v at the first step

w = sum(p.nbytes for p in model.parameters())
g = sum(p.grad.nbytes for p in model.parameters())
s = sum(v.nbytes for st in opt.state.values() for k, v in st.items() if k != "step")
print("weights", w, " grads", g, " Adam states", s, "bytes")   # 1 : 1 : 2

n = 7_000_000_000
for name, per_param in [("fp32 + Adam", 4 + 4 + 8), ("mixed precision + Adam", 2 + 2 + 4 + 8), ("pure bf16 + Adam", 2 + 2 + 4)]:
    print(f"7B {name}: {per_param} bytes per parameter -> {n * per_param / 1e9:.0f} GB (no activations)")

@@ concept
title: Activations grow with batch and length
--- body
In the forward pass, many layers save their input or output because the backward pass needs it. For example, for `y = x @ W`, the gradient of W needs x. These saved intermediate results are the activations.

Activations do not depend on the number of parameters. They grow with how much data you feed in at once: double the batch and they double; double the sequence length and they at least double (plain attention also stores a T×T score matrix, which grows faster).

A rough estimate for a Transformer: in the forward pass each layer saves a dozen or more tensors of size (batch, seq, hidden) (the various intermediate results of attention and the MLP). This course uses 16:

```
activations per sample ≈ seq × hidden × layers × 16 × bytes per value
```

Example: 24 layers, hidden 2048, seq 2048, bf16 (2 bytes). One sample needs about 3.2 GB of activations. This model has about 1.2 billion parameters, so the first three parts with mixed precision + Adam (16 bytes per parameter) take about 19.3 GB. A 24 GB GPU has only about 4.7 GB left for activations: the micro-batch can be 1 at most. To use bigger batches: gradient accumulation (day 17), activation checkpointing (a later card), or shorter sequences.

You can "measure" activations without a GPU. `torch.autograd.graph.saved_tensors_hooks` calls you every time autograd saves a tensor for the backward pass. The `saved_bytes` function below adds up their bytes: each block of memory counts once, and tensors in `skip` (such as the model's parameters) exist anyway, so they do not count. The tests of several exercises today use this function.
--- code
def act_bytes_per_sample(seq, hidden, n_layers, bytes_per_value, tensors_per_layer=16):
    return seq * hidden * n_layers * tensors_per_layer * bytes_per_value

per = act_bytes_per_sample(2048, 2048, 24, 2)
print(f"{per / 1e9:.2f} GB per sample; batch=8 needs {8 * per / 1e9:.1f} GB")

def saved_bytes(fn, *args, skip=()):
    skip_ptrs = {t.untyped_storage().data_ptr() for t in skip}
    seen = {}
    def pack(t):                              # called each time autograd saves a tensor for backward
        s = t.untyped_storage()
        if s.data_ptr() not in skip_ptrs:
            seen[s.data_ptr()] = s.nbytes()   # each block of memory counts once
        return t
    with torch.autograd.graph.saved_tensors_hooks(pack, lambda t: t):
        out = fn(*args)
    return out, sum(seen.values())

mlp = nn.Sequential(nn.Linear(64, 256), nn.GELU(), nn.Linear(256, 64))
for batch in (8, 16, 32):
    _, n = saved_bytes(mlp, torch.randn(batch, 64), skip=mlp.parameters())
    print(f"batch={batch:2d}: saved {n} bytes for backward")

@@ concept
title: Leaks: a stored loss keeps its whole graph
--- body
A tensor that needs gradients (a loss, for example) carries a `grad_fn`. Through it you can reach the whole computation graph, and the graph holds the activations of the forward pass. As long as you keep that tensor, all of this stays alive.

The classic mistake:

```
losses.append(loss)      # stores a tensor, still connected to its graph
total += loss            # total becomes a tensor with a graph too, and every step joins the same chain
```

- If that step never calls `backward()` (a validation loop, or you only wanted to log the value), the whole graph and all its activations stay in GPU memory. A few batches later you get OOM (out of memory).
- Even with `backward()` (which frees the activations stored in the graph), the graph nodes remain, and `total += loss` links every step's graph into one chain that keeps growing. Memory creeps up.

The fix: if you want to keep a number, keep a number. `loss.item()` returns a Python float that has nothing to do with the graph. If you need to keep a tensor (predictions, say), use `.detach()`, and usually `.cpu()` to move it out of GPU memory. (On a GPU, `.item()` has to wait for the GPU to finish, so for logging you can call it every N steps.)

How to read GPU memory: `nvidia-smi` shows the memory PyTorch has **reserved**. PyTorch has a caching allocator: when a tensor is freed, its memory stays with PyTorch for the next tensor instead of going back to the driver. So:

- `torch.cuda.memory_allocated()`: memory that tensors really use
- `torch.cuda.max_memory_allocated()`: the peak so far
- `torch.cuda.memory_reserved()`: everything PyTorch holds, close to the nvidia-smi number

The code below shows a leak without a GPU. `weakref.ref(h)` is a weak reference: it does not keep h alive. If the weak reference can still reach h after the loop, something else (the graph) is holding on to it.
--- code
import weakref

torch.manual_seed(0)
model = nn.Sequential(nn.Linear(4, 256), nn.ReLU(), nn.Linear(256, 1))

def run(keep_tensor):
    alive, kept = [], []
    for _ in range(3):
        h = model[1](model[0](torch.randn(64, 4)))   # an intermediate activation, (64, 256)
        alive.append(weakref.ref(h))
        loss = model[2](h).pow(2).mean()              # no backward, e.g. we only log it
        kept.append(loss if keep_tensor else loss.item())
        del h, loss
    return [r() is not None for r in alive], kept[0]

print("append(loss)        activations still alive?", run(True))
print("append(loss.item()) activations still alive?", run(False))

@@ concept
title: No graph at inference: no_grad and inference_mode
--- body
By default, as soon as one input needs gradients (and model parameters do), PyTorch builds a computation graph and saves activations as it computes. Inference and validation never run a backward pass, so that is wasted memory and wasted time.

- Tensors computed inside `with torch.no_grad():` have `requires_grad=False`, no `grad_fn`, and no activations are saved.
- `with torch.inference_mode():` goes further and skips some internal bookkeeping too, so it is a little faster. The price: the "inference tensors" it creates cannot be used later in a computation that needs gradients, or you get an error.
- Both also work as decorators: put `@torch.no_grad()` or `@torch.inference_mode()` above a function.

Note: they control the computations done inside the with block. They do not change the parameters' `requires_grad`. Outside the block, results computed with the same model carry a graph again.

Also, `model.eval()` is a different thing (day 18): it switches how dropout and BatchNorm behave and has nothing to do with the graph. For inference you need both.
--- code
lin = nn.Linear(4, 2)
x = torch.randn(3, 4)

y = lin(x)
print("default:        requires_grad =", y.requires_grad, " has grad_fn:", y.grad_fn is not None)
with torch.no_grad():
    y = lin(x)
print("no_grad:        requires_grad =", y.requires_grad, " has grad_fn:", y.grad_fn is not None)
with torch.inference_mode():
    y = lin(x)
print("inference_mode: requires_grad =", y.requires_grad, " is_inference =", y.is_inference())
print("the parameter:  lin.weight.requires_grad =", lin.weight.requires_grad)

try:
    lin(y).sum().backward()        # use an inference tensor for training
except RuntimeError as e:
    print("error:", str(e).split(".")[0])

@@ concept
title: Timing: warm up, synchronize, take the median
--- body
"How much faster did this change make the model?" You answer that with timing. There are three common ways to get it wrong:

1. **No warm-up.** The first call is often much slower: memory gets allocated, cuDNN picks its algorithms, `torch.compile` compiles. So run the function a few times first (warm-up) and do not time those runs.
2. **No synchronization.** The GPU is asynchronous: `y = model(x)` only puts the work in a queue and returns at once, while the GPU keeps working in the background. If you read the clock before the work is done, you measure only the time to queue it. So call `torch.cuda.synchronize()` (wait until the GPU has finished everything in its queue) before you read the start time and before you read the end time. The first one makes sure leftover work (from the warm-up, say) is not counted in this run.
3. **One run, or the mean.** Every run's time jitters (other programs, the OS scheduler). Run many times and take the **median** (the middle value after sorting). One unusually slow run does not move the median; it pulls the mean up.

Read the time with `time.perf_counter()`, a high-resolution clock made for measuring intervals. `time.time()` is calendar time: less precise, and the system may adjust it.

The code first uses a "fake GPU" to show point 2: `launch` only queues work, and only `sync` moves the clock forward. No real time passes, so the output is the same every run.
--- code
import statistics, time

class FakeGPU:
    def __init__(self):
        self.now, self.pending = 0.0, 0.0
    def launch(self, seconds):        # like a CUDA kernel: queue the work, return at once
        self.pending += seconds
    def sync(self):                   # like torch.cuda.synchronize(): wait for the queue
        self.now += self.pending
        self.pending = 0.0
    def clock(self):
        return self.now

gpu = FakeGPU()
t0 = gpu.clock(); gpu.launch(0.010); t1 = gpu.clock()
print(f"no sync:               {t1 - t0:.3f} s   only the queueing was measured")
t0 = gpu.clock(); gpu.launch(0.010); gpu.sync(); t1 = gpu.clock()
print(f"sync only at the end:  {t1 - t0:.3f} s   includes the 10 ms left over from before")
gpu.sync(); t0 = gpu.clock(); gpu.launch(0.010); gpu.sync(); t1 = gpu.clock()
print(f"sync before and after: {t1 - t0:.3f} s   correct")

times = [0.010, 0.011, 0.250, 0.010, 0.012]     # one run was interrupted by another program
print("mean:", round(statistics.mean(times), 4), " median:", statistics.median(times))

x = torch.randn(256, 256)
for _ in range(3):                  # warm-up
    x @ x
ts = []
for _ in range(20):
    t0 = time.perf_counter()
    x @ x
    ts.append(time.perf_counter() - t0)
print(f"256x256 matmul on this CPU: median {statistics.median(ts) * 1e3:.3f} ms")

@@ concept
title: Activation checkpointing: compute for memory
ref: day19
--- body
Activation checkpointing (also called gradient checkpointing): in the forward pass, a block saves none of its internal intermediate results, only its input. In the backward pass, it runs the block again from that input to get the intermediate results it needs, then computes the gradients.

- You save: each block keeps just one input tensor, so activations drop from a dozen or more copies per layer to about one.
- You pay: every block's forward runs twice, roughly one third more compute.
- Nothing changes in the outputs or the gradients. It is a different way to compute the same math, using less memory.

How to write it:

```
from torch.utils.checkpoint import checkpoint
x = checkpoint(block, x, use_reentrant=False)   # instead of x = block(x)
```

Always pass `use_reentrant=False`. The old `use_reentrant=True` has a trap: if none of the tensors you pass in needs gradients (for example, the first layer's input is just data), the parameters inside that part get no gradients, and backward may even raise an error. If you leave the argument out, current PyTorch warns you and still uses the old True.

Dropout inside a block is fine: by default checkpoint remembers the random-number state and reuses the same dropout mask when it recomputes, so the gradients are identical.

The code below measures it with `saved_bytes` from the card "Activations grow with batch and length".
--- code
from torch.utils.checkpoint import checkpoint

torch.manual_seed(0)
blocks = nn.ModuleList([nn.Sequential(nn.Linear(64, 256), nn.GELU(), nn.Linear(256, 64)) for _ in range(4)])
x = torch.randn(32, 64)

def plain(x):
    for b in blocks:
        x = b(x)
    return x

def ckpt(x):
    for b in blocks:
        x = checkpoint(b, x, use_reentrant=False)
    return x

grads = []
for f in (plain, ckpt):
    blocks.zero_grad()
    out, n = saved_bytes(f, x, skip=blocks.parameters())
    out.pow(2).mean().backward()
    grads.append([p.grad.clone() for p in blocks.parameters()])
    print(f"{f.__name__:5s}: saved {n:6d} bytes for backward")
print("identical gradients:", all(torch.equal(a, b) for a, b in zip(*grads)))

@@ concept
title: DataLoader workers and torch.compile recompiles
--- body
### DataLoader

With `num_workers=0`, loading and preprocessing happen in the main process while the GPU waits. With a value like `num_workers=4`, the DataLoader starts a few child processes (workers) that prepare the next batches in parallel.

- Windows and macOS start workers with spawn: each worker is a brand-new Python that first imports your script again. The top-level code of your script runs again in every worker. If the top level builds the DataLoader and starts training, each worker tries to start its own workers, and Python raises a RuntimeError. So put the training code in a function and guard it with `if __name__ == "__main__":`.
- Define your Dataset class in a .py file that can be imported. A class defined in a Jupyter notebook cannot be found by spawned workers.
- `pin_memory=True`: puts batches in page-locked memory, which copies to the GPU faster and allows `.to("cuda", non_blocking=True)` to copy while the GPU computes.
- `persistent_workers=True`: keeps the workers alive after an epoch, so the next epoch does not start them again (starting them is slow on Windows).

```
def main():
    loader = DataLoader(ds, batch_size=32, num_workers=4, pin_memory=True, persistent_workers=True)
    for x, y in loader:
        ...

if __name__ == "__main__":
    main()
```

### torch.compile

On the first call, `torch.compile` compiles the model into faster code for the shapes of that input. This can take seconds or even tens of seconds. Later calls with the same shapes reuse it. A new shape triggers a recompile. With the default settings, when a second, different shape shows up, PyTorch marks the changing dimension as "dynamic" and compiles once more; later new lengths can usually reuse that code. With `dynamic=False`, every new shape compiles again, until a limit (8 in this version); after that it stops compiling and falls back to plain, slower execution.

What to do in production: warm up at start-up with a few typical shapes, or pad inputs to a few fixed lengths (e.g. 64, 128, 256; this is called bucketing). To see why a recompile happened, set the environment variable `TORCH_LOGS=recompiles`.

The code below prints how this machine starts workers, then counts compiles with a backend that only counts and does not really compile.
--- code
import multiprocessing
print("how this machine starts workers:", multiprocessing.get_start_method())

compiles = []
def counting_backend(gm, example_inputs):
    compiles.append(1)
    return gm.forward                          # no real compiling, run the code as it is

for dynamic in (None, False):
    compiles.clear()
    torch._dynamo.reset()                      # forget earlier compiles so every run prints the same
    f = torch.compile(lambda x: (x * 2).sum(), backend=counting_backend, dynamic=dynamic)
    for n in [4, 4, 5, 6, 7, 4]:
        f(torch.ones(n))
    print(f"dynamic={dynamic}: lengths 4,4,5,6,7,4 compiled {len(compiles)} time(s)")

--- solution
PER_PARAM = {           # weights, grads, master, adam
    "fp32": (4, 4, 0, 8),
    "mixed": (2, 2, 4, 8),
    "bf16": (2, 2, 0, 4),
}

def train_state_bytes(n_params, precision):
    if precision not in PER_PARAM:

--- context
When you debug GPU memory, the first step is reading the right number. nvidia-smi does not show the memory tensors are using right now. Read the wrong number and you will chase a leak that does not exist.
--- prompt
A training script runs on a GPU. You `del` a 4 GB tensor (and you checked that no other variable refers to it). `torch.cuda.memory_allocated()` drops by 4 GB, but in nvidia-smi the process uses exactly as much memory as before. What is the most likely reason?
--- options
- `del` only removes the variable name; the tensor itself is freed only when the program exits
- PyTorch's caching allocator keeps that memory for the next tensor; it still counts in `torch.cuda.memory_reserved()`, and that is what nvidia-smi sees
- The tensor was moved to CPU memory automatically and the driver has not updated yet
- Memory has leaked and only restarting the process helps
answer: 2
--- explain
`memory_allocated()` went down, so the tensor really was freed. PyTorch does not give freed memory back to the driver; it keeps it (reserved) and reuses it for the next allocation, because asking the driver for memory is slow. Your program can use those 4 GB later; other processes cannot. `torch.cuda.empty_cache()` gives unused cached memory back to the driver, which you usually need only when you share the GPU with other processes. Only if `memory_allocated()` did not go down is something still referring to the tensor, such as a loss stored in a list that keeps its graph.
--- hints
- Note that the question says `memory_allocated()` already went down.
- Asking the GPU driver for memory is slow, so PyTorch keeps the memory it got and reuses it.

import statistics
import time

def benchmark(fn, warmup=3, runs=10, clock=time.perf_counter, sync=None):
    for _ in range(warmup):
        fn()
    times = []
    for _ in range(runs):
        if sync is not None:
            sync()               # first wait for earlier work (e.g. the warm-up) to finish
        t0 = clock()
        fn()
        if sync is not None:
            sync()               # wait until this call has really finished
        times.append(clock() - t0)
    return statistics.median(times)

--- context
A training script that runs fine on a Linux server crashes on a Windows PC as soon as num_workers is set. The reason: the two systems start child processes in different ways.
--- prompt
You run `train.py` on Windows. These lines sit at the top level of the file, with no function and no `if __name__ == "__main__":`:

```
ds = MyDataset("data/")
loader = DataLoader(ds, batch_size=32, num_workers=4)
for x, y in loader:
    train_step(x, y)
```

What happens?
--- options
- It runs normally: 4 workers load data in parallel, faster than `num_workers=0`
- A RuntimeError: each worker is a freshly started Python that runs the top level of train.py again, so it builds a DataLoader and tries to start workers of its own; Python sees "a new process is being started before this one has finished starting" and raises an error
- PyTorch detects Windows, falls back to `num_workers=0` and prints a warning
- No error, but every batch is read 4 times and training goes wrong
answer: 2
--- explain
On Windows, Python starts child processes with spawn: the new process first imports your main script (with `__name__` set to `"__mp_main__"`, not `"__main__"`), then takes its work. Unguarded top-level code runs again in every worker, and each worker tries to start workers. Python raises a RuntimeError ("An attempt has been made to start a new process before the current process has finished its bootstrapping phase"), and the main process then reports "DataLoader worker (pid ...) exited unexpectedly". The fix: put the training code in `main()` and end the file with `if __name__ == "__main__": main()`. On Linux, Python 3.13 and earlier use fork by default (copy the running process, without running the script again), which is why the same script often works on a server.
--- hints
- On Windows, a child process is not a copy; it is a new Python started from scratch.
- The new Python first imports your script. What happens to the lines at its top level?

- The 1st request compiled code for the fixed length 37; the 2nd request's length did not match, which triggered a recompile, and this time PyTorch treated the length as a dynamic dimension and compiled general code that later lengths reuse

import statistics
import time

def benchmark(fn, warmup=3, runs=10, clock=time.perf_counter, sync=None):
    for _ in range(warmup):
        fn()
    times = []
    for _ in range(runs):
        if sync is not None:
            sync()
        t0 = clock()
        fn()
        if sync is not None:
            sync()
        times.append(clock() - t0)
    return statistics.median(times)
--- tests

--- solution
PER_PARAM = {           # weights, grads, master, adam
    "fp32": (4, 4, 0, 8),
    "mixed": (2, 2, 4, 8),
    "bf16": (2, 2, 0, 4),
}

def train_state_bytes(n_params, precision):
    if precision not in PER_PARAM:
        raise ValueError(precision)
    w, g, m, a = PER_PARAM[precision]
    out = {"weights": n_params * w, "grads": n_params * g, "master": n_params * m, "adam": n_params * a}
    out["total"] = sum(out.values())
    return out
