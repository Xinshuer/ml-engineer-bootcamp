@@ concept
title: The inference checklist
ref: day21
--- body
The same model runs differently in training and in production. Before you serve a model (run inference), go through this checklist:

1. **`model.eval()`** switches to inference mode. Dropout stops dropping values at random. BatchNorm uses the statistics it collected during training (`running_mean` / `running_var`) and stops updating them. Forget this, and the same input gives a different prediction every time.
2. **`with torch.inference_mode():`** tells PyTorch not to record a computation graph (the graph is only needed for backward, to compute gradients). It saves memory and is faster. The output has `requires_grad == False`.
3. **The same preprocessing as in training**: the same normalisation statistics, the same tokenizer version (day 18 covers this in detail).

Today's exercises all use this small model `Net`. It is already defined in the hidden setup code:

```
class Net(nn.Module):              # 8 features -> 3 classes
    def __init__(self, hidden=16, p_drop=0.5):
        super().__init__()
        self.fc1 = nn.Linear(8, hidden)
        self.bn = nn.BatchNorm1d(hidden)
        self.drop = nn.Dropout(p_drop)
        self.fc2 = nn.Linear(hidden, 3)

    def forward(self, x):
        return self.fc2(self.drop(F.relu(self.bn(self.fc1(x)))))
```

`trained_net()` returns a "trained" Net: its BatchNorm statistics are already filled in, and it is still in train mode, just like a model that has just finished training.

In the code below, `num_batches_tracked` counts how many times BatchNorm was updated in train mode.
--- code
torch.manual_seed(0)
net = trained_net()               # train mode
x = torch.randn(3, 8)

print("train mode, same result twice:", torch.equal(net(x), net(x)))
print("BatchNorm updates so far:", net.bn.num_batches_tracked.item())

net.eval()
with torch.inference_mode():
    a, b = net(x), net(x)
print("eval mode, same result twice:", torch.equal(a, b))
print("BatchNorm updates so far:", net.bn.num_batches_tracked.item())
print("output requires grad:", a.requires_grad)

@@ concept
title: Export: turning a Python model into a fixed graph
ref: day21
--- body
PyTorch is convenient for training, but the production machine may not have Python or PyTorch at all: it may be a C++ service, a phone, or a dedicated inference engine (onnxruntime, TensorRT). So you first "export" the model into a computation graph: a fixed list of operations, where every step and every shape is written down.

`torch.export.export(model, (x,))` works like this:

1. It runs `forward` once, with the example input `x` you give it.
2. While it runs, it records every tensor operation (linear, relu, ...). What it records is the graph.
3. Plain Python does not go into the graph: a `print` runs only once, during the export; a `for` loop is unrolled (3 iterations give 3 copies of the operations); an `if self.use_relu:` that looks at a Python variable is decided during the export.

Two consequences to remember:

- Shapes in the graph are **fixed** by default: export with a `(2, 4)` example, and the graph only accepts `(2, 4)`. The card "A dynamic batch dimension" shows how to make the batch size variable.
- The graph records whatever the model does in its current mode. Export with `torch.export` in train mode, and the Dropout in the graph is switched on (the last two lines of the code below). So always call `model.eval()` before exporting. `torch.onnx.export` also warns you when the model is in train mode: `Exporting a model while it is in training mode`.

The first call to `torch.export` takes 1–2 seconds (it is loading things); later calls are fast.
--- code
class Tiny(nn.Module):
    def __init__(self):
        super().__init__()
        self.fc = nn.Linear(4, 4)

    def forward(self, x):
        print("forward is running, x has shape", tuple(x.shape))
        for _ in range(3):                    # a Python loop: unrolled into 3 copies
            x = torch.relu(self.fc(x))
        return x

ep = torch.export.export(Tiny(), (torch.randn(2, 4),))
print("operations in the graph:", [n.target.__name__ for n in ep.graph.nodes if n.op == "call_function"])

net = Net()
for mode in ("train", "eval"):
    getattr(net, mode)()                      # the same as net.train() or net.eval()
    ep = torch.export.export(net, (torch.randn(2, 8),))
    drop = [n.args[2] for n in ep.graph.nodes if n.op == "call_function" and "dropout" in n.target.__name__]
    print("exported in", mode, "mode, dropout switched on in the graph:", drop)

@@ concept
title: Export to ONNX, then check it with onnxruntime
ref: day21
--- body
ONNX is a common file format for models: one `.onnx` file holds the computation graph and the weights. onnxruntime is an inference engine made to run ONNX files. It does not need PyTorch and runs on CPUs and GPUs.

To export (`dynamo=True` selects the new exporter: it captures the graph with `torch.export`, then translates it to ONNX):

```
model.eval()
prog = torch.onnx.export(model, (example,), dynamo=True, verbose=False)
prog.save(path)                    # write the .onnx file
```

- The second argument is a **tuple**: `(example,)`. Do not forget the comma.
- `verbose=False` turns off the progress messages.
- The returned `prog` is an `ONNXProgram`; `.save(path)` writes it to a file. Today every file goes into a temporary folder made by `tempfile.TemporaryDirectory()`, which is deleted automatically afterwards.
- One export takes 1–3 seconds.

To run it with onnxruntime:

```
sess = ort.InferenceSession(path, providers=["CPUExecutionProvider"])
name = sess.get_inputs()[0].name              # read the input's name from the file
out = sess.run(None, {name: x.numpy()})[0]    # None = all outputs; it returns a list
```

onnxruntime takes numpy arrays and returns numpy arrays.

**Always compare after exporting**: run the same input through PyTorch and through onnxruntime, and look at the largest difference, `np.abs(a - b).max()`. The two will not be exactly equal. Different libraries add numbers in a different order, and with floating-point numbers `(a + b) + c` and `a + (b + c)` can differ in the last digit. In fp32, differences of 1e-7 to 1e-5 are normal, and 1e-4 is a common tolerance. A difference of 1e-2 or more is a real bug: wrong weights in the export, PyTorch not in `eval()` mode, different preprocessing, ...
--- code
import os, tempfile
import numpy as np
import onnxruntime as ort

torch.manual_seed(0)
net = trained_net().eval()
x = torch.randn(2, 8)
prog = torch.onnx.export(net, (x,), dynamo=True, verbose=False)

with tempfile.TemporaryDirectory() as folder:
    path = os.path.join(folder, "net.onnx")
    prog.save(path)
    print("file size:", os.path.getsize(path), "bytes")
    sess = ort.InferenceSession(path, providers=["CPUExecutionProvider"])
    inp = sess.get_inputs()[0]
    print("input:", inp.name, inp.shape)
    got = sess.run(None, {inp.name: x.numpy()})[0]
    del sess                                  # close the session first, so the folder can be deleted

with torch.inference_mode():
    want = net(x).numpy()
print("onnxruntime, row 1:", got.round(4)[0])
print("PyTorch,     row 1:", want.round(4)[0])
print("largest difference:", np.abs(got - want).max())

@@ concept
title: A dynamic batch dimension: say which dimension can change
ref: day21
--- body
The previous card exported with a `(2, 8)` example, so the input shape in the file is `[2, 8]`: it only accepts batch = 2. Feed it 5 samples and onnxruntime fails:

```
INVALID_ARGUMENT : Got invalid dimensions for input: x for the following indices
 index: 0 Got: 5 Expected: 2
```

In production, every request has a different number of samples. So when you export, say that dimension 0 (the batch) can change:

```
prog = torch.onnx.export(
    model, (example,), dynamo=True, verbose=False,
    input_names=["x"], output_names=["logits"],     # names of the input and output in the file
    dynamic_shapes={"x": {0: "batch"}},             # dimension 0 of argument x can change; call it batch
)
```

- The keys of `dynamic_shapes` are **the names of forward's arguments**. `Net.forward(self, x)` has an argument called `x`; `nn.Sequential`'s argument is called `input`, and a wrong name raises `its top-level keys must be the arg names`. You can also skip the names and give a tuple, by position: `dynamic_shapes=({0: "batch"},)`.
- `input_names` / `output_names` are the names stored in the file. Without them, the input is named after the argument and the output gets an automatic name (such as `linear_1`), which is awkward for whoever calls the model.
- After the export, the input shape is `['batch', 8]`: a string means "this dimension can change".
- After exporting, compare with PyTorch at a few different batch sizes (1, medium, large).
--- code
import os, tempfile
import numpy as np
import onnxruntime as ort

torch.manual_seed(0)
net = trained_net().eval()
prog = torch.onnx.export(net, (torch.randn(2, 8),), dynamo=True, verbose=False,
                         input_names=["x"], output_names=["logits"],
                         dynamic_shapes={"x": {0: "batch"}})

with tempfile.TemporaryDirectory() as folder:
    path = os.path.join(folder, "net.onnx")
    prog.save(path)
    sess = ort.InferenceSession(path, providers=["CPUExecutionProvider"])
    print("input:", sess.get_inputs()[0].name, sess.get_inputs()[0].shape)
    print("output:", sess.get_outputs()[0].name, sess.get_outputs()[0].shape)
    for b in (1, 7, 64):
        x = torch.randn(b, 8)
        got = sess.run(None, {"x": x.numpy()})[0]
        with torch.inference_mode():
            diff = np.abs(got - net(x).numpy()).max()
        print(f"batch = {b}: output shape {got.shape}, largest difference {diff:.1e}")
    del sess

@@ concept
title: Export failure no. 1: a Python if on a tensor's value
ref: day21
--- body
During an export, forward runs once and the graph records only tensor operations. A Python `if` has to pick a branch right there:

- `if x.shape[1] != 8:` or `if self.use_relu:` is fine: the answer (a shape, a Python variable) is known during the export. Whichever branch runs is the one that gets recorded.
- `if x.mean() > 0:` depends on the **values in the input**. Today's input takes one branch; tomorrow's may take the other. A fixed graph cannot hold a Python branch like this, so the export fails:

```
GuardOnDataDependentSymNode: Could not guard on data-dependent expression Eq(u0, 1)
```

"Data-dependent" means "depends on the values of the data". With `torch.onnx.export(dynamo=True)`, this error is wrapped in `TorchExportError: Failed to export the model with torch.export. This is step 1/3 ...`, and the real reason is further down, under `Exception summary`.

A row-by-row `for row in x:` loop with an `if row.sum() > 0:` inside has the same problem.

**The fix: compute both branches, then pick with `torch.where`.** `torch.where(cond, a, b)` takes a where cond is True and b everywhere else. It is an ordinary tensor operation, so it goes into the graph. cond can be smaller than a and b; it is broadcast:

- one condition for the whole input: `torch.where(x.mean() > 0, x * 2, -x)`
- one condition per row: `n = x.norm(dim=1, keepdim=True)` has shape `(B, 1)`; `torch.where(n > 1, x / n, x)` picks separately for each row.

Some branches already have an operation for them: `x.clamp(max=10)`, `torch.maximum(x, y)`, `F.relu(x)`.

The code below uses a small helper from the setup code, `export_error(model, x)`: it calls `torch.export.export` quietly and returns None if the export works, or the one-line reason if it fails.
--- code
class Bad(nn.Module):
    def forward(self, x):
        if x.mean() > 0:                      # needs the values in x to pick a branch
            return x * 2
        return -x

class Good(nn.Module):
    def forward(self, x):
        return torch.where(x.mean() > 0, x * 2, -x)   # compute both, pick by the condition

x = torch.randn(3, 4)
print("Bad :", export_error(Bad(), x))
print("Good:", export_error(Good(), x))       # None = the export works
for inp in (x.abs(), -x.abs()):               # try each branch once
    print("same result:", torch.equal(Bad()(inp), Good()(inp)))

@@ concept
title: int8 quantization: one byte per weight
--- body
An fp32 weight takes 4 bytes. Quantization means storing numbers with fewer bytes. int8 numbers are whole numbers from -128 to 127 and take 1 byte each.

How to turn decimals into integers (symmetric quantization):

```
scale = max(|w|) / 127                   # the largest |w| maps to 127
q = round(w / scale), kept in [-127, 127] # stored as int8
w ≈ q * scale                            # multiply back when you use it (dequantize)
```

- You store `q` (1 byte per number) and `scale` (one decimal number). The weights get about 4× smaller.
- Rounding adds an error: each number is off by at most `scale / 2`.
- Weights smaller than `scale / 2` become exactly 0.
- With one scale for the whole matrix (per-tensor), one very large number makes the scale large, so the small numbers only get a few integers and a bigger error (see row 2 in the code below). That is why, in practice, each row (each output channel) often gets its own scale (per-channel).

The "dynamic" in "dynamic quantization" is about the activations (the inputs of each layer): the weights are quantized ahead of time and stored as int8; the activations are quantized on the fly, at every inference, from the range of the current batch. So it needs no extra calibration data and takes one line of code. PyTorch's dynamic quantization runs only on the CPU and mainly replaces `nn.Linear` (next card).
--- code
w = torch.tensor([[0.50, -0.20, 0.01],
                  [0.02, 0.03, -0.04]])
scale = w.abs().max() / 127                  # one scale for the whole matrix
q = torch.round(w / scale).clamp(-127, 127).to(torch.int8)
w_back = q.float() * scale                   # dequantize

print("scale:", round(scale.item(), 5))
print("q:", q.tolist(), q.dtype)
print("every error <= scale / 2:", bool(((w - w_back).abs() <= scale / 2 + 1e-7).all()))
print("row 2 before:", [round(v, 4) for v in w[1].tolist()])
print("row 2 after: ", [round(v, 4) for v in w_back[1].tolist()])

@@ concept
title: Dynamic quantization: size, accuracy, speed
ref: day21
--- body
One line of PyTorch replaces every `nn.Linear` in a model with an int8 version:

```
q = torch.ao.quantization.quantize_dynamic(model, {nn.Linear}, dtype=torch.qint8)
```

- It returns a **new model** and leaves the original alone (it makes a copy first).
- `{nn.Linear}`: only layers of these types are replaced.
- The new layers print as `DynamicQuantizedLinear`.

Quantization is not free. Before you ship, check all three costs:

1. **Size**: measure "how big is it when saved". Save the `state_dict` with `torch.save` into an in-memory `io.BytesIO()` and count the bytes. **Do not count `parameters()`**: the quantized weights are packed in a special format and are no longer `nn.Parameter`s, so `parameters()` is empty.
2. **Accuracy**: run the same batch through both models and compare the outputs. The largest difference is one hint; more useful is "the share of predictions (argmax) that stay the same". In a real project, recompute your metric (accuracy, ...) on the validation set.
3. **Speed**: depends on the CPU model, the compute backend and the batch size. On some machines it is a lot faster; on others it is even slower. Always measure on the machine you will serve on (warm up first, time many runs, take the median; see day 19).

For large language models on GPUs, other quantization methods are common (weight-only int8 / int4, for example bitsandbytes, GPTQ, AWQ). The idea is the same: store the weights in fewer bytes and pay with a little accuracy.

`make_mlp()` below comes from the setup code: `Linear(256, 512) -> ReLU -> Linear(512, 10)`.
--- code
import io, time

torch.manual_seed(0)
model = make_mlp().eval()
q = torch.ao.quantization.quantize_dynamic(model, {nn.Linear}, dtype=torch.qint8)
print(q[0])

def size_bytes(m):
    buf = io.BytesIO()
    torch.save(m.state_dict(), buf)
    return buf.getbuffer().nbytes

print("numbers in parameters():", sum(p.numel() for p in model.parameters()), "->", sum(p.numel() for p in q.parameters()))
print("bytes when saved:", size_bytes(model), "->", size_bytes(q))

x = torch.randn(256, 256)
with torch.inference_mode():
    a, b = model(x), q(x)
print("largest difference:", round((a - b).abs().max().item(), 4))
print("share of equal argmax:", (a.argmax(1) == b.argmax(1)).float().mean().item())

def median_ms(m, n=30):
    ts = []
    with torch.inference_mode():
        for i in range(n + 5):
            t0 = time.perf_counter()
            m(x)
            if i >= 5:                        # the first 5 runs are warm-up and do not count
                ts.append(time.perf_counter() - t0)
    return sorted(ts)[n // 2] * 1000

print(f"fp32 {median_ms(model):.2f} ms, int8 {median_ms(q):.2f} ms (different on every machine)")

@@ concept
title: fp16 and bf16 inference
ref: day21
--- body
Another way to compress: store each number in 2 bytes (half precision) instead of 4. It halves memory and bandwidth, and on GPUs that support it, it is much faster (it uses the Tensor Cores). There are two half-precision types:

- **fp16**: the largest number it can hold is 65504. Anything larger becomes `inf`, and a few operations later, `nan`. In exchange, it keeps a few more significant digits (a bit over 3).
- **bf16**: the same range as fp32 (largest about 3.4e38), so it rarely overflows. The price: only 2–3 significant digits. 70000 becomes 70144, and 1.001 becomes 1.0.

Which one: on recent NVIDIA GPUs (A100, RTX 30 series and later), prefer bf16; almost all large language models use it. With fp16, watch out for overflow: attention scores and large activations can exceed 65504.

How: `model.to(torch.bfloat16)`, and **convert the inputs too**: `x.to(torch.bfloat16)`. Convert only the model and you get `mat1 and mat2 must have the same dtype`. You can also use `torch.autocast` and let PyTorch choose which operations run in half precision.

When you compare with fp32, use a looser tolerance: bf16 differences are often 1e-3 to 1e-2. Day 18 covers precision and tolerances in detail.
--- code
for dt in (torch.float32, torch.float16, torch.bfloat16):
    fi = torch.finfo(dt)
    print(f"{str(dt):15} {torch.tensor([], dtype=dt).element_size()} bytes per number, largest {fi.max:.3g}, precision eps {fi.eps:.3g}")

big = torch.tensor([70000.0, 1.001])
print("fp16:", big.half().tolist())
print("bf16:", big.bfloat16().tolist())

torch.manual_seed(0)
net = trained_net().eval()
x = torch.randn(4, 8)
with torch.inference_mode():
    want = net(x)
    out = net.to(torch.bfloat16)(x.to(torch.bfloat16))
print(f"bf16 output: {out.dtype}, largest difference from fp32: {(out.float() - want).abs().max().item():.4f}")

@@ item d21-03
type: choice
title: How big a difference is normal?
level: 1
cards: Export to ONNX, then check it with onnxruntime
--- context
Comparing two implementations on the same input is the most important habit in deployment. But first you need to know what difference is normal: a tolerance that is too strict raises false alarms every day; one that is too loose lets real bugs through.
--- prompt
You export an fp32 model to ONNX. On the same input, the largest difference between the onnxruntime and PyTorch outputs is `3e-7`. What does that tell you?
--- options
- The export has a bug: the two should be exactly equal, the difference must be 0
- It is normal: the two libraries add numbers in a different order; in fp32 a difference this small is common, so compare with a tolerance around 1e-4
- onnxruntime is secretly computing in fp16
- PyTorch was not switched to model.eval()
answer: 2
--- explain
Floating-point addition is not associative: `(a + b) + c` and `a + (b + c)` can differ in the last digit. PyTorch and onnxruntime use different kernels: they add in a different order, and they may fuse several steps into one. So the results differ a tiny bit. fp32 has about 7 significant digits, so differences from 1e-7 to 1e-5 are normal.

import numpy as np
import onnxruntime as ort

def verify_export(model, path, example, batch_sizes=(1, 4, 16), tol=1e-4):
    model.eval()
    sess = ort.InferenceSession(path, providers=["CPUExecutionProvider"])
    name = sess.get_inputs()[0].name
    worst = 0.0
    for b in batch_sizes:
        x = torch.randn(b, *example.shape[1:])
        with torch.inference_mode():
            want = model(x).numpy()
        got = sess.run(None, {name: x.numpy()})[0]
        worst = max(worst, float(np.abs(got - want).max()))
    if worst > tol:
        raise AssertionError(f"ONNX and PyTorch differ by {worst:.2e}, more than the tolerance {tol}")
    return worst

class ClipNorm(nn.Module):

    scale = (w.abs().amax(dim=1, keepdim=True) / 127).clamp_min(1e-8)   # (out, 1)

--- explain
- The largest number fp16 can hold is 65504. 70000 is above it and becomes `inf`; 1000 is fine. So: `[False, True]`.
- bf16 has the same range as fp32 (largest about 3.4e38), so neither number overflows: `[False, False]`. The price is precision: 70000 is actually stored as 70144.
- Bytes per number: 4 for fp32, 2 for both fp16 and bf16.

import numpy as np
import onnxruntime as ort

def verify_export(model, path, example, batch_sizes=(1, 4, 16), tol=1e-4):
    model.eval()
    sess = ort.InferenceSession(path, providers=["CPUExecutionProvider"])
    name = sess.get_inputs()[0].name
    worst = 0.0
    for b in batch_sizes:
        x = torch.randn(b, *example.shape[1:])
        with torch.inference_mode():
            want = model(x).numpy()
        got = sess.run(None, {name: x.numpy()})[0]
        worst = max(worst, float(np.abs(got - want).max()))
    if worst > tol:
        raise AssertionError(f"ONNX and PyTorch differ by {worst:.2e}, more than the tolerance {tol}")
    return worst
