@@ concept
title: The first loss should be about ln C
--- body
A classifier that has just been initialized knows nothing. It should give each of the C classes roughly the same probability, about 1/C.

Cross-entropy is the negative log of "the probability of the correct class". So the loss at the first step should be about -ln(1/C) = **ln C**:

- 10 classes: ln 10 ≈ 2.30
- GPT-2's vocabulary has 50257 tokens: ln 50257 ≈ 10.8

Work this number out in your head before training starts, then compare it with the first loss in the log:

- About the same (a few tenths apart): fine.
- Much larger: the model starts out "confidently wrong". Common causes: the initial weights are too large, or the logits (the raw score the model gives each class, before softmax) are scaled up.
- Much smaller: a model that has learned nothing cannot beat guessing, so the loss is probably computed wrong, or the weights are not freshly initialized (for example, a trained checkpoint was loaded by mistake). A label that leaked into the input does not lower the first loss; it shows up a few steps later, as a loss that falls towards 0 suspiciously fast.

In the example below, a normally initialized model has a first loss of 2.478, close to ln 10 = 2.303. Multiply the weights by 30 and the first loss becomes 25.738.
--- code
torch.manual_seed(0)
C = 10
model = nn.Linear(32, C)
x = torch.randn(64, 32)
y = torch.randint(0, C, (64,))

print("ln C                    =", round(math.log(C), 3))
print("first loss              =", round(F.cross_entropy(model(x), y).item(), 3))
with torch.no_grad():
    model.weight.mul_(30)            # pretend the initialization is too large
print("loss with weights x 30  =", round(F.cross_entropy(model(x), y).item(), 3))

@@ concept
title: Reading a loss curve: flat, exploding, bouncing, floor
--- body
Print the loss every few steps (or plot it) and look at its shape first. These are the usual ways it can look wrong:

- **Flat**: it stays near the first value (around 2.30 with 10 classes). The model is learning nothing. Either the parameters are not being updated at all (frozen, missing from the optimizer, lr is 0), or the labels do not match the inputs.
- **Exploding**: it keeps growing, often all the way to inf or nan. The most common cause is a learning rate that is too high.
- **Bouncing**: it jumps up and down with no downward trend. Usually the learning rate is a bit too high.
- **Floor**: it drops to some value and never goes lower, even on one small batch. This is almost always a code bug, for example an extra softmax before cross_entropy.

The learning rate (lr) is how far each step moves along the gradient. It decides the shape of the curve. Here is the simplest possible demo: one parameter w, loss = (w - 3)², lowest at w = 3.

- lr = 0.05: each step moves only a little; the loss falls slowly.
- lr = 0.4: w reaches 3 in a few steps; the loss falls to 0.
- lr = 1.1: every step jumps over the bottom of the valley to the other side of 3, and each jump lands further away, so the loss keeps growing. That is "exploding". In real training, a few more jumps make the weights so large that they overflow, and the loss becomes inf or nan.
--- code
for lr in (0.05, 0.4, 1.1):
    w = torch.tensor(0.0, requires_grad=True)
    ws, losses = [], []
    for step in range(6):
        loss = (w - 3) ** 2
        ws.append(round(w.item(), 2))
        losses.append(round(loss.item(), 2))
        w.grad = None
        loss.backward()
        with torch.no_grad():
            w -= lr * w.grad            # move lr times the gradient, downhill
    print(f"lr={lr:<5} w   : {ws}")
    print(f"{'':9}loss: {losses}")

@@ concept
title: Where NaN and inf come from
--- body
inf means "infinity". nan means "Not a Number". Once either one appears in the loss, backward carries it into every gradient. After one optimizer step every weight is nan, and the model is ruined. The usual sources:

- **log(0) = -inf**: a probability came out as exactly 0 (for example, a softmax probability too small for float32).
- **exp of a large number**: float32 tops out at about 3.4e38. exp(88.7) already reaches it; anything larger is inf.
- **Division by 0**: 1/0 = inf and 0/0 = nan. For example, standardizing by the standard deviation when one column has the same value everywhere, so its standard deviation is 0.
- **inf used in more math**: 0 × inf = nan, inf - inf = nan.
- **Square root or log of a negative number**: nan.
- **fp16 overflow** (next card) and **a learning rate that is too high** (the weights grow with every update until they overflow).

One more trap: **every comparison with nan is False**. `nan > 10` is False, and even `nan == nan` is False. So `if loss > 100: alert` never catches a nan.

To check whether a number is normal, use `math.isfinite(x)` (Python numbers) or `torch.isfinite(t)` (tensors). They return True for ordinary numbers and False for nan, inf and -inf.
--- code
print(torch.exp(torch.tensor([10.0, 50.0, 90.0])).tolist())   # 90 already overflows
print(torch.tensor(-1.0).sqrt().item(), float("inf") - float("inf"))

x = torch.tensor([[1.0, 5.0], [1.0, 7.0]])      # column 0 is all 1s: standard deviation 0
print(((x - x.mean(0)) / x.std(0)).tolist())     # 0 / 0 = nan

print(torch.tensor([1.0, float("nan"), 3.0]).sum().item())   # one nan ruins the whole sum

nan = float("nan")
print(nan > 10, nan < 10, nan == nan)                          # all False
print(math.isfinite(nan), math.isfinite(float("inf")), math.isfinite(2.5))

@@ concept
title: fp16 tops out at 65504
--- body
Mixed-precision training does much of the math in 16-bit floating point: it uses less memory and runs faster. But the two 16-bit formats are very different:

- **float16 (fp16)**: the largest number it can hold is 65504. 256 × 256 = 65536 is already too big and becomes inf.
- **bfloat16 (bf16)**: the same range as float32 (up to about 3.4e38), so it almost never overflows. The price is low precision: only 2 to 3 significant digits.
- **float32**: up to about 3.4e38, about 7 significant digits.

Where fp16 overflows most often: squares (x²), sums of many numbers, attention scores q·k, variances and norms. They are perfectly fine in float32 and become inf as soon as they run in fp16. After that, the inf may turn into nan, or it may quietly turn into 0: 1/sqrt(inf) = 0, so the whole layer's output gets multiplied by 0, with no error.

The usual fixes:

1. Do the risky part in float32 and convert back afterwards: `xf = x.float()` … `.to(x.dtype)`. Llama's RMSNorm is written exactly like this.
2. Use bf16 instead of fp16 if your GPU supports it.
3. When training in fp16, use `torch.amp.GradScaler`. It scales the loss up before backward, so tiny gradients do not round to 0 in fp16, and it skips the update for any step whose gradients contain inf.
--- code
print("float16 max:", torch.finfo(torch.float16).max)
print("bfloat16 max:", torch.finfo(torch.bfloat16).max)

a = torch.tensor([255.0, 256.0], dtype=torch.float16)
print("fp16 squares:", (a * a).tolist())
print("bf16 squares:", (a.bfloat16() * a.bfloat16()).tolist())
print("fp32 squares:", (a.float() * a.float()).tolist())

s = torch.full((1000,), 100.0, dtype=torch.float16)
print("sum of 1000 x 100 in fp16:   ", s.sum().item())
print("convert to float32, then sum:", s.float().sum().item())

@@ concept
title: Writing numerically stable code
--- body
The same formula, written a different way, can avoid inf and nan. Remember these rules:

- **Never write `torch.log(torch.softmax(x))` yourself.** When a probability is too small for float32 it becomes 0, and log(0) = -inf. Use `F.log_softmax(x, dim=-1)`: it subtracts the maximum first, so the result is an ordinary negative number, never -inf.
- **`F.cross_entropy` takes logits** (raw scores). It does the log_softmax itself. **Do not** put a softmax in front of it.
- **The same goes for two classes**: do not take a sigmoid and then a log; use `F.binary_cross_entropy_with_logits`.
- **Guard anything that can hit 0**: `torch.log(p.clamp_min(1e-12))`, `torch.sqrt(x + 1e-12)`, `x / (std + 1e-5)`.
- **Do the overflow-prone part** (squares, sums, variances) in float32, then convert back to low precision.

In the example below the logits are [0, 200]. Class 0 has probability e^-200, which float32 cannot hold, so softmax returns 0 and the log gives -inf. log_softmax gives the exact answer, -200.
--- code
logits = torch.tensor([[0.0, 200.0]])
print("log(softmax):", torch.log(logits.softmax(-1)).tolist())
print("log_softmax :", F.log_softmax(logits, -1).tolist())

z = torch.tensor([40.0])             # the model is sure it is "positive", but the label is 0
p = torch.sigmoid(z)
print("after sigmoid:", p.item(), "  log(1 - p):", torch.log(1 - p).item())
print("loss with the with_logits version:", F.binary_cross_entropy_with_logits(z, torch.tensor([0.0])).item())

@@ concept
title: Catch the first NaN: isfinite and detect_anomaly
--- body
A nan spreads to everything computed after it, so what you want is the **first** place it appears.

1. **Check the loss at every step**: `if not torch.isfinite(loss): raise FloatingPointError(...)`. Training stops at the step where things went wrong. You can save that step's batch and study it, instead of training with nan weights for a few more hours.
2. **A nan from forward**: pass the input through the model one layer at a time and check `torch.isfinite(out).all()` after each layer. The first layer that fails is the source; the layers after it were only infected.
3. **A nan from backward**: every forward output is fine, but the gradients are nan. Wrap forward and backward in `with torch.autograd.detect_anomaly():`. Backward then raises an error as soon as it produces a nan, and the message names the backward function, for example `Function 'LogBackward0' returned nan values`. It also prints a warning that shows where that operation was called during forward: look for the line from your own code. It makes training much slower, so only turn it on while debugging.

A classic example: `torch.where(x > 0, torch.log(x), 0)`. Forward is perfectly fine: where x ≤ 0 it picks the 0. But backward computes the gradient of both branches. The backward of log is "incoming gradient ÷ x", which at x = 0 is 0 ÷ 0 = nan. The fix is to make the input to log safe first: `torch.log(torch.where(x > 0, x, 1.0))`.
--- code
loss = torch.tensor(float("nan"))
print("isfinite:", torch.isfinite(loss).item(), "  loss > 100:", (loss > 100).item())

x = torch.tensor([0.0, 2.0], requires_grad=True)
y = torch.where(x > 0, torch.log(x), torch.zeros_like(x))
print("forward looks fine:", y.tolist())
y.sum().backward()
print("gradient:", x.grad.tolist())              # element 0 is nan

x.grad = None
try:
    with torch.autograd.detect_anomaly():
        y = torch.where(x > 0, torch.log(x), torch.zeros_like(x))
        y.sum().backward()
except RuntimeError as e:
    print("detect_anomaly raised:", str(e).splitlines()[0])

@@ concept
title: Gradient norms per layer
--- body
After backward, each parameter's `.grad` holds its gradient. The **gradient norm** treats the gradient as one long vector and measures its length: `p.grad.norm()`. It tells you how hard that layer is being pushed.

Print it for every layer and many problems are obvious at a glance:

- **None**: this parameter got no gradient at all. Either it is frozen (`requires_grad=False`), or it was not used to compute the loss (for example, a layer you defined but never called in forward).
- **0**: it got a gradient, but it is all zeros. For example, every input to a ReLU is negative (a "dead" ReLU), or the loss does not actually depend on it.
- **Very large** (hundreds, thousands) or inf: exploding gradients; the next step may give nan. Lower the lr first, or clip the gradients (`torch.nn.utils.clip_grad_norm_`).
- **Early layers several orders of magnitude smaller than later layers**: vanishing gradients; the early layers barely learn.

During training, print the total gradient norm next to the loss (the return value of `clip_grad_norm_` is the total norm before clipping). Before the loss explodes, the gradient norm usually climbs first.
--- code
torch.manual_seed(0)
model = nn.Sequential(nn.Linear(8, 16), nn.ReLU(), nn.Linear(16, 4))
model[0].weight.requires_grad_(False)           # pretend someone froze the first layer's weight
x, y = torch.randn(32, 8), torch.randint(0, 4, (32,))
F.cross_entropy(model(x), y).backward()

for name, p in model.named_parameters():
    g = None if p.grad is None else round(p.grad.norm().item(), 4)
    print(f"{name:9s} requires_grad={p.requires_grad!s:5s}  grad norm = {g}")

@@ concept
title: The loss won't go down: check in this order
--- body
When the loss will not go down, do not start tuning hyperparameters yet. First make sure the code is right. Check in this order:

1. **Overfit one small batch first** (you did this on day 14): train on the same batch again and again; the loss should get close to 0. If it does not, the code has a bug, and no lr or extra data will help.
2. **Do you call zero_grad every step?** PyTorch **adds** gradients up: without clearing, this step's gradient is added on top of the last one, and every update is wrong.
3. **Are the parameters really being trained?** Look at the gradient norms per layer: None means frozen. A gradient that is there while the weights never change means the parameter is not in the optimizer (typical when the optimizer was created first and a layer of the model was replaced afterwards).
4. **Do the labels still match the inputs?** When you shuffle, x and y must use the same order. Print a few (x, y) pairs and look. With mismatched pairs, the loss gets stuck near ln C.
5. **Is there an extra softmax before cross_entropy?** It expects logits. With one extra softmax, even a model that is completely right has a floor it cannot get below: ln(1 + (C-1)/e) for C classes, about 0.744 for 4 classes and about 1.46 for 10.
6. **The learning rate**: too high explodes or bounces; too low falls very slowly. Try multiplying or dividing it by 10.
--- code
w = torch.tensor([1.0], requires_grad=True)
for step in range(3):
    loss = 3 * w.sum()                # the gradient of this loss with respect to w is always 3
    loss.backward()
    print("no zero_grad, step", step, " w.grad =", w.grad.item())

logits = torch.tensor([[100.0, 0.0, 0.0, 0.0]])   # the model is very sure, and right
y = torch.tensor([0])
print("cross_entropy(logits)          =", F.cross_entropy(logits, y).item())
print("cross_entropy(softmax(logits)) =", round(F.cross_entropy(logits.softmax(-1), y).item(), 4))

--- context
The first loss tells you whether the initialization and the loss are right. An experienced engineer looks at the first line of a training log and compares it with ln C, worked out in their head.
--- prompt
What does this code print? (three lines) Logits that are all 0 mean every class gets the same score.
--- code
logits = torch.zeros(4, 10)             # 4 samples, 10 classes, every score the same
y = torch.tensor([3, 0, 7, 1])
print(round(F.cross_entropy(logits, y).item(), 1))

logits = torch.zeros(2, 50257)          # GPT-2's vocabulary size
y = torch.tensor([11, 42])
print(round(F.cross_entropy(logits, y).item(), 1))

logits = torch.zeros(1, 10)
logits[0, 0] = 20.0                     # very sure it is class 0...
y = torch.tensor([3])                   # ...but the right answer is class 3
print(round(F.cross_entropy(logits, y).item(), 1))
--- explain
Equal scores → every class has probability 1/C → loss = ln C. ln 10 ≈ 2.3 and ln 50257 ≈ 10.8. So when you train a model with a GPT-2-sized vocabulary from scratch, the first loss should be near 10.8. If you see 50, something is wrong with the initialization.

Third line: the correct class scores 0 and class 0 scores 20, so the loss = ln(e^20 + 9) ≈ 20.0. Being confidently wrong costs about as much as the confidence. That is why an initialization that is too large makes the first loss much bigger than ln C.
--- hints
- After softmax, what probability does each class get when all the logits are 0?
- loss = -ln(1/C) = ln C. ln 50257 = ln 5.0257 + 4 × ln 10 ≈ 1.6 + 9.2. Third line: loss = ln(e^20 + 9), and e^20 is far bigger than 9.

def curve_verdict(losses):
    if not all(math.isfinite(v) for v in losses):     # nan and ±inf are not finite
        return "nan"
    if losses[-1] > 2 * losses[0]:
        return "exploding"
    if abs(losses[-1] - losses[0]) < 0.01 * losses[0]:
        return "flat"
    return "ok"

When nan shows up in a training log, you need to know which operations can produce it. These lines cover the most common sources in real projects: log(0), the 0·log 0 in an entropy, exp overflow, 0/0 and fp16 overflow.
--- prompt
What does this code print? (five lines)
--- code
x = torch.tensor([0.0, 1.0])
print(torch.log(x).tolist())

print(torch.exp(torch.tensor(100.0)).item())

--- explain

- exp(100) is larger than float32's maximum (about 3.4e38; exp(88.7) already reaches it), so it is inf.
- 0 / 0 = nan.
- 300 × 300 = 90000 > 65504, so in fp16 it overflows to inf; converted to float32 first, it is a normal 90000.0.
--- hints
- The first two lines print Python lists via `.tolist()`, like `[1.5, 0.0]`. Python writes infinity as `inf` or `-inf` and nan as `nan`.
- What is 0 × (-inf)? Is exp(100) above float32's limit? fp16's limit is 65504.

def train_classifier(model, x, y, steps=100, lr=0.5):
    opt = torch.optim.SGD(model.parameters(), lr=lr)
    losses = []
    for step in range(steps):
        loss = F.cross_entropy(model(x), y)
        if not torch.isfinite(loss):
            raise FloatingPointError(f"step {step}: loss = {loss.item()}")
        opt.zero_grad()
        loss.backward()
        opt.step()
        losses.append(loss.item())
    return losses

def grad_norms(model):
    out = {}
    for name, p in model.named_parameters():
        out[name] = None if p.grad is None else p.grad.norm().item()
    return out
