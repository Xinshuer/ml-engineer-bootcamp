@@ concept
title: Two phases: prefill and decode
ref: day23
--- body
An LLM writes its answer in two phases:

1. **Prefill**: the whole prompt goes into the model at once, and one forward pass computes every position. On the way, the k and v of every layer are stored in the KV cache (day 5: the k/v of old tokens are kept, so they are never computed again). The logits at the last position give the first new token.
2. **Decode**: each step feeds only the **one** token generated in the previous step, together with the KV cache, and gets the next token. For 100 new tokens you need 1 prefill (which gives the first one) plus 99 decode steps.

The two phases hit different limits:

- Prefill handles hundreds or thousands of tokens in one go. The matrix multiplications are big, so the limit is the GPU's compute (compute-bound).
- Decode computes just 1 token per step, but it still has to read all the weights and the KV cache from GPU memory. Little compute, lots of reading: the limit is memory bandwidth (memory-bound). That is why it pays to decode many requests in the same step: the weights are read once and shared by all of them.

Users feel two latencies:

- **TTFT** (time to first token): mostly the prefill time. The longer the prompt, the slower.
- **TPOT** (time per output token): the time of one decode step. It decides how fast the text "types itself out".

Total time ≈ TTFT + (number of output tokens - 1) × TPOT.

Today's tiny model `TinyLM` (random weights, a vocabulary of 32 tokens) is called as `logits, cache = model(ids, cache)`. Passing `cache=None` means prefill; passing back the cache from the previous call means decode. `model.calls` records how many tokens each call processed.
--- code
model = make_tiny_lm()
prompt = torch.tensor([[12, 15, 21, 0, 3, 27]])          # a prompt of 6 tokens
with torch.inference_mode():
    logits, cache = model(prompt)                        # prefill: all 6 tokens in one call
    tok = logits[0, -1].argmax().item()                  # last position -> first new token
    out = [tok]
    for _ in range(4):                                   # decode: feed only the 1 new token each step
        logits, cache = model(torch.tensor([[tok]]), cache)
        tok = logits[0, -1].argmax().item()
        out.append(tok)
print("tokens processed per call:", model.calls)
print("the 5 generated tokens:", out)
print("shape of k in layer 0's cache:", tuple(cache[0][0].shape), "= (B, KV heads, tokens so far, head_dim)")
n = sum(p.numel() for p in model.parameters())
print(f"every call reads all {n} parameters: prefill shares that among 6 tokens, decode spends it on 1 token")

@@ concept
title: The KV cache memory bill
ref: day23
--- body
The KV cache stores one k vector and one v vector for every layer, every KV head and every token so far. So its size is just a product of a few numbers:

```
bytes = 2 × layers × KV heads × head_dim × sequence length × batch × bytes per number
```

- The 2 at the front: one copy for K and one for V.
- KV heads: in a model with GQA (day 5: several q heads share one set of k/v), use the number of KV heads, not the number of q heads.
- Bytes per number: 4 for fp32, 2 for fp16 / bf16, 1 for fp8 / int8. In PyTorch, `torch.float16.itemsize` gives you the 2 directly.

Two real models (fp16, 2 bytes per number; 1 KiB = 1024 bytes, 1 GiB = 1024³ bytes):

- Llama-2-7B: 32 layers, 32 KV heads, head_dim 128. One token takes 2 × 32 × 32 × 128 × 2 = 524,288 bytes = 512 KiB. One sequence of 4096 tokens is 2 GiB; serving 8 of them at once is 16 GiB.
- Llama-3-8B: also 32 layers and head_dim 128, but only 8 KV heads (GQA). One token takes 128 KiB, a quarter of the above.

This is why the KV cache often runs out of memory before the weights do: the weights have a fixed size, while the KV cache grows with "requests served at once × their length". How many sequences one GPU can serve at the same time is roughly "memory left after the weights ÷ KV cache per sequence".
--- code
def per_token_bytes(layers, kv_heads, head_dim, bytes_per_number):
    return 2 * layers * kv_heads * head_dim * bytes_per_number

llama2 = per_token_bytes(32, 32, 128, torch.float16.itemsize)
llama3 = per_token_bytes(32, 8, 128, torch.float16.itemsize)
print("Llama-2-7B:", llama2 // 1024, "KiB / token; 4096 tokens:", llama2 * 4096 / 1024**3, "GiB")
print("Llama-3-8B:", llama3 // 1024, "KiB / token; 4096 tokens:", llama3 * 4096 / 1024**3, "GiB")

model = make_tiny_lm()                                   # 2 layers, 2 KV heads, head_dim 8, fp32
with torch.inference_mode():
    _, cache = model(torch.randint(0, 32, (3, 5)))       # batch 3, 5 tokens each
real = sum(k.numel() * k.element_size() + v.numel() * v.element_size() for k, v in cache)
print("TinyLM's cache really holds:", real, "bytes; formula:", 2 * 2 * 2 * 8 * 5 * 3 * torch.float32.itemsize, "bytes")

title: Streaming: a generator that yields one token at a time
--- body
In a chat window the text appears word by word: the service sends each token to the user as soon as it is generated, instead of waiting for the whole answer. The user waits only the TTFT for the first word, not the time of the full answer.

In Python you write this kind of "hand over as you go" function as a **generator**: if a function body contains `yield`, calling it does not run it. You get a generator object instead.

- Each `next(gen)` (or each round of a `for` loop) resumes the function where it stopped. It runs to the next `yield`, hands over that value, and pauses again.
- When the function `return`s (or reaches its end), the loop is over.
- Nothing is computed until the caller asks for it. If the user disconnects and nobody asks any more, generation stops and no GPU time is wasted.

FastAPI's `StreamingResponse` takes such a generator directly and sends each yielded piece to the browser (the service itself is day 22's topic).

A generation loop always needs two stop conditions:

1. **eos** (end of sequence): when the model generates this token, it means "I am done". The eos token itself is not sent to the user.
2. **max_new_tokens**: the most new tokens to generate. It is a hard limit: even if the model never produces eos, one request must not hold the GPU forever.

OpenAI-style APIs tell you which one ended the answer: `finish_reason` is `"stop"` (eos or a stop string) or `"length"` (max_new_tokens reached).

One more detail: to turn off gradients in a generator, put `@torch.inference_mode()` above the function definition as a decorator. Do not write `with torch.inference_mode():` inside the body and yield from inside it: while the generator is paused, that mode "leaks" into the caller's code. The code below tries both.
--- code
def count_up(n):
    print("  (the body starts running)")
    for i in range(n):
        print(f"  computed {i}")
        yield i
    print("  (the body is finished)")

gen = count_up(3)
print("after the call the body has not run yet; we got a:", type(gen).__name__)
print("take the first one:", next(gen))
for x in gen:                                            # carries on where it stopped
    print("for got:", x)

@torch.inference_mode()
def good():
    yield torch.is_grad_enabled()

def leaky():
    with torch.inference_mode():
        yield torch.is_grad_enabled()

for name, make in [("decorator", good), ("with inside the body", leaky)]:
    g = make()
    inside = next(g)
    print(f"{name}: gradients inside the generator? {inside}; in the caller while it is paused? {torch.is_grad_enabled()}")
    g.close()                                            # close the generator; only now does the with block exit

@@ concept
title: Stop strings span tokens
--- body
The third stop condition is a **stop string**: "stop when you reach `\nUser:`", for example (in a chat template this starts the user's next turn; without the stop, the model would start speaking for the user).

The hard part: the model produces tokens, not characters. A stop string is often split over several tokens, such as `"\n"`, `"User"` and `":"`. So checking "is this one token the stop string?" will never catch it.

The right way: join the text generated so far and search for the stop in the **joined text**. When you find it, keep only the part before it; the stop itself is dropped. With several stop strings, cut at whichever appears first in the text.

Streaming adds one more problem: text that was sent cannot be taken back. Say you already sent `"Bye.\n"`, and then `"User"` and `":"` arrive. Only now do you see that the `\n` was the start of the stop, but it is already on the user's screen.

The fix is to **hold back a little**: each time you join the text, check whether its end could be the start of some stop string. If so, hold that part back and send everything before it. When the next piece of text arrives, look again:

- It completes a stop string: drop what you held back and finish.
- It can no longer become a stop string (say `"\n"` is followed by `"Thanks"`): send the held-back text together with the new text.
- The stream ends while you still hold something: it was not a stop, so send it.

You hold back at most "length of the stop - 1" characters, so users hardly notice. In the code below, `held(text, stop)` computes "how many characters at the end to hold back".
--- code
pieces = ["Sure", "!", " Bye", ".\n", "User", ":", " next"]
stop = "\nUser:"
print("is any single piece equal to the stop:", any(p == stop for p in pieces))

def held(text, stop):
    """how many characters at the end of text could be the start of stop (the longest such end)"""
    for k in range(min(len(stop) - 1, len(text)), 0, -1):
        if text.endswith(stop[:k]):
            return k
    return 0

text = ""
for p in pieces:
    text += p
    if stop in text:
        print(f"after adding {p!r} the stop is found; the result is {text[:text.find(stop)]!r}")
        break
    print(f"after adding {p!r:8} hold back {held(text, stop)} characters at the end")

@@ concept
title: Sampling parameters: validate before the GPU
--- body
What temperature, top-k and top-p do was day 5. A service has one more job: **check the parameters in each request before it reaches the GPU**. Bad parameters rarely crash the service. More often they quietly produce strange output, or keep a request on the GPU far too long:

- `temperature = 0` used directly to divide the logits gives inf and nan. Treat 0 as a special case, "greedy" (just take the argmax). Negative values and very large values make no sense either; a common valid range is 0 to 2.
- `top_p` must be in (0, 1]. `top_p = 0` filters out every token.
- `top_k` is a non-negative integer; 0 means "no top-k".
- `max_new_tokens` is a positive integer, and "prompt length + max_new_tokens" must fit in the model's context length. Otherwise generation fails or gets cut off halfway.

Two Python traps:

1. **NaN**: Python's `json.loads` happily reads `NaN` and `Infinity`. Every comparison with NaN is False, so `if t < 0 or t > 2` lets it through. Rule out NaN and inf first with `math.isfinite(t)` (or write the "valid" condition, `if not (0 <= t <= 2)`: NaN makes the whole condition False, so it is rejected too).
2. **bool is an int**: `isinstance(True, int)` is True, so a JSON `true` counts as 1. Write `isinstance(x, int) and not isinstance(x, bool)`.

One more: a misspelled parameter name (`"temprature": 0.2`) that is silently ignored makes the user think they set the temperature, while the default was used. Unknown names must be errors.

When validation fails, report all the errors at once (HTTP 400 or 422), not just the first. Otherwise the user fixes one, hits the next, and so on.
--- code
import json
t = json.loads('{"temperature": NaN}')["temperature"]
print("json.loads read:", t)
print("nan < 0:", t < 0, "  nan > 2:", t > 2, "  -> t < 0 or t > 2 lets it through")
print("math.isfinite(nan):", math.isfinite(t))
print("isinstance(True, int):", isinstance(True, int))
logits = torch.tensor([2.0, 1.0, 0.5])
print("temperature=0, divide and softmax:", (logits / 0.0).softmax(-1).tolist())
print("temperature=0 treated as greedy:", logits.argmax().item())

@@ concept
title: Continuous batching: leave as soon as you are done
ref: day23
--- body
A GPU can only decode a limited number of sequences at the same time (KV cache memory is limited). Call these places **slots**. With many requests waiting, how do you schedule them?

**Static batching**: collect a batch (say 4 requests) and generate them together. The batch returns when its longest request is done, and only then does the next batch start. The problems:

- A batch takes as long as its longest request. A short request that needs 3 tokens waits for a long one that needs 500.
- When a short one finishes, its slot sits idle while other requests are still waiting in the queue.

**Continuous batching** (also called iteration-level scheduling; inference engines such as vLLM and TGI use it) schedules at every decode step:

1. At the start of each step, if a slot is free and someone is waiting, the request at the front of the queue joins.
2. During the step, every request in a slot generates 1 token.
3. A request that has all its tokens leaves right away and returns its result; its slot is free for someone else from the next step on.

The result: short requests come back quickly, slots are almost never idle, and the total number of steps goes down.

Today's simulation makes two simplifications. Time is counted in decode steps, and each step costs 1 unit no matter how many requests are in the slots (decode is limited by memory bandwidth, so this is a fair approximation). The prefill of a joining request costs nothing.

Below, `continuous_timeline` prints who is in the slots at each step; `simulate_continuous` and `simulate_static` return the step at which each request finishes.
--- code
lengths = [4, 1, 1, 3]                                   # how many tokens each request needs
for step, running, waiting, finished in continuous_timeline(lengths, n_slots=2):
    print(f"step {step}: in slots {running}  waiting {waiting}  finished {finished}")
print("continuous: step at which each request returns:", simulate_continuous(lengths, 2))
print("static batching: step at which each request returns:", simulate_static(lengths, 2))

title: Diffusion: steps are latency
ref: day23
--- body
A diffusion model (days 8 and 9) calls its denoising network many times to make one image: once per sampling step. So the latency is roughly:

```
total time ≈ fixed overhead + steps × time per step × (another × 2 with CFG)
```

- **Fixed overhead**: the part that does not depend on the steps, such as the text encoder reading the prompt and the VAE decoding the latent into an image.
- **Time per step**: one forward pass of the denoising network. Higher resolution and bigger batches make it slower.
- **CFG** (classifier-free guidance, day 9): every step computes the "conditional" and the "unconditional" prediction (twice, or once as a batch of 2). Estimate it as roughly 2×.

When the service has a latency budget ("return an image within 2 seconds"), work backwards: subtract the fixed overhead from the budget and divide by the time per step. That is the most steps you can afford. Fewer steps lower the image quality, so pair this with a sampler that does well in few steps (such as DDIM from day 9). If not even 1 step fits, the only options are a smaller resolution, a smaller model, or rejecting the request.

The code below really measures time. Each step of the tiny network is fast and the numbers change a little from run to run, but you can see that twice the steps take about twice the time. The CFG column may add far less than 2×: the network is so small that the fixed cost of each call dominates, and going from batch 1 to batch 2 adds little. With a big model at high resolution it gets close to 2×.
--- code
import time
torch.manual_seed(0)
net = TinyDenoiser().eval()
x = torch.randn(1, 4, 32, 32)

def sample_ms(steps, cfg):
    t0 = time.perf_counter()
    with torch.inference_mode():
        z = x
        for _ in range(steps):
            if cfg:                                      # conditional + unconditional as a batch of 2 (this tiny net has no condition input; timing only)
                e = net(torch.cat([z, z]))
                eps = e[1:] + 3.0 * (e[:1] - e[1:])
            else:
                eps = net(z)
            z = z - 0.1 * eps
    return (time.perf_counter() - t0) * 1000

sample_ms(5, False)                                      # warm up once: the first call is always slower
for steps in (10, 20, 40):
    print(f"{steps:2d} steps: {sample_ms(steps, False):6.1f} ms    with CFG: {sample_ms(steps, True):6.1f} ms")

title: A Dockerfile for a GPU inference image
--- body
Docker packs "code + dependencies + system libraries" into an **image** that runs exactly the same on any machine with Docker. A running image is a **container**. An image is described by a text file called `Dockerfile`, one instruction per line:

- `FROM`: the existing image to start from, such as an official image with PyTorch and CUDA installed.
- `WORKDIR`: the folder the following commands run in.
- `COPY`: copies files from your machine into the image. `RUN`: runs a command at build time, such as `pip install`.
- `ENV`: sets an environment variable. `USER`: the user that runs everything after it.
- `EXPOSE`: documents the port the service uses. `CMD`: the command the container runs when it starts.

Four rules for a GPU inference image:

1. **Pin versions.** `FROM pytorch/pytorch:latest` may be one image today and a different one next month. A new CUDA version may not match the GPU driver on the machine; a new PyTorch may change the numbers. Use an exact tag such as `pytorch/pytorch:2.7.0-cuda12.8-cudnn9-runtime`, and write `==version` for every package in `requirements.txt`.
2. **Keep model files out of the image.** Copying gigabytes of weights into the image makes it big and slow, and every model change means a new build and a new push. The code goes into the image; the weights are mounted when the container runs, with `docker run -v host_folder:/models:ro`. `:ro` means read-only: the service cannot change or delete the model files.
3. **Do not run as root.** Inside a container you are root by default. If the service is ever broken into, root can do far more damage. Create a normal user (`RUN useradd ...`) and switch to it with `USER`.
4. **One worker per GPU.** `uvicorn --workers 4` starts 4 processes. Each loads its own full copy of the model and keeps its own KV cache memory, and all 4 fight over the same GPU. Instead: one process per container (`--workers 1`), given exactly one GPU with `docker run --gpus device=0`. Concurrency comes from batching inside the process (for example today's continuous batching). For two GPUs, start two containers.

The code below checks a "what not to do" Dockerfile and points out the lines that break the rules.
--- code
dockerfile = """FROM pytorch/pytorch:latest
WORKDIR /app
COPY requirements.txt server.py ./
COPY weights/ /app/weights/
RUN pip install -r requirements.txt
CMD ["uvicorn", "server:app", "--host", "0.0.0.0", "--workers", "4"]"""

lines = dockerfile.splitlines()
for line in lines:
    if line.startswith("FROM") and (":" not in line or line.endswith(":latest")):
        print("version not pinned      ->", line)
    if line.startswith("COPY") and "weights" in line:
        print("weights inside image    ->", line)
    if '"--workers", "4"' in line:
        print("4 processes on one GPU  ->", line)
print("is there a USER line:", any(l.startswith("USER") for l in lines), "-> without one, the container runs as root")

def kv_cache_bytes(n_layers, n_kv_heads, head_dim, seq_len, batch, dtype):
    bytes_per_number = dtype.itemsize                    # fp16 / bf16 -> 2, fp32 -> 4

--- context
Before you speed up an LLM service, you need to know which phase is slow. Prefill and decode hit different limits, so they need different fixes.
--- prompt
Which statements about prefill and decode are **true**? (Pick all that apply.)
--- options
- Prefill handles the whole prompt at once; the matrix multiplications are big, so the limit is usually the GPU's compute
- Decode computes only 1 token per step but has to read all the weights and the KV cache, so the limit is usually memory bandwidth
- The time a user waits for the first word (TTFT) is mostly set by max_new_tokens
- Decoding many requests together in the same step pays off: the weights are read once and shared by all of them
- With a KV cache, the time of one decode step does not depend at all on how long the sequence already is

Every LLM inference service is built around this loop: prefill once, then decode one token at a time, hand each token to the user right away, and stop at eos or at the limit. Get it right and you see how TTFT, the KV cache and streaming fit together.
--- prompt
Write the **generator** `stream_tokens(model, prompt_ids, max_new_tokens, eos_id)`. It decodes greedily (each step takes the token with the largest logit) and yields the new tokens one by one.

- `prompt_ids`: a (1, T) long tensor. `model` works like `TinyLM`: `logits, cache = model(ids, cache)`, where logits has shape (1, tokens fed in this call, V).
- First call: feed the whole prompt with `cache=None` (prefill). After that, feed only the 1 token generated in the previous step (shape (1, 1)) together with the cache (decode).
- The next token comes from `logits[0, -1]` (the last position). Yield a Python int (use `.item()`), because it will be turned into JSON for the user.
- Stop when `eos_id` is generated; do not yield the eos itself. Yield at most `max_new_tokens` tokens.
- No wasted forward passes: after the last token is yielded, do not call the model again. With `max_new_tokens=0`, do not call it at all.

@torch.inference_mode()                                  # decorator form: does not affect the caller while paused
def stream_tokens(model, prompt_ids, max_new_tokens, eos_id):
    ids, cache = prompt_ids, None
    for _ in range(max_new_tokens):
        logits, cache = model(ids, cache)                # first call: prefill the prompt; then: decode 1 token
        tok = logits[0, -1].argmax().item()              # greedy: take the largest; .item() gives a Python int
        if tok == eos_id:
            return                                       # eos is not sent to the user
        yield tok
        ids = torch.tensor([[tok]], device=prompt_ids.device)   # the next step feeds only this 1 new token

def stream_until_stop(pieces, stops):
    buf = ""                                             # text not sent yet
    for piece in pieces:
        buf += piece
        hits = [buf.find(s) for s in stops if s in buf]
        if hits:                                         # a complete stop: send what comes before it, then finish
            if buf[:min(hits)]:
                yield buf[:min(hits)]
            return
        keep = 0                                         # the longest end that could start some stop string
        for s in stops:
            for k in range(min(len(s) - 1, len(buf)), 0, -1):
                if buf.endswith(s[:k]):
                    keep = max(keep, k)
                    break
        if len(buf) > keep:                              # everything before it is safe: send it
            yield buf[:len(buf) - keep]
            buf = buf[len(buf) - keep:]
    if buf:
        yield buf                                        # the stream ended: what we held was not a stop, send it

def simulate_continuous(lengths, n_slots):
    queue = list(range(len(lengths)))                    # waiting requests (in order)
    slots = []                                           # requests being generated
    made = [0] * len(lengths)                            # tokens generated so far per request
    finish = [0] * len(lengths)
    step = 0
    while queue or slots:
        step += 1
        while queue and len(slots) < n_slots:            # 1. fill the free slots
            slots.append(queue.pop(0))
        for i in slots:                                  # 2. every request generates 1 token
            made[i] += 1
        done = [i for i in slots if made[i] == lengths[i]]
        for i in done:                                   # 3. finished requests leave at this step
            finish[i] = step
        slots = [i for i in slots if i not in done]
    return finish

def pick_steps(budget_ms, step_ms, overhead_ms, cfg, max_steps=50):
    per_step = step_ms * (2 if cfg else 1)                     # CFG: two passes per step
    steps = math.floor((budget_ms - overhead_ms) / per_step)   # how many steps fit in the rest (round down)
    return int(max(0, min(max_steps, steps)))                  # at most max_steps, never negative

--- context
Prefill + decode + streaming + stop conditions is the skeleton of every LLM inference service. Write it without the answer, and you can read the generation loop of any inference engine, and write one on the spot in an interview.
--- prompt
Write the generator `stream_tokens(model, prompt_ids, max_new_tokens, eos_id)`: greedy decoding that yields the new tokens (Python ints) one at a time.

- `prompt_ids`: (1, T) long. The model is called as `logits, cache = model(ids, cache)`.
- The first call feeds the whole prompt (cache is `None`); after that, each call feeds only the previous new token (shape (1, 1)) together with the cache.
- Stop when `eos_id` is generated, without yielding it; yield at most `max_new_tokens` tokens; do not call the model after the last token (with `max_new_tokens=0`, do not call it at all).

--- solution
@torch.inference_mode()                                  # decorator form: does not affect the caller while paused
def stream_tokens(model, prompt_ids, max_new_tokens, eos_id):
    ids, cache = prompt_ids, None
    for _ in range(max_new_tokens):
        logits, cache = model(ids, cache)                # first call: prefill the prompt; then: decode 1 token
        tok = logits[0, -1].argmax().item()              # greedy: take the largest; .item() gives a Python int
        if tok == eos_id:
            return                                       # eos is not sent to the user
        yield tok
        ids = torch.tensor([[tok]], device=prompt_ids.device)   # the next step feeds only this 1 new token
