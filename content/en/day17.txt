@@ concept
title: train() and eval(): Dropout and BatchNorm change behaviour
--- body
Two common layers behave differently in training and in inference. `model.train()` and `model.eval()` switch between the two behaviours, and they apply to every submodule automatically.

- **Dropout**: in train mode, each value is set to 0 with probability p, and the survivors are multiplied by 1/(1-p) so the average stays the same. In eval mode it does nothing.
- **BatchNorm**: in train mode, it normalises with the mean and variance of *this batch*, and it also updates `running_mean` / `running_var` (statistics accumulated over training). In eval mode it uses those stored statistics instead.

So if you forget `model.eval()` before predicting, nothing raises an error, but:

1. Predicting the same input twice gives two different results (Dropout is dropping at random).
2. One sample's prediction changes with the other samples in the batch (BatchNorm uses batch statistics).
3. Every prediction changes BatchNorm's running statistics. `torch.no_grad()` does not stop this: it controls gradients, not the mode.

Remember: **`no_grad` and `eval()` are two different things, and inference needs both.** The other way round: after an evaluation inside the training loop, switch back with `model.train()`, or the rest of training runs without Dropout.
--- code
torch.manual_seed(0)
model = nn.Sequential(nn.Linear(4, 8), nn.BatchNorm1d(8), nn.Dropout(0.5), nn.Linear(8, 2))
x = torch.randn(6, 4)
with torch.no_grad():
    model.train()
    print("train mode, same result twice:", torch.equal(model(x), model(x)))
    print("running_mean was quietly changed:", model[1].running_mean[:3])
    model.eval()
    print("eval mode, same result twice:", torch.equal(model(x), model(x)))
    print("eval mode, first 2 samples alone == inside the batch:", torch.allclose(model(x[:2]), model(x)[:2]))

@@ concept
title: Data leakage: statistics come from the training set only
--- body
Data leakage: information from the test set sneaks into training. Your evaluation scores then look better than the model will do in production, and you do not know it.

The most common kind: you compute the mean and standard deviation for normalisation on *all* the data, and only then split it into a training set and a test set. The test values have now helped transform the training data.

The correct order:

1. Split first: training set and test set apart.
2. Compute `mean` and `std` on the training set only (this is called "fitting" the statistics).
3. Use that same `mean` / `std` to transform the training set, the test set, and every request in production.

A simple check (this is an invariant test): **change only the test set, and the transformed training data must stay exactly the same.** If it changes, you have a leak.

The same rule holds for a tokenizer's vocabulary, feature selection and the values used to fill in missing data: they may only "learn" from the training set.

In the example below the test distribution has shifted. The leaky version hides half of that shift: in evaluation the test data looks only 1.74 standard deviations away, but in production the model faces 3.39.
--- code
torch.manual_seed(0)
train = torch.randn(100, 1) + 5.0      # training set: mean about 5
test = torch.randn(20, 1) + 8.0        # test set: shifted, mean about 8
both = torch.cat([train, test])
print(f"mean over all the data:      {both.mean().item():.2f}")
print(f"mean over the training set:  {train.mean().item():.2f}")
leaky = ((test - both.mean()) / both.std()).mean().item()
clean = ((test - train.mean()) / train.std()).mean().item()
print(f"normalised test mean, leaky:   {leaky:.2f}")
print(f"normalised test mean, correct: {clean:.2f}  <- this is what the model sees in production")

@@ concept
title: Next-token labels are shifted by one
--- body
A language model's task: see the tokens at positions 0..t and guess the token at position t+1. So the inputs and the labels are **shifted by one**:

- `inputs = tokens[:, :-1]` (drop the last token)
- `targets = tokens[:, 1:]` (drop the first token)

The model's output at position t, `logits[:, t]`, is compared with `targets[:, t]`, which is token t+1 of the original sequence.

What happens if you forget the shift? The label is the current token, which the model can already see. It only has to learn to copy, and the loss drops almost to 0. The training curve looks great; the generated text is garbage. **A loss that is too good to be true is itself a bug signal.**

The other mistake is shifting the wrong way (`inputs = tokens[:, 1:]`, `targets = tokens[:, :-1]`): the model then guesses the past from the future.

Before `F.cross_entropy`, flatten the (B, T, V) logits to (B·T, V) and the labels to (B·T,). A sliced tensor may not be contiguous in memory, so use `.reshape`, not `.view` (day 16).
--- code
tokens = torch.tensor([[5, 6, 7, 8, 9]])
inputs, targets = tokens[:, :-1], tokens[:, 1:]
print("inputs :", inputs.tolist())
print("targets:", targets.tolist())
for t in range(inputs.shape[1]):
    print(f"sees {inputs[0, :t + 1].tolist()} -> must guess {targets[0, t].item()}")

@@ concept
title: Padding must not count in the mean
--- body
Sentences in a batch have different lengths. The short ones get padding (fake filler tokens) at the end so that they fit into one (B, T) tensor. A mask goes with it: 1 marks a real token, 0 marks padding.

Padding is not data. The loss, mean pooling and accuracy must be computed over real tokens only. The correct way:

```
masked_mean = (x * mask).sum() / mask.sum()
```

The common mistake: set the padding to 0 with `x * mask`, then call `.mean()`. The numerator is right, but the denominator counts *all* positions. The result: the more padding, the smaller the loss looks. Change the batch size or bucket the data by length, and the loss changes for no visible reason.

With `F.cross_entropy` there is another way: set the target at padding positions to -100. Its default argument `ignore_index=-100` skips those positions, and the denominator counts only real tokens.

The check (another invariant): **add a few more columns of padding, and the loss must not change at all.**
--- code
loss = torch.tensor([[2.0, 1.0, 3.0, 0.0, 0.0],
                     [4.0, 0.0, 0.0, 0.0, 0.0]])   # loss per position (already 0 at the padding)
mask = torch.tensor([[1., 1., 1., 0., 0.],
                     [1., 0., 0., 0., 0.]])
print("wrong   (loss*mask).mean()          =", (loss * mask).mean().item())
print("correct (loss*mask).sum()/mask.sum() =", ((loss * mask).sum() / mask.sum()).item())
wide_loss = torch.cat([loss, torch.zeros(2, 5)], 1)     # 5 more columns of padding
wide_mask = torch.cat([mask, torch.zeros(2, 5)], 1)
print("with 5 more columns, wrong   =", (wide_loss * wide_mask).mean().item())
print("with 5 more columns, correct =", ((wide_loss * wide_mask).sum() / wide_mask.sum()).item())

@@ concept
title: Gradient accumulation: weight each part by its size
--- body
When a big batch does not fit in memory, you can cut it into several small batches (micro-batches). You call `backward()` on each one; the gradients are **added up automatically** in `.grad`; then you call `step()` once. This is gradient accumulation.

The trap is the adding up. Each micro-batch loss is already an average over that micro-batch, so K gradients added together are **K times** the big-batch gradient.

- Micro-batches of equal size: divide each loss by K.
- Micro-batches of different sizes (the last one is often smaller): multiply each loss by `len(xb) / N`, where N is the total number of samples. Dividing by K gives the samples in the small batch too much weight.

Why can this bug hide for so long? With Adam you barely notice: Adam rescales by the size of the gradient, so gradients that are K times larger give almost the same update. But with SGD the steps are K times too big, a gradient clipping threshold no longer means what you think, and the logged loss is K times too big.

The check (compare with a reference): **the accumulated gradient == the gradient computed on the big batch directly.**
--- code
torch.manual_seed(0)
x, y = torch.randn(8, 3), torch.randn(8, 1)
m = nn.Linear(3, 1)
F.mse_loss(m(x), y).backward()
full = m.weight.grad.clone()                  # big-batch gradient (the reference)
m.zero_grad()
for xb, yb in zip(x.split(2), y.split(2)):    # 4 micro-batches of 2
    F.mse_loss(m(xb), yb).backward()          # no weighting
print("no weighting: the gradient is", (m.weight.grad / full).round(decimals=3).tolist(), "times the big-batch gradient")
m.zero_grad()
for xb, yb in zip(x.split(2), y.split(2)):
    (F.mse_loss(m(xb), yb) * len(xb) / len(x)).backward()
print("weighted by size, same as the big batch:", torch.allclose(m.weight.grad, full))

@@ concept
title: No weight decay on 1-D parameters
--- body
Weight decay pulls every parameter a little towards 0 at every step (in AdamW roughly `p = p - lr * wd * p`). It stops the weight matrices from growing too large.

Two kinds of parameters should not be pulled towards 0:

- **Biases**: they only shift values; pulling them to 0 does not regularise anything.
- **The weight (scale) of LayerNorm / RMSNorm**: it starts at 1. Pulling it towards 0 shrinks the layer's whole output, more and more.

What they have in common: they are 1-D (`p.ndim == 1`). Weight matrices and embeddings are 2-D. So the standard approach splits the parameters into two groups by number of dimensions and hands them to the optimizer as param groups (each group can have its own hyperparameters):

```
decay    = [p for p in model.parameters() if p.ndim >= 2]
no_decay = [p for p in model.parameters() if p.ndim < 2]
opt = torch.optim.AdamW([{"params": decay, "weight_decay": 0.1},
                         {"params": no_decay, "weight_decay": 0.0}], lr=3e-4)
```

Filtering by name (`"bias" in name`) is common, but it misses LayerNorm's weight: its name is something like `norm.weight`, with no "bias" in it.
--- code
torch.manual_seed(0)
net = nn.Sequential(nn.Linear(4, 4), nn.LayerNorm(4))
for name, p in net.named_parameters():
    print(f"{name:9s} ndim={p.ndim}  ->", "decay" if p.ndim >= 2 else "no decay")
opt = torch.optim.AdamW(net.parameters(), lr=0.1, weight_decay=0.1)   # the bad example: decay everything
for _ in range(10):
    for p in net.parameters():
        p.grad = torch.zeros_like(p)          # zero gradient: only weight decay acts
    opt.step()
print("LayerNorm weight after 10 steps:", net[1].weight.data)

@@ concept
title: Step the LR scheduler every step
--- body
A learning-rate scheduler sets the current learning rate from how many times `scheduler.step()` has been called. Warmup (raising the learning rate slowly from a tiny value over the first few hundred steps) and cosine decay, the usual schedules for training Transformers, are designed in **optimizer steps**. (A schedule written in epochs, such as "divide the lr by 10 every 30 epochs", is stepped once per epoch: call `scheduler.step()` in the unit the schedule was designed in.)

So for a schedule in steps, the call belongs in the inner loop, right after `optimizer.step()`:

```
for x, y in loader:
    loss = ...
    optimizer.zero_grad()
    loss.backward()
    optimizer.step()
    scheduler.step()      # once per step
```

Two common mistakes, neither of which raises an error:

- In the epoch loop: the schedule moves one step per epoch. A warmup meant to end after 1,000 steps now takes 1,000 epochs; the learning rate stays tiny and the loss falls absurdly slowly.
- Before `optimizer.step()`: the whole schedule runs one step early and the first learning rate is skipped. PyTorch only prints a warning.

The check: record the learning rate actually used at every step (`optimizer.param_groups[0]["lr"]`) and compare it, entry by entry, with the schedule you designed.
--- code
def used_lrs(per_step):
    m = nn.Linear(2, 1)
    opt = torch.optim.SGD(m.parameters(), lr=0.1)
    sched = torch.optim.lr_scheduler.LambdaLR(opt, lambda s: min(1.0, (s + 1) / 4))  # 4 warmup steps
    used = []
    for epoch in range(2):
        for step in range(3):
            used.append(round(opt.param_groups[0]["lr"], 4))
            opt.step()
            if per_step:
                sched.step()
        if not per_step:
            sched.step()
    return used

print("step every step: ", used_lrs(True))
print("step every epoch:", used_lrs(False))

@@ concept
title: Invariant tests: make silent bugs visible
ref: day17
--- body
Bugs that raise no error are the most expensive: the code runs, the loss goes down, and the results are quietly worse. You may train for days before you notice.

The remedy is **invariant tests**: find a property that must hold whatever the input is, and check it with random inputs. Today uses these:

- **Causality**: change the inputs after position t, and the outputs at positions 0..t must not change. Catches a wrong attention mask, or a convolution that peeks at the next position.
- **Batch independence**: split the batch in two halves and run each half separately; the result must match running the whole batch. Catches BatchNorm left in train mode, a softmax over dim 0.
- **Padding invariance**: add a few columns of padding; the loss must not change. Catches padding counted in the mean.
- **Change only the test set; the training data must not change**: catches data leakage.
- **Compare with a reference**: gradient accumulation vs one big batch; hand-written attention vs `F.scaled_dot_product_attention`.
- **Overfit one batch** (day 15): if the loss cannot get close to 0 there is a bug; if it drops to 0 immediately, be suspicious too (for example, unshifted labels).

Two details when writing such tests. First, call `model.eval()`, or Dropout's randomness makes outputs change that should stay the same. Second, compare floats with `torch.allclose(a, b, atol=1e-5)`, not `==`.

The code below checks causality at one position only. `CumMean` (the output at t is the mean of the first t+1 inputs) and `TinyAttention` (one-head attention; `mask="none"` means no mask) are small models prepared for today. In the practice items you turn this into a tool that checks every position.
--- code
torch.manual_seed(0)
x = torch.randn(1, 6, 8)
x2 = x.clone()
x2[:, 4:] = torch.randn(1, 2, 8)          # change positions 4 and 5 only: the "future"
for name, m in [("CumMean", CumMean()), ("attention without a mask", TinyAttention(8, mask="none"))]:
    m.eval()
    with torch.no_grad():
        same = torch.allclose(m(x)[:, :4], m(x2)[:, :4], atol=1e-5)
    print(f"{name}: outputs at the first 4 positions unchanged = {same}")

@@ item d17-01
type: predict
title: What Dropout outputs in train and in eval mode
level: 1
cards: train() and eval(): Dropout and BatchNorm change behaviour
--- context
"The same input gives a different prediction every time" is one of the most common beginner questions, and the cause is almost always a forgotten `model.eval()`. First see with your own eyes what Dropout does in each mode.
--- prompt
Read the code and write the two lines it prints.

Hint: in train mode, a Dropout with `p=0.5` multiplies the values it keeps by 1/(1-p).
--- code
torch.manual_seed(0)
drop = nn.Dropout(p=0.5)
x = torch.ones(4)
drop.eval()
print(drop(x).tolist())
drop.train()
print(sorted(set(drop(x).tolist())))
--- explain
Line 1: in eval mode Dropout does nothing, so the output equals the input: `[1.0, 1.0, 1.0, 1.0]`.

Line 2: in train mode, each value becomes 0 with probability one half, and the others are multiplied by 1/(1-0.5) = 2, so the average stays 1. `set` removes duplicates and `sorted` orders them: `[0.0, 2.0]` (with this seed both values occur).

So if you forget `eval()` at inference time, part of the network is switched off at random, and every prediction is different.
--- hints
- In eval mode Dropout lets everything through unchanged.
- In train mode each 1.0 becomes either 0 or 1.0 / (1 - 0.5).

--- solution
def fit(model, train_batches, val_batch, eval_every=2):
    opt = torch.optim.SGD(model.parameters(), lr=0.1)
    val_losses = []
    for step, (x, y) in enumerate(train_batches):
        model.train()                # train mode at the start of every step, whatever happened before
        loss = F.mse_loss(model(x), y)
        opt.zero_grad()
        loss.backward()
        opt.step()
        if (step + 1) % eval_every == 0:
            model.eval()
            with torch.no_grad():
                xv, yv = val_batch
                val_losses.append(F.mse_loss(model(xv), yv).item())
    return val_losses

def check_batch_independent(f, x):
    h = x.shape[0] // 2
    with torch.no_grad():
        whole = f(x)                                   # the whole batch at once
        parts = torch.cat([f(x[:h]), f(x[h:])])        # the two halves separately
    return torch.allclose(parts, whole, atol=1e-5)

Each option pairs an invariant test with a bug it can catch. Which pairs are **correct**? (Several answers.)
--- options
- Causality check (change the inputs after position t; the outputs at 0..t stay the same) → catches: an attention mask written as `tril(diagonal=1)`
- Batch-independence check (two halves separately == whole batch at once) → catches: `model.eval()` forgotten before predicting, so BatchNorm uses batch statistics
- Padding invariance (a few more columns of padding; the loss stays the same) → catches: padding positions counted in the mean loss
- Comparison with the big batch (accumulated gradient == big-batch gradient) → catches: the scheduler steps only once per epoch
- Causality check → catches: normalisation that uses the test set's mean
answer: 1,2,3
--- explain
The first three are correct: each bug breaks the matching property, so the test fails.

Option 4 is wrong: comparing with the big batch catches gradient accumulation without weighting. For the scheduler, record the learning rate actually used at every step and compare it with the schedule.

Option 5 is wrong: causality is about positions in a sequence (the past must not see the future); it has nothing to do with leakage between the training and test sets. Check data leakage with "change only the test set; the training data must not change".
--- hints

- The gradient-accumulation comparison never calls a scheduler at all.

def masked_lm_loss(logits, targets, mask):
    V = logits.size(-1)
    loss = F.cross_entropy(logits.reshape(-1, V), targets.reshape(-1), reduction="none")
    mask = mask.reshape(-1).to(loss.dtype)
    return (loss * mask).sum() / mask.sum()      # the denominator counts real tokens only
