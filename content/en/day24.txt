@@ concept
title: Six things to record for every run
--- body
Three months from now, someone asks you: "How was the production model trained? Can you train the same one again?" If you cannot answer, nobody can fix or improve that model, or even explain why it is good.

So every training run must leave a **run record**. It answers one question: with the same inputs, do we get the same result again? Record at least six things:

1. **config**: every hyperparameter (learning rate, batch size, number of epochs, model size, ...).
2. **git commit**: the version of the code, a 40-character hexadecimal string (what `git rev-parse HEAD` prints). If there are uncommitted changes (a "dirty" working tree), the commit is not the code you ran. Commit first, or save the diff with the record.
3. **data fingerprint**: the sha256 of the data files' contents (next card). A file can keep its name while someone changes what is inside.
4. **seed**: the random seed.
5. **library versions**: Python, torch and numpy. Results that change after a torch upgrade are common.
6. **metrics**: the results of this run (val_loss, val_acc, ...).

Add a `run_id` to name the run. Save the whole record as one JSON file, next to the checkpoint.

In today's exercises the git commit is passed in as a string; you never run git.
--- code
import platform
import numpy as np

record = {
    "run_id": "run-01",
    "config": {"lr": 0.001, "batch_size": 32, "epochs": 10},
    "git_commit": "3f9a2c1d0b7e4f6a8c5d2e1f0a9b8c7d6e5f4a3b",
    "data_fingerprint": "(the next card shows how to compute it)",
    "seed": 42,
    "versions": {"python": platform.python_version(), "torch": torch.__version__, "numpy": np.__version__},
    "metrics": {"val_loss": 0.47, "val_acc": 0.842},
}
for key, value in record.items():
    print(f"{key:17s}", value)
print("the git commit has", len(record["git_commit"]), "characters")

@@ concept
title: Data fingerprints: sha256 recognises the same data
--- body
sha256 is a **hash function**: it turns any number of bytes into a 64-character hexadecimal string (the hash). Two properties make it a good "fingerprint" for data:

- The same bytes always give the same hash, on any machine, under any file name.
- Change even one byte and the hash is completely different.

Python has `hashlib` built in:

```
h = hashlib.sha256()
h.update(b"some bytes")    # you can call update several times; the result is the same as one big call
h.hexdigest()              # 64 characters
```

Open files in binary mode `"rb"` (the hash is over bytes) and read them in chunks, for example 1 MB at a time. Then even a 10 GB file never has to fit in memory.

A dataset is often several files. How do you turn them into one fingerprint? Gluing the contents together in order has a problem: the order in which `os.listdir` returns files can differ between machines, so the same data would get different fingerprints.

The fix: **hash each file on its own, sort those hashes, join them with newlines, and hash the result once more.** Now the order of the files, their names and their folder do not matter. Only the contents count.
--- code
import hashlib

a, b = b"cat,1\n", b"dog,0\n"                     # the contents of two "files"
print("sha256 of a:        ", hashlib.sha256(a).hexdigest()[:16], "... (64 characters in total)")
print("a with one space:   ", hashlib.sha256(b"cat,1 \n").hexdigest()[:16], "...")
print("glued together, is a+b the same as b+a:", hashlib.sha256(a + b).hexdigest() == hashlib.sha256(b + a).hexdigest())

def fingerprint(contents):
    hashes = sorted(hashlib.sha256(c).hexdigest() for c in contents)
    return hashlib.sha256("\n".join(hashes).encode("utf-8")).hexdigest()

print("hash each, sort, combine: does the order still matter:", fingerprint([a, b]) != fingerprint([b, a]))

@@ concept
title: Seeds: torch, numpy and random each need one
--- body
One training run often has three separate sources of random numbers:

- **torch**: weight initialisation, Dropout, `torch.randn`. Seed it with `torch.manual_seed(seed)`.
- **numpy**: a lot of data code shuffles or splits with `np.random.permutation`. Seed it with `np.random.seed(seed)`.
- **Python's own random**: common in data augmentation, like `random.random() < 0.5`. Seed it with `random.seed(seed)`.

Each has its own state. **Seeding torch does nothing to numpy or random.** The order numpy shuffles into then depends on whatever used numpy's random numbers earlier in the process. Same seed, two runs, different data order, different results.

Two rules:

1. Seed all three at the start of training, once. If you re-seed inside every epoch, every epoch sees exactly the same order, and the shuffle does nothing.
2. Write the seed into the run record.

numpy also has a cleaner option: `rng = np.random.default_rng(seed)`, then `rng.permutation(n)`. That generator belongs to you alone; no other code can move it.

Some GPU operations are not deterministic by themselves (`cudnn.benchmark`, deterministic algorithms); day 18 covers that. Today is only about seeds.
--- code
import numpy as np

def shuffled(seed, also_numpy):
    torch.manual_seed(seed)
    if also_numpy:
        np.random.seed(seed)
    return np.random.permutation(6).tolist()

np.random.seed(1); a = shuffled(0, also_numpy=False)    # pretend other code used numpy's random numbers before
np.random.seed(2); b = shuffled(0, also_numpy=False)
print("only torch seeded: ", a, b, "same:", a == b)
np.random.seed(1); a = shuffled(0, also_numpy=True)
np.random.seed(2); b = shuffled(0, also_numpy=True)
print("numpy seeded too:  ", a, b, "same:", a == b)
rng = np.random.default_rng(0)
print("your own generator default_rng(0):", rng.permutation(6).tolist())

@@ concept
title: Saving as JSON: only a few simple types
--- body
Run records and the registry are saved as JSON: plain text that people can read, every language can parse, and git diff can compare.

- `json.dump(obj, f)` writes to a file; `json.load(f)` reads it back.
- The versions with an s, `json.dumps(obj)` / `json.loads(text)`, work on strings, not files.

JSON only knows these types: dict, list, str, int, float, True / False, None. Three common traps:

- **Tensors and numpy float32 values cannot be saved.** You get `TypeError: Object of type Tensor is not JSON serializable`. Metrics are often 0-dim tensors like `loss.mean()`; turn them into Python numbers with `float(v)` before saving.
- **Dict keys must be strings.** Save `{1: ...}` and you read back `{"1": ...}`, so `1 in d` becomes False. That is why today's registry keeps version numbers inside a list instead of using them as keys.
- Tuples come back as lists.

Two good habits: `indent=2` puts the file on several indented lines, easy to read; `sort_keys=True` fixes the key order, so two files can be compared line by line. Pass `encoding="utf-8"` when you open the file; otherwise Windows may use a different encoding.
--- code
import json
import numpy as np

metrics = {"val_loss": torch.tensor(0.25), "val_acc": np.float32(0.875)}
try:
    json.dumps(metrics)
except TypeError as e:
    print("cannot save:", e)
clean = {k: float(v) for k, v in metrics.items()}
print("after float():", json.dumps(clean, sort_keys=True))
back = json.loads(json.dumps({"versions": {1: "a", 2: "b"}}))
print("int keys come back as:", list(back["versions"]), "  1 in it:", 1 in back["versions"])
print(json.dumps({"lr": 0.001, "betas": (0.9, 0.95)}, indent=2))

@@ concept
title: Comparing runs: which is best, and what changed
ref: day24
--- body
While tuning you run many experiments, and each one leaves a JSON record. Comparing them takes two moves.

**1. Pick the best run by one metric.** First decide the direction: for accuracy higher is better, so use `max`; for loss lower is better, so use `min`. Different metrics can pick different "best" runs.

`max(runs, key=lambda r: r["metrics"]["val_acc"])` returns the **whole record**, not just the number. `key=` tells `max` what to compare; `lambda r: ...` is a one-line function.

A run that crashed (say the loss became nan before evaluation) does not have the metric. Skip it: it must not raise an error, and it must not count as a score of 0.

**2. See where two configs differ.** Take all keys from both configs (`set(a) | set(b)`) and compare the values one by one. A key that only one side has (say warmup, added later) counts as None on the other side. `d.get(key)` returns exactly None when the key is missing.

One more rule: only runs with the same data fingerprint can be compared directly. On a different test set, a higher score may just mean easier questions.
--- code
runs = sample_runs()
for r in runs:
    print(r["run_id"], " lr =", r["config"]["lr"], " batch =", r["config"]["batch_size"], " metrics =", r["metrics"])
done = [r for r in runs if "val_acc" in r["metrics"]]          # skip run-03, which crashed
print("highest val_acc:", max(done, key=lambda r: r["metrics"]["val_acc"])["run_id"])
print("lowest val_loss:", min(done, key=lambda r: r["metrics"]["val_loss"])["run_id"])
a, b = runs[1]["config"], runs[3]["config"]
print("all keys of both configs:", sorted(set(a) | set(b)))
print("warmup:", a.get("warmup"), "->", b.get("warmup"))

@@ concept
title: A model registry: register, promote, history
ref: day24
--- body
You keep training models. Which one is in production? Which one was before it? Which run produced it? A **model registry** answers these questions. Tools like MLflow and Weights & Biases have one. Today we build the smallest possible one in a JSON file:

```
{"versions": [{"version": 1, "run_id": "run-01", "metrics": {"val_acc": 0.842}},
              {"version": 2, "run_id": "run-04", "metrics": {"val_acc": 0.875}}],
 "production": 2,
 "history": [2]}
```

- **register**: add a new version. Versions count up 1, 2, 3, and each records the run it came from (run_id) and its metrics. Registering is not deploying.
- **promote**: make a version the `production` one and append it to `history` (the versions that were in production, in order).
- **production**: which version is in production now, or None.

One important rule: **every method loads the file, changes it and writes it back; nothing is kept only in memory.** The training script, the release script and the inference service are different processes. The file is the only way they all see the same state.

Write the file by "write a temporary file, then `os.replace`", so a crash halfway never leaves a broken file (day 20). Today's `JsonStore` already has `self._load()` and `self._save(data)`; when the file does not exist yet, `_load()` returns an empty registry.
--- code
import json
import tempfile

with tempfile.TemporaryDirectory(ignore_cleanup_errors=True) as folder:
    reg = BasicRegistry(folder)
    print("register, version numbers:", reg.register("run-01", {"val_acc": 0.842}), reg.register("run-04", {"val_acc": 0.875}))
    print("production:", reg.production())
    reg.promote(2)
    print("after promote(2), seen by a brand-new object:", BasicRegistry(folder).production())
    print(json.dumps(reg._load()))

@@ concept
title: The promotion gate and rollback
ref: day24
--- body
**The gate**: a new version may go to production only if its evaluation metric is not worse than production's. Without it, one careless command ships a worse model. The rules:

- Nothing in production yet: promote it.
- Mind the direction. With `higher_is_better=True` (accuracy), the new one is worse when it is **smaller**; with `False` (loss), it is worse when it is **larger**.
- Equally good is fine.
- Worse: `raise ValueError(...)` and change nothing in the file. Put both numbers in the message; it helps whoever investigates.

**Rollback**: a new version is live and something goes wrong (more complaints, higher latency). The first move is to go back to the previous version, so production is healthy again; find the cause afterwards. With `history`, rollback means: remove the last entry of history and set production to the new last entry. With fewer than 2 versions in history there is nothing to go back to: `raise ValueError`.

Note: **rollback does not go through the gate.** The previous version usually scores lower (that is why it was replaced), so the gate would block every rollback. In an incident you want one step back to a state you know works.

Real systems check more before promoting, for example sending only a small share of traffic first (a canary). That is day 25.
--- code
import tempfile

with tempfile.TemporaryDirectory(ignore_cleanup_errors=True) as folder:
    reg = Registry(folder)                       # compares val_acc, higher is better
    for run_id, acc in [("run-01", 0.842), ("run-04", 0.875), ("run-05", 0.861)]:
        reg.register(run_id, {"val_acc": acc})
    reg.promote(1)
    reg.promote(2)
    try:
        reg.promote(3)
    except ValueError as e:
        print("v3 refused:", e)
    print("production:", reg.production(), " history:", reg._load()["history"])
    print("rolled back to:", reg.rollback(), " history:", reg._load()["history"])

@@ concept
title: Model cards: a manual for the people who use the model
ref: day24
--- body
A run record is for **you**: how to reproduce the model. A **model card** is for **the people who use the model**: what it can do, what it cannot do, and when it makes mistakes. Another team that wants to call your model, or a product manager deciding whether to launch, reads it first.

A minimal model card has these sections:

1. **Name and version**: the same version number as in the registry.
2. **Intended use**: what it was built for, for example "label English product reviews as positive / negative".
3. **Out of scope**: where it must not be used, for example "other languages", "medical or legal decisions".
4. **Evaluation**: which metrics and what scores. Besides the overall score, add scores for groups (for example long reviews on their own); an average hides weak spots.
5. **Training data**: what the data is, plus its fingerprint.
6. **How to reproduce**: git commit, seed, library versions, all from the run record.
7. **Limitations and risks**: known problems, for example "often wrong on sarcasm".

Fill the numbers in a model card **with code, from the run record**; never copy them by hand. Hand-copied numbers drift away from the real ones sooner or later.
--- code
rec = sample_runs()[3]
lines = ["# Model card: review-sentiment v2", "## Evaluation"]
lines += [f"- {k}: {v:.4f}" for k, v in sorted(rec["metrics"].items())]
lines += ["## How to reproduce", "- git commit: " + rec["git_commit"], "- seed: " + str(rec["seed"])]
print("\n".join(lines))

type: predict
title: Fed in two parts, or in another order: same hash?
level: 1
cards: Data fingerprints: sha256 recognises the same data
--- context
Data fingerprints rest on two properties of sha256: feeding the bytes in chunks gives the same result as feeding them at once (so big files can be read in chunks), and changing the order of the bytes changes the result (so several files must be sorted first). Check both with your own eyes.
--- prompt
Read the code and write the three lines it prints.
--- code
import hashlib
h = hashlib.sha256()
h.update(b"cat,1\n")
h.update(b"dog,0\n")                          # fed in two parts
one_go = hashlib.sha256(b"cat,1\ndog,0\n").hexdigest()
print(h.hexdigest() == one_go)
print(len(one_go))
swapped = hashlib.sha256(b"dog,0\ncat,1\n").hexdigest()
print(one_go == swapped)
--- explain
Line 1, `True`: you can call `update` several times on a sha256, and the result is exactly the same as feeding all the bytes at once. That is why a big file can be read and hashed one chunk at a time, without loading it into memory.

Line 2, `64`: `hexdigest()` returns 64 hexadecimal characters (256 bits, 4 bits per character).

Line 3, `False`: the two lines are the same but in the other order, so the bytes are different and so is the hash. That is why several files are combined into one fingerprint by hashing each one, sorting the hashes, and only then combining them.
--- hints
- After the two `update` calls, what bytes has the hash seen in total? Compare them with the bytes behind `one_go`.
- A hash only sees bytes. Are `b"cat,1\ndog,0\n"` and `b"dog,0\ncat,1\n"` the same bytes?

--- prompt

import hashlib

def file_sha256(path):
    """path -> 64-character hexadecimal string"""
    h = hashlib.sha256()
    with open(path, "rb") as f:                  # binary mode: read the bytes as they are
        while True:
            chunk = f.read(1 << 20)              # 1 MB at a time
            if not chunk:                        # the empty b"": end of file
                break
            h.update(chunk)
    return h.hexdigest()

--- context
If the same data has one fingerprint on your laptop and another on the training cluster, the fingerprint is useless. `os.listdir` and `glob` do not promise any file order, so a fingerprint must not depend on the order, and it should not depend on file names either.
--- prompt
Write `data_fingerprint(paths)`: `paths` is a list of file paths; return a 64-character fingerprint. Follow these steps exactly (the checks compare the value):

1. Hash every file with `file_sha256(p)` (already written).

3. Join them with a newline `"\n"`, turn the result into bytes with `.encode("utf-8")`, hash it once more with sha256 and return `hexdigest()`.

import hashlib

def data_fingerprint(paths):
    """a set of files -> one 64-character fingerprint, independent of file order and names"""
    hashes = sorted(file_sha256(p) for p in paths)          # sorted: the order no longer counts
    joined = "\n".join(hashes).encode("utf-8")
    return hashlib.sha256(joined).hexdigest()

import random
import numpy as np

def train_run(seed, x, y, epochs=2, batch_size=8):
    """Return (trained weight, the sample order of every epoch)"""
    torch.manual_seed(seed)
    np.random.seed(seed)                               # numpy: shuffling
    random.seed(seed)                                  # random: augmentation

def best_run(runs, metric, higher_is_better=True):
    """Return the record with the best metric; skip records without that metric"""
    have = [r for r in runs if metric in r["metrics"]]      # skip crashed runs
    if not have:
        raise ValueError(f"no record has the metric {metric!r}")
    pick = max if higher_is_better else min
    return pick(have, key=lambda r: r["metrics"][metric])


def config_diff(a, b):
    """{key: (value in a, value in b)}, only for keys whose values differ; a missing side is None"""
    diff = {}
    for k in sorted(set(a) | set(b)):                       # every key of both sides
        if a.get(k) != b.get(k):                            # for the missing side, get returns None
            diff[k] = (a.get(k), b.get(k))
    return diff

class Registry(JsonStore):
    def register(self, run_id, metrics):
        """Add a new version; return its number (1, 2, 3, ...)"""
        data = self._load()
        version = len(data["versions"]) + 1
        data["versions"].append({"version": version, "run_id": run_id, "metrics": metrics})
        self._save(data)
        return version

    def production(self):
        """The production version number, or None"""
        return self._load()["production"]

    def promote(self, version):
        """Make version the production version and record it in history"""
        data = self._load()
        if not any(v["version"] == version for v in data["versions"]):
            raise ValueError(f"no version {version}")
        data["production"] = version
        data["history"].append(version)
        self._save(data)

class Registry(BasicRegistry):
    def promote(self, version):
        """Promote only if not worse than production; if worse, raise ValueError"""
        new = self.get(version)["metrics"][self.metric]
        data = self._load()
        current = data["production"]
        if current is not None:
            old = self.get(current)["metrics"][self.metric]
            worse = new < old if self.higher_is_better else new > old
            if worse:
                raise ValueError(f"v{version} has {self.metric}={new}, worse than production v{current} with {old}")
        data["production"] = version
        data["history"].append(version)
        self._save(data)

    def rollback(self):
        """Go back to the previously promoted version; return its number"""
        data = self._load()
        if len(data["history"]) < 2:
            raise ValueError("nothing to roll back to")
        data["history"].pop()                          # drop the version that caused trouble
        data["production"] = data["history"][-1]       # back to the previous one, no gate
        self._save(data)
        return data["production"]

Write `promote(version)` and `rollback()` of `class Registry(BasicRegistry)`. You can use `self.get(version)`, `self._load()`, `self._save(data)`, `self.metric` and `self.higher_is_better`.

- `promote`: if a version is in production, the new version's `self.metric` must not be worse (the direction comes from `higher_is_better`). If it is worse, `raise ValueError` and leave the file unchanged; otherwise make it `production`, append it to `history`, save.
- `rollback`: with fewer than 2 entries in `history`, `raise ValueError`; otherwise go back to the previously promoted version and return its number. Rollback does not go through the gate.

--- solution
class Registry(BasicRegistry):
    def promote(self, version):
        new = self.get(version)["metrics"][self.metric]
        data = self._load()
        current = data["production"]
        if current is not None:
            old = self.get(current)["metrics"][self.metric]
            worse = new < old if self.higher_is_better else new > old
            if worse:
                raise ValueError(f"v{version} has {self.metric}={new}, worse than production v{current} with {old}")
        data["production"] = version
        data["history"].append(version)
        self._save(data)

    def rollback(self):
        data = self._load()
        if len(data["history"]) < 2:
            raise ValueError("nothing to roll back to")
        data["history"].pop()                          # drop the version that caused trouble
        data["production"] = data["history"][-1]       # back to the previous one, no gate
        self._save(data)
        return data["production"]

import os, json, tempfile

def _setup(folder, scores, metric="val_acc", higher=True):
    reg = Registry(folder, metric=metric, higher_is_better=higher)
    for i, s in enumerate(scores, 1):
        reg.register(f"run-{i:02d}", {metric: s})
    return reg

def _refused(fn):
    try:
        fn()
    except ValueError:
        return True
    return False

@check("the first version goes straight to production; a version that is not worse can follow")
def _():
    with tempfile.TemporaryDirectory(ignore_cleanup_errors=True) as folder:
        reg = _setup(folder, [0.80, 0.85, 0.85])
        reg.promote(1)
        true(reg.production() == 1, "with nothing in production, the first version should be promoted directly")
        reg.promote(2)
        true(reg.production() == 2, "v2 (0.85) is better than v1 in production (0.80); it should be promoted")
        reg.promote(3)
        true(reg.production() == 3, "v3 equals v2 in production (both 0.85); that is not worse, so it should be promoted")
        history = reg._load()["history"]
    true(history == [1, 2, 3], f"history should be [1, 2, 3]; it is {history}")

@check("a version worse than production is refused; production and history stay the same")
def _():
    with tempfile.TemporaryDirectory(ignore_cleanup_errors=True) as folder:
        reg = _setup(folder, [0.80, 0.85, 0.78])
        reg.promote(1)
        reg.promote(2)
        true(_refused(lambda: reg.promote(3)), "v3 (0.78) is worse than v2 in production (0.85); promote(3) should raise ValueError")
        other = Registry(folder)
        true(other.production() == 2, f"after the refusal, production should still be v2; it is v{other.production()}")
        history = other._load()["history"]
    true(history == [1, 2], f"after the refusal, history should still be [1, 2]; it is {history}: check first, and change the file only if the check passes")

@check("val_loss, lower is better: the direction flips")
def _():
    with tempfile.TemporaryDirectory(ignore_cleanup_errors=True) as folder:
        reg = _setup(folder, [0.50, 0.40, 0.45], metric="val_loss", higher=False)
        reg.promote(1)
        true(not _refused(lambda: reg.promote(2)), "v2 has val_loss 0.40, lower than v1's 0.50, so it is better, yet it was refused. With higher_is_better=False, lower is better.")
        true(reg.production() == 2, "v2 should be in production now")
        true(_refused(lambda: reg.promote(3)), "v3 has val_loss 0.45, higher than production v2's 0.40, so it is worse and should be refused")

@check("rollback: back to the previous production version, whatever its score")
def _():
    with tempfile.TemporaryDirectory(ignore_cleanup_errors=True) as folder:
        reg = _setup(folder, [0.80, 0.85])
        reg.promote(1)
        reg.promote(2)
        try:
            back = reg.rollback()
        except ValueError as e:
            true(False, f"rollback raised: {e}. Rollback does not go through the gate: the previous version usually scores lower. Change production and history directly; do not call promote.")
        true(back == 1, f"rollback() should return the version it went back to, 1; you returned {back!r}")
        other = Registry(folder)
        true(other.production() == 1, "after rollback, production should be v1 (a new Registry must see it too)")
        history = other._load()["history"]
    true(history == [1], f"after rollback, history should be [1]; it is {history}")

@check("nothing to roll back to: raise ValueError")
def _():
    with tempfile.TemporaryDirectory(ignore_cleanup_errors=True) as folder:
        reg = _setup(folder, [0.80, 0.85])
        reg.promote(1)
        true(_refused(reg.rollback), "only v1 was ever promoted, there is nothing earlier: rollback() should raise ValueError")
        true(Registry(folder).production() == 1, "after a failed rollback, production should still be v1")
--- hints
- promote: compare first; change data only if the check passes.
- rollback: pop the last entry; production becomes the new last entry.
