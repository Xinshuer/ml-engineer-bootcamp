@@ concept
title: Waveforms and sample rate: numbers per second
--- body
To a computer, a piece of audio is just a list of numbers called a **waveform**. Each number records how far the sound vibration is from rest at one instant. The values are roughly between -1 and 1.

The **sample rate** (sr) is how many numbers are recorded per second. 16 kHz means 16,000 numbers per second.

- number of samples = seconds × sr, rounded down. 2 seconds at 16 kHz → 32,000 samples
- seconds = number of samples ÷ sr. 48,000 samples at 16 kHz → 3.0 seconds
- one mono clip has shape `(T,)`; a batch has shape `(B, T)`

Common sample rates: speech recognition often uses 16 kHz; TTS and audio codecs often use 22.05 kHz or 24 kHz; music CDs use 44.1 kHz.

Models usually do not look at every sample. They cut the waveform into frames. The distance between the starts of two neighbouring frames is the **hop**. So:

- frames per second (frame rate) = sr ÷ hop
- 16 kHz with hop=160 → 100 frames per second (this is what Whisper uses)

The frame rate plays the role of "how many characters per token" in an LLM: it decides how long a sequence a clip becomes, and so how much work the model has to do.
--- code
sr = 16000
seconds = 2.5
T = int(seconds * sr)
wav = torch.zeros(T)                  # 2.5 seconds of silence
print("shape:", tuple(wav.shape))
print("duration:", wav.numel() / sr, "seconds")

for sr_, hop in [(16000, 160), (22050, 256), (24000, 300)]:
    print(f"sr={sr_}, hop={hop}: {sr_ / hop:.1f} frames per second")

@@ concept
title: Peak normalization: making volumes match
--- body
Recordings differ a lot in volume. Someone speaking right into the microphone has a **peak** (the sample with the largest absolute value) close to 1. Someone far away may peak at 0.05. Before training, a common step is to bring every clip to the same level.

**Peak normalization** multiplies the whole waveform by one number so that the peak lands exactly on a target, for example 0.95.

- peak = `wav.abs().max()` (take the absolute value: negative samples count too)
- result = `wav * (target / peak)`
- every sample is multiplied by the same number, so the shape of the wave stays the same; only the volume changes
- the target is 0.95 rather than 1.0 to leave some headroom: if later processing pushes values past 1 they get clipped, which sounds like crackling

The trap: a clip of pure silence has peak 0. `0.95 / 0` is inf, and `0 * inf` is nan. One silent file in the dataset is enough to put nan into training. So when the peak is 0, return the input unchanged.
--- code
wav = torch.tensor([0.05, -0.2, 0.1])
peak = wav.abs().max()
print("peak:", round(peak.item(), 3))
out = wav * (0.95 / peak)
print("normalized:", [round(v, 4) for v in out.tolist()])
print("new peak:", round(out.abs().max().item(), 4))

silence = torch.zeros(3)
print("silence, divided anyway:", (silence * (0.95 / silence.abs().max())).tolist())

@@ concept
title: Framing: cutting a waveform into frames with unfold
--- body
Sound changes all the time, but over a very short stretch (20 to 60 milliseconds) it stays roughly the same. So the first step in audio processing is usually **framing**: a window of length `size` slides along the waveform, moving `step` samples each time (this step is the hop).

`wav.unfold(0, size, step)` does it in one call: along dimension 0 it takes a piece of length `size` every `step` samples and stacks the pieces along a new dimension.

- input `(T,)` → output `(n_frames, size)`
- frame i is `wav[i*step : i*step + size]`
- n_frames = `(T - size) // step + 1`; a tail too short for a full frame is dropped
- the result is a view: no data is copied, so it is fast; cutting frames one by one in a Python loop is much slower on long audio

Example: T=8, size=3, step=2 → (8 - 3) // 2 + 1 = 3 frames, starting at 0, 2 and 4. The last sample (7) is dropped.

Remember this frame-count formula: it is exactly the STFT frame count with `center=False` on the next card.
--- code
wav = torch.arange(8.)
frames = wav.unfold(0, 3, 2)
print(frames)
print("frame-count formula:", (8 - 3) // 2 + 1)

big = torch.randn(16000).unfold(0, 400, 160)   # 16 kHz: 25 ms frames, 10 ms hop
print(tuple(big.shape), "=", (16000 - 400) // 160 + 1, "frames")

@@ concept
title: STFT: frequency bins and frame count
--- body
After framing, run an FFT (fast Fourier transform) on each frame. That tells you how strong each frequency is inside that frame. Put all frames side by side and you have the **STFT** (short-time Fourier transform). `torch.stft` does the framing, the windowing and the FFT in one call.

Three parameters:

- `n_fft`: samples per frame, e.g. 1024
- `hop_length`: samples between the starts of neighbouring frames, e.g. 256
- `window`: each frame is first multiplied by a window that fades its edges to 0; the usual one is `torch.hann_window(n_fft)`

The output shape is `(n_bins, n_frames)`, or `(B, n_bins, n_frames)` for a batch.

- **number of frequency bins** = `n_fft // 2 + 1`. Each bin is `sr / n_fft` Hz wide; bin k stands for `k * sr / n_fft` Hz
- **number of frames, center=True** (the default): pad `n_fft // 2` samples at both ends, then frame. n_frames = `T // hop + 1`
- **number of frames, center=False**: no padding, same as unfold. n_frames = `(T - n_fft) // hop + 1`

Example: T=16000, n_fft=512, hop=128 → 257 bins; 126 frames with center=True, 122 with center=False. Note that with center=True the frame count does not depend on n_fft at all, only on the hop.

Pass `return_complex=True`: the output is a complex tensor (`complex64`). The absolute value `.abs()` of each complex number is how strong that frequency is. That gives the **magnitude spectrogram**, an ordinary real tensor.
--- code
sr = 16000
t = torch.arange(sr) / sr                      # a 1-second time axis
tone = torch.sin(2 * math.pi * 1000 * t)       # a pure 1000 Hz tone
n_fft, hop = 512, 128
spec = torch.stft(tone, n_fft, hop, window=torch.hann_window(n_fft), return_complex=True)
print("complex spectrogram:", tuple(spec.shape), spec.dtype)
mag = spec.abs()
print("magnitude:", tuple(mag.shape), mag.dtype)
print("strongest bin in frame 60:", mag[:, 60].argmax().item(), " expected 1000 * 512 / 16000 =", 1000 * n_fft / sr)

nc = torch.stft(tone, n_fft, hop, window=torch.hann_window(n_fft), return_complex=True, center=False)
print("center=False:", tuple(nc.shape))

@@ concept
title: Magnitude and phase: what the magnitude spectrogram loses
--- body
Each cell of the STFT output is a complex number `a + bi`. Picture it as an arrow in a plane:

- **magnitude** = the arrow's length = `z.abs()` = √(a² + b²). How strong this frequency is. Always ≥ 0
- **phase** = the arrow's angle = `z.angle()`. Where in its cycle this frequency's wave starts within the frame
- `z.real` is only the real part a. It is neither the magnitude nor the phase, and it can be negative. Writing `.real` when you want the magnitude is a very common bug

Magnitude + phase = the full information. `torch.polar(magnitude, phase)` rebuilds the complex numbers, and `torch.istft` (the inverse STFT) turns them back into a waveform with almost zero error.

But mel spectrograms and log-mels are computed from the magnitude only; the phase is thrown away. The experiment below sets every phase to 0 and rebuilds the waveform. The relative error is about 1.0: the error is as large as the signal itself, and the waveform is unrecognisable. That is why a TTS model that predicts a mel spectrogram also needs a **vocoder**, which "guesses" the phase back to produce playable audio (you will meet it on Day 12).
--- code
torch.manual_seed(1)
wav = torch.randn(4096)
win = torch.hann_window(512)
spec = torch.stft(wav, 512, 128, window=win, return_complex=True)
mag, phase = spec.abs(), spec.angle()
print("spec:", tuple(spec.shape), spec.dtype)

z = torch.tensor(-3 + 4j)
print("one cell -3+4j: real =", z.real.item(), " abs =", z.abs().item())

def rel_err(x):
    return (((x - wav) ** 2).mean() / (wav ** 2).mean()).item()

full = torch.istft(torch.polar(mag, phase), 512, 128, window=win, length=4096)
print(f"rebuilt from magnitude + phase, relative error: {rel_err(full):.1e}")

no_phase = torch.istft(mag.to(torch.complex64), 512, 128, window=win, length=4096)
print(f"rebuilt from magnitude only (phase = 0), relative error: {rel_err(no_phase):.2f}")

@@ concept
title: The mel scale and the mel filterbank
--- body
Our ears are very sensitive to changes at low frequencies: 100 Hz and 200 Hz sound very different, but 7900 Hz and 8000 Hz sound almost the same. The **mel scale** turns Hz into "perceived distance":

`mel = 2595 * log10(1 + f / 700)`

- 0 Hz → 0 mel; 1000 Hz → about 1000 mel
- 100 → 200 Hz is 133 mel apart; 7900 → 8000 Hz is only 13 mel apart
- low frequencies get stretched out, high frequencies get squeezed together

A **mel filterbank** is a matrix `fb` of shape `(n_mels, n_freq)`, e.g. `(80, 513)`. Each row is one triangular filter. The 80 triangles are evenly spaced on the mel scale. Seen in Hz, the low triangles are narrow and packed tightly, the high ones are wide and spread out.

Squeezing 513 frequency bins into 80 mel bands is a single matrix multiplication:

- `fb @ mag`: `(80, 513) @ (513, 63)` → `(80, 63)`
- with a batch: `(80, 513) @ (B, 513, 63)` → `(B, 80, 63)`; `@` broadcasts over the batch

Real projects build fb with a library function (`torchaudio.functional.melscale_fbanks` or `librosa.filters.mel`). Watch the orientation: librosa returns `(n_mels, n_freq)` as here, but torchaudio returns the transpose `(n_freq, n_mels)`, so take `.T` before `fb @ mag`. The code below builds one by hand so you can see what it looks like.
--- code
def hz_to_mel(f):
    return 2595 * math.log10(1 + f / 700)

for f in [100, 200, 1000, 7900, 8000]:
    print(f, "Hz ->", round(hz_to_mel(f)), "mel")

sr, n_fft, n_mels = 16000, 1024, 80
edges_mel = torch.linspace(0, hz_to_mel(sr / 2), n_mels + 2)   # evenly spaced in mel
edges_hz = 700 * (10 ** (edges_mel / 2595) - 1)                # back to Hz
freqs = torch.linspace(0, sr / 2, n_fft // 2 + 1)              # the Hz of each of the 513 bins
fb = torch.zeros(n_mels, freqs.numel())
for i in range(n_mels):
    lo, mid, hi = edges_hz[i], edges_hz[i + 1], edges_hz[i + 2]
    rise = (freqs - lo) / (mid - lo)
    fall = (hi - freqs) / (hi - mid)
    fb[i] = torch.clamp(torch.minimum(rise, fall), min=0)      # a triangle

print("fb:", tuple(fb.shape))
print("bins covered by filter 0:", (fb[0] > 0).sum().item())
print("bins covered by filter 79:", (fb[79] > 0).sum().item())
mag = torch.rand(2, 513, 63)
print("fb @ mag:", tuple((fb @ mag).shape))

@@ concept
title: Log-mel: take the log, add eps
--- body
Mel values cover a huge range: a quiet part may be 0.001 and a loud part 1000, a factor of a million. Fed in directly, the big numbers drown out everything else. Also, our sense of loudness is roughly logarithmic: ten times the energy sounds like just "one step louder".

So almost every speech model uses the **log-mel**: the log of the mel spectrogram. After the log, a factor of a million becomes a difference of only 13.8.

The trap: where there is total silence, mel = 0, and `log(0) = -inf`. One -inf inside the network and the loss becomes nan. So add a tiny number **eps**:

`log_mel = log(fb @ mag + eps)`, usually with eps = 1e-5.

With eps, total silence becomes log(1e-5) ≈ -11.5. This is the "silence floor" of a log-mel. The -11.5 used later for padding comes from here.

The whole chain: waveform `(T,)` → magnitude `(n_freq, n_frames)` → `fb @` → mel `(n_mels, n_frames)` → `log(· + eps)` → log-mel `(n_mels, n_frames)`.
--- code
mel = torch.tensor([0.0, 0.001, 1.0, 1000.0])
print("no eps  :", [round(v, 2) for v in torch.log(mel).tolist()])
print("with eps:", [round(v, 2) for v in torch.log(mel + 1e-5).tolist()])
print("silence floor log(1e-5) =", round(math.log(1e-5), 2))
print("max / min (linear):", 1000.0 / 0.001)
print("max - min (log)   :", round(math.log(1000.0) - math.log(0.001), 1))

@@ concept
title: Before the model: channel dim, padding and mask
--- body
**A mel spectrogram is a one-channel image**: height = n_mels, width = number of frames. Image models expect `(B, C, H, W)`, so for `(B, n_mels, n_frames)` you only add a channel dimension at position 1: `mel.unsqueeze(1)` → `(B, 1, n_mels, n_frames)`. After that the `nn.Conv2d` layers from Day 8 work unchanged.

**Variable length**: the clips in a batch have different lengths, so different frame counts, but a tensor must be a neat box. The fix is the same padding you know from text:

- find the longest frame count Tmax and create a `(B, n_mels, Tmax)` tensor filled with the pad value
- copy each mel into the left part; whatever is left on the right is padding
- use -11.5 (the log-mel silence floor) as the pad value, not 0: a log-mel value of 0 means energy 1, which is "sound", not silence
- also build a **mask** of shape `(B, Tmax)`: 1 for real frames, 0 for padding. The loss and attention use it later to ignore the padding

`F.pad(x, (left, right), value=v)` pads the last dimension on both sides; `arange < lengths` builds the whole mask in one go.

The code below walks the whole shape chain for 0.5 seconds with n_fft=512, hop=128, n_mels=64.
--- code
wav = torch.randn(8000)                         # 0.5 seconds at 16 kHz
mag = torch.stft(wav, 512, 128, window=torch.hann_window(512), return_complex=True).abs()
fb = torch.rand(64, 257)                        # a fake filterbank, only the shape matters here
log_mel = torch.log(fb @ mag + 1e-5)
x = log_mel.unsqueeze(0).unsqueeze(0)           # add a batch dim and a channel dim
print(tuple(wav.shape), "->", tuple(mag.shape), "->", tuple(log_mel.shape), "->", tuple(x.shape))
print("Conv2d output:", tuple(nn.Conv2d(1, 8, 3, padding=1)(x).shape))

short = torch.zeros(2, 3)                       # a mel with 3 frames (n_mels=2)
print(F.pad(short, (0, 5 - 3), value=-11.5))    # pad 2 frames on the right
lengths = torch.tensor([3, 5])
print((torch.arange(5)[None, :] < lengths[:, None]).long())

--- context
The sequence length the model sees is the STFT frame count. Get it wrong by one frame and the alignment between mel frames and text, or between mel frames and audio tokens, slips; concatenations may also fail with a shape mismatch.
--- prompt
Write `n_frames(n_sample, n_fft, hop_length, center=True)`. It returns the number of frames `torch.stft` would produce, as an int. Do not call `torch.stft`; use a formula.

- `center=True`: first pad `n_fft // 2` samples at both ends of the waveform, then cut frames
- `center=False`: no padding. The first frame starts at sample 0, each frame has `n_fft` samples, and a tail too short for a full frame is dropped

The check compares your result with the real `torch.stft(...).shape[-1]` (every `n_fft` is even).
--- starter
def n_frames(n_sample, n_fft, hop_length, center=True):
    """Return the number of frames torch.stft produces."""
    raise todo()
--- solution
def n_frames(n_sample, n_fft, hop_length, center=True):
    if center:
        return n_sample // hop_length + 1
    return (n_sample - n_fft) // hop_length + 1
--- tests
@check("STFT frame-count formula")
def t02():
    for n, nf, hop in [(16000, 1024, 256), (12345, 512, 128), (48000, 2048, 512)]:
        real = torch.stft(torch.zeros(n), nf, hop, window=torch.hann_window(nf),
                          return_complex=True, center=True).shape[-1]
        true(n_frames(n, nf, hop, True) == real,
             f"center=True, n={n}, n_fft={nf}, hop={hop}: you computed {n_frames(n, nf, hop, True)}, torch.stft gives {real}")
        real2 = torch.stft(torch.zeros(n), nf, hop, window=torch.hann_window(nf),
                           return_complex=True, center=False).shape[-1]
        true(n_frames(n, nf, hop, False) == real2,
             f"center=False, n={n}, n_fft={nf}, hop={hop}: you computed {n_frames(n, nf, hop, False)}, torch.stft gives {real2}")
--- hints
- center=False works exactly like unfold: frames start at 0, hop, 2·hop, …, and the last frame must fit completely.
- center=False: `(n_sample - n_fft) // hop_length + 1`. With center=True the length becomes `n_sample + n_fft`; put that into the same formula and simplify.
- center=True simplifies to `n_sample // hop_length + 1`.

def stft_mag(wav, n_fft=1024, hop_length=256):
    """wav: (T,) or (B, T) -> magnitude (..., n_fft//2 + 1, n_frames)"""

--- solution
def stft_mag(wav, n_fft=1024, hop_length=256):
    win = torch.hann_window(n_fft, device=wav.device)
    return torch.stft(wav, n_fft, hop_length, window=win,

The mel scale makes the frequency axis closer to how we hear, which is why speech models almost always use mel spectrograms. Building a filterbank, setting `f_min` / `f_max` or reading a spectrogram plot all mean converting between Hz and mel.
--- prompt
Write two functions. Inputs and outputs are plain Python numbers (`math` is enough):

- `hz_to_mel(f)`: `2595 * log10(1 + f / 700)`
- `mel_to_hz(m)`: its inverse, so that `mel_to_hz(hz_to_mel(f)) ≈ f`

    raise todo()

--- solution
def hz_to_mel(f):
    return 2595.0 * math.log10(1.0 + f / 700.0)


def mel_to_hz(m):
    return 700.0 * (10 ** (m / 2595.0) - 1.0)
--- tests
@check("mel conversion")

    true(close(hz_to_mel(0), 0.0), f"hz_to_mel(0) should be 0, got {hz_to_mel(0)}")

--- hints
- `math.log10(x)` is the base-10 log.
- To invert, solve `m = 2595 * log10(1 + f/700)` for f: divide both sides by 2595, then raise 10 to the power of both sides.

def pad_mels(mels, pad_value=-11.5):

    n_mels = mels[0].size(0)
    Tmax = max(m.size(1) for m in mels)
