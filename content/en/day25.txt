@@ concept
title: The numbers to watch after launch
--- body
Once a model is live, someone asks every day: "Is it OK?" To answer, you look at two kinds of numbers.

**Is the service healthy?** (the same as for any web backend)

- **Latency**: how long one request takes from arrival to response. Look at percentiles p50 / p95 / p99 (day 22), not only the mean. A few very slow requests pull the mean up, and at the same time the mean hides them.
- **Error rate**: the share of requests that fail. 5xx (server errors) and timeouts count. 4xx (the user sent bad data) is usually tracked separately.
- **Throughput**: how many requests per second are handled (req/s). If more come in than get finished, the queue keeps growing.
- **Saturation**: GPU use, GPU memory, number of queued requests. GPU at 100% and a growing queue mean you are out of capacity.
- **Cost**: what 1,000 requests cost (the last card today).

**Is the model right?** All of the above can be green while the model quietly gets worse. Say a new group of users arrives and the inputs no longer look like the training data. The service still answers on time; the answers are just wrong. True labels (did this loan default, was this payment fraud) often take days or weeks to arrive. So first watch the **input distribution** and the **prediction distribution** (the next cards).

Below, a 10-second request log turns into the numbers on a dashboard.
--- code
latency_ms = torch.tensor([21., 19, 25, 22, 480, 20, 23, 18, 2000, 24, 22, 19])
status = torch.tensor([200, 200, 200, 200, 200, 200, 200, 200, 504, 200, 500, 200])
seconds = 10                                         # these 12 requests arrived within 10 seconds
gpu_util = torch.tensor([0.62, 0.71, 0.68, 0.66])    # sampled every 2.5 seconds

print("throughput:", len(latency_ms) / seconds, "req/s")
print("error rate:", round((status >= 500).float().mean().item(), 3))
print("mean latency:", round(latency_ms.mean().item(), 1), "ms   <- pulled up by two slow requests")
q = torch.quantile(latency_ms, torch.tensor([0.5, 0.95]))
print("p50, p95:", [round(v, 1) for v in q.tolist()], "ms")
print("GPU use:", round(gpu_util.mean().item(), 3))

@@ concept
title: PSI: how much the input has changed
--- body
**Drift**: the distribution of live data slowly moves away from the training data. Say the average user age was 35 in training, and after a marketing campaign a big group of 20-year-olds signs up. The model has never seen data like this, so its predictions may get worse, while the service itself reports no error at all.

PSI (Population Stability Index) is the most common drift metric. Credit-risk teams have used it for decades. You compute it for one feature (one input column) at a time:

1. **Take the bin edges from the training data**: the 10%, 20%, ..., 90% quantiles of the training values, 9 edges in total, which cut the line into 10 bins. Each bin then holds exactly 10% of the training data.
2. Count: the share of training data in each bin (e, "expected") and the share of live data in each bin (a, "actual").
3. PSI = Σ (a − e) × ln(a / e), summed over the 10 bins. When both sides match, every term is 0; the bigger the difference, the bigger the PSI.

Details that matter:

- The edges must **come from the training data only**, and are saved together with the model. Live data is counted with the same edges. If you bin live data with its own quantiles, every bin always holds 10% and PSI is always close to 0 (one of today's fix exercises is exactly this bug).
- Live values outside the training range still count, in the outermost bins. `torch.bucketize(x, edges)` does exactly that: anything below the first edge goes to bin 0, anything above the last edge goes to bin 9.
- `torch.bincount(idx, minlength=10)` counts how many values fall in each bin. Always pass minlength: otherwise the result gets shorter when the last bins are empty.
- If a bin gets no live data at all, a = 0 and ln(0) is minus infinity. So clip the shares to a tiny number first: `clamp_min(1e-4)`.
- Common rules of thumb: PSI < 0.1 means almost no change; 0.1 to 0.25 means some change, keep an eye on it; > 0.25 means a big change, find out why.
--- code
torch.manual_seed(0)
train = torch.randn(5000)                                          # one feature at training time
edges = torch.quantile(train, torch.linspace(0, 1, 11))[1:-1]      # 9 edges -> 10 bins
print("edges:", [round(v, 2) for v in edges.tolist()])

def shares(x):
    return torch.bincount(torch.bucketize(x, edges), minlength=10) / len(x)

e = shares(train).clamp_min(1e-4)
print("training share per bin:", [round(v, 3) for v in e.tolist()])

for name, live in [("no change", torch.randn(2000)),
                   ("mean +0.3", torch.randn(2000) + 0.3),
                   ("mean +1.0", torch.randn(2000) + 1.0)]:
    a = shares(live).clamp_min(1e-4)
    psi = ((a - e) * torch.log(a / e)).sum().item()
    print(f"{name:9s} PSI = {psi:.3f}")

@@ concept
title: The KS statistic: the biggest gap between two curves
--- body
PSI needs bins first, and the choice of bins changes the result. The KS statistic (Kolmogorov–Smirnov) needs no bins.

First meet the **empirical cumulative distribution** (ECDF): F(x) = the share of values that are ≤ x. For the data [1, 2, 3, 4]: F(0) = 0, F(2) = 2/4 = 0.5, F(10) = 1. As x moves from small to large, F climbs step by step from 0 to 1. Drawn out, it looks like a staircase.

Each of two datasets has its own staircase. **The KS statistic is the largest vertical distance between the two staircases**:

- 0 means the two distributions are identical; 1 means they are completely apart (every value of one is smaller than every value of the other).
- The largest distance always sits at one of the data points. So it is enough to evaluate both curves at "all values of both datasets put together".

To compute F in PyTorch: sort with `torch.sort`, then call `torch.searchsorted(sorted_a, points, right=True)`. It returns how many values of a are ≤ each point (right=True counts equal values too). Divide by len(a) and you have F(points).

PSI or KS? Both are common. PSI comes with thresholds the industry already uses. KS needs no bins and always lies between 0 and 1, which makes it easy to read. scipy's `ks_2samp` also gives a p-value, but with the huge sample sizes of live traffic even a tiny difference is "significant", so monitoring usually puts a threshold on the KS value itself. Today you write it yourself, without scipy.
--- code
a = torch.tensor([1., 2., 3., 4.])
b = torch.tensor([3., 4., 5., 6.])
points = torch.cat([a, b]).sort().values          # sorted only to make the printout readable
Fa = torch.searchsorted(a, points, right=True) / len(a)     # a and b are already sorted
Fb = torch.searchsorted(b, points, right=True) / len(b)
print("x   :", points.tolist())
print("F_a :", Fa.tolist())
print("F_b :", Fb.tolist())
print("KS  :", (Fa - Fb).abs().max().item())

torch.manual_seed(0)
train = torch.randn(3000).sort().values
live = (torch.randn(1000) + 0.5).sort().values
pts = torch.cat([train, live])
d = (torch.searchsorted(train, pts, right=True) / len(train)
     - torch.searchsorted(live, pts, right=True) / len(live)).abs().max()
print("KS when the mean moves by 0.5:", round(d.item(), 3))

@@ concept
title: Prediction drift: watch the outputs before labels arrive
--- body
The most direct way to monitor a model is to compute its accuracy on live traffic. But true labels often take a long time: you learn whether a loan defaults months later, and about fraud only when the customer complains. By the time the labels are in, the damage is done.

**Prediction drift**: ignore the labels and ask whether the distribution of the model's **outputs** has changed. You know every prediction the moment it is made, so this works in real time.

- Classifiers: the share of predictions for each class. In the first week after launch 2% of payments were predicted "fraud"; today it is 9%. Either there really is more fraud, or the inputs changed and the model has started guessing. Both are worth a person's attention.
- You can also check whether the mean confidence (the average of the largest softmax value) has dropped.

The classes are already "bins", so no binning is needed:

- Shares: `torch.bincount(pred, minlength=num_classes) / len(pred)`. Always pass minlength: if a class never appears today, bincount returns a shorter result that no longer lines up with the training shares.
- Then use the PSI formula: Σ (a − e) × ln(a / e), again after `clamp_min(eps)`.

Input drift and prediction drift complement each other. The inputs can change without the predictions changing (the model may not care about that feature). When the predictions change, it is always worth a look.
--- code
ref_pred = torch.repeat_interleave(torch.arange(3), torch.tensor([700, 250, 50]))    # predictions in the first week
live_pred = torch.repeat_interleave(torch.arange(3), torch.tensor([450, 250, 300]))  # predictions today
print("start of ref_pred:", ref_pred[:5].tolist(), " length", len(ref_pred))

e = torch.bincount(ref_pred, minlength=3) / len(ref_pred)
a = torch.bincount(live_pred, minlength=3) / len(live_pred)
print("first week:", [round(v, 3) for v in e.tolist()])
print("today:     ", [round(v, 3) for v in a.tolist()])
a, e = a.clamp_min(1e-4), e.clamp_min(1e-4)
print("PSI of the predictions:", round(((a - e) * torch.log(a / e)).sum().item(), 3))

only_0_and_1 = torch.tensor([0, 1, 1, 0])
print("without minlength:", torch.bincount(only_0_and_1).tolist())
print("with minlength:   ", torch.bincount(only_0_and_1, minlength=3).tolist())

@@ concept
title: Alert rules: a rolling window plus a minimum count
--- body
An alert has two jobs: fire **fast** when something is wrong, and stay **quiet** when nothing is. After being woken up a few times at night for nothing, people start to ignore alerts.

**Rolling window**: look only at the requests of the last stretch of time (say, the last 5 minutes).

- The error rate "since launch" does not work. The service has run for a week at 0.5% errors; for the last 5 minutes it has been at 30%, and the all-time rate only moves from 0.5% to about 0.51%. Nobody notices.
- A window that is too short makes the number jump around; one that is too long fires long after the trouble started. A few minutes is a common choice.

**Minimum count**: with too few requests in the window, the error rate means nothing. At 3 a.m. there may be only 2 requests in a minute; 1 fails, the error rate is 50%, and it is probably just one user sending bad data. So the rule is: fire only when **count ≥ min_count and error rate > threshold**.

Implementation: keep (time, is_error) pairs in time order in a `collections.deque` (a queue that is fast to add to and remove from at both ends). New requests `append` on the right. On every check, first `popleft` the old ones on the left (time ≤ now − window_s); what remains is the window. Dropping old requests has a second benefit: after months of running, memory has not grown.

Real systems (for example Prometheus alert rules) often add "above the threshold for N minutes in a row" and "after firing, stay quiet for a while". Same idea.
--- code
from collections import deque

window_s, threshold, min_count = 60, 0.05, 20
events = deque()                                        # (t in seconds, is it an error), oldest on the left

def check(now):
    while events and events[0][0] <= now - window_s:   # too old: drop from the left
        events.popleft()
    n = len(events)
    errors = sum(1 for _, is_error in events if is_error)
    rate = errors / n if n else 0.0
    return n, round(rate, 3), n >= min_count and rate > threshold

events.extend([(3, True), (41, False)])                 # night: only 2 requests in one minute
print("3 a.m. (count, error rate, alert):", check(now=50))

for t in range(100, 160):                               # daytime: 1 request per second, every 5th one fails
    events.append((t, t % 5 == 0))
print("daytime incident (count, error rate, alert):", check(now=160))
print("left in the deque:", len(events), "requests (the 2 from the night are gone)")

@@ concept
title: Shadow traffic: the new model rides along
--- body
A new model that wins on the offline test set does not always win in production. Live data, live traffic and all the odd inputs are not necessarily in your test set.

**Shadow traffic** (also "shadow mode"): every live request is also sent to the new model (the shadow), but **the user always gets the old model's (prod's) answer**. The shadow's answers are only recorded and compared with prod's.

- Zero risk for users: if the shadow is wrong, slow or crashes, nobody notices.
- You get numbers from real traffic: the **disagreement rate** (the share of rows where the two models predict differently), plus the shadow's latency and error count.
- A high disagreement rate is not automatically bad (maybe the new model fixes mistakes). But it tells you how many users' results will change when you switch, and you can pull out the rows where they disagree for a person to review.

Two iron rules:

1. If the shadow fails, catch it with `try/except`, record it, and return prod's answer as usual. A user must **never** see an error because of the shadow.
2. If prod itself fails, the error must go out as usual (that is normal error handling). The shadow's try/except must not swallow it by accident. So the try wraps only the shadow's line.

In real systems the shadow usually runs asynchronously, in a background thread or a separate service, so it does not slow down the response either. To keep today's exercise simple, it is called synchronously.
--- code
torch.manual_seed(0)
prod = nn.Linear(4, 3)
shadow = nn.Linear(4, 3)
shadow.load_state_dict(prod.state_dict())
with torch.no_grad():
    shadow.weight.add_(0.05 * torch.randn(3, 4))     # the "new model": slightly different from prod

x = torch.randn(1000, 4)                             # 1000 live requests
with torch.inference_mode():
    p = prod(x).argmax(dim=-1)                       # what the user gets
    s = shadow(x).argmax(dim=-1)                     # only recorded
print("rows where they disagree:", int((p != s).sum()))
print("disagreement rate:", round((p != s).float().mean().item(), 3))

def broken(x):
    raise RuntimeError("CUDA out of memory (simulated)")

try:
    broken(x)
except Exception as e:
    print("shadow failed, recorded:", type(e).__name__, "-> the user still gets prod's answer, shape", tuple(p.shape))

@@ concept
title: Canary and A/B: no decision without enough samples
--- body
**Canary release**: the new version first gets only a small slice of real traffic (say 5%); the rest still goes to the old version (the baseline). You compare the error rate and latency of both. If all is well, you raise the slice step by step to 100%; if not, you roll back. The name comes from the canary that miners took into the mine: it got into trouble first, so the people had time to get out.

**A/B testing** looks similar but has a different goal: each version gets part of the users for a period fixed in advance, and you compare a business metric (click rate, conversion rate) to decide which version is better.

Both run into the same problem: **with too few samples, a difference may be pure luck.** For a service whose true error rate is p, the error rate you measure on n requests wobbles up and down. The size of that wobble is the **standard error** (SE):

SE = sqrt(p × (1 − p) / n)

With p = 2% and n = 50, SE ≈ 2 percentage points: a model whose true error rate is 2% can easily look like 4%. With 100 times more requests, SE only shrinks to 1/10 (because of the square root).

So the decision rule has three outcomes:

1. Either side has fewer than min_n requests (fixed in advance): **wait**. Keep collecting; do not decide.
2. The canary's error rate is higher than the baseline's by more than z standard errors (z = 2 is common): **rollback**. The combined standard error of both sides is se = sqrt(p_b(1 − p_b)/n_b + p_c(1 − p_c)/n_c), where b is the baseline and c the canary.
3. Otherwise: **promote** (give it more traffic).

The code below simulates 2000 canaries where the new and the old model are **exactly the same**, both with a true error rate of 2%. Each time we look at only n requests. How often does the canary "look" like it has 4% errors or more?
--- code
torch.manual_seed(0)
p = 0.02
for n in [50, 500, 5000]:
    errors = torch.binomial(torch.full((2000,), float(n)), torch.full((2000,), p))  # failures in each of 2000 canaries
    looks_bad = (errors / n >= 0.04).float().mean().item()
    se = math.sqrt(p * (1 - p) / n)
    print(f"n={n:5d}  SE={se:.4f}  share that looks >= 4%: {looks_bad:.3f}")

@@ concept
title: What 1,000 requests cost
--- body
Your manager will ask: "What does this model cost per month? Is it worth it?" An engineer should be able to work out the **cost per 1,000 requests**.

You pay for a GPU by the hour, busy or not. So:

- requests actually handled per hour = throughput at full load (per second) × 3600 × average utilization
- cost per request = GPU price per hour ÷ requests handled per hour
- cost per 1,000 requests = cost per request × 1000

Two levers:

- **Throughput**: batching (day 22) and int8 / fp16 (day 21) let the same GPU handle more requests per second, and the cost drops in proportion.
- **Utilization**: traffic is high in the day and low at night. A GPU sized for the peak sits mostly idle at night, and you still pay for it. At 25% average utilization, the cost is 4 times the full-load cost. Autoscaling (adding and removing machines as traffic changes) exists to raise utilization.

Generative models often talk about "cost per 1,000 tokens". The arithmetic is the same, with tokens instead of requests.

The price below is made up, just to show the calculation.
--- code
price = 2.00                                         # assumed: one GPU costs 2 dollars per hour
for name, rps, util in [("batch=1,  100% utilization", 40, 1.0),
                        ("batch=1,  25% utilization", 40, 0.25),
                        ("batch=16, 25% utilization", 400, 0.25)]:
    per_hour = rps * 3600 * util                     # requests actually handled per hour
    cost = price / per_hour * 1000
    print(f"{name}   per 1,000 requests ${cost:.4f}")

--- context
Every number on a monitoring dashboard is computed from request logs, one line per request. Compute a few yourself and you will see why a number like "mean latency 125 ms" can mislead.
--- prompt
10 requests arrived within 5 seconds. Write the 4 lines this code prints.
--- code
latency_ms = [12, 15, 11, 240, 14, 13, 16, 12, 15, 900]
status = [200, 200, 200, 500, 200, 200, 200, 200, 200, 504]
seconds = 5

print(len(latency_ms) / seconds)                        # throughput, req/s
print(sum(s >= 500 for s in status) / len(status))      # error rate
print(sum(latency_ms) / len(latency_ms))                # mean latency
print(sorted(latency_ms)[len(latency_ms) // 2])         # the middle one after sorting
--- explain
Throughput: 10 / 5 = 2.0. Two status codes are ≥ 500: 500 (server error) and 504 (timeout), so the error rate is 2 / 10 = 0.2. The latencies add up to 1248, so the mean is 124.8 ms. Sorted, they are [11, 12, 12, 13, 14, 15, 15, 16, 240, 900]; counting from 0, position 10 // 2 = 5 holds 15.

The mean of 124.8 ms describes no request at all: 8 requests took 16 ms or less, and the other 2 took far longer. That is why dashboards show percentiles (day 22's p50 / p95 / p99) and not just the mean.
--- hints
- How many status codes are ≥ 500? 504 counts too.
- `sorted(...)[5]`: sort first, then count from 0 up to position 5.

@@ item d25-02
type: choice
title: Reading a latency dashboard
level: 2
cards: The numbers to watch after launch
--- context
During an incident, the person on call often has a few minutes to read the dashboard and decide. If you can read the cause from the combination of curves, you do not waste time on the wrong fix, such as rolling back a model that is fine.
--- prompt
The dashboard from 8 p.m. onwards:

- Incoming requests: 200 per second → 320 per second
- Finished requests: stuck at about 250 per second
- p50 latency: 25 ms → 160 ms; p99 latency: 80 ms → 2000 ms
- Error rate: 0.1% → 4%; almost all new errors are 504 (timeout; the service's timeout is 2 seconds)
- GPU use: 100%; queued requests: still growing

What is the most likely cause, and the first thing to do?
--- options
- The new model's outputs got worse: roll back to the previous version right away
- Not enough capacity: more requests come in than can be handled, so they wait longer and longer in the queue, and the ones that wait longest time out. Add capacity (more replicas) or rate-limit first
- The input data drifted: the model sees data it has never seen, so it computes more slowly
- Network jitter: p50 is slower too, so it is the network; wait for it to recover
answer: 2
--- explain
The key is two numbers that do not match: 320 requests come in per second but only 250 get handled, so 70 more join the queue every second and the queue can only grow. The GPU is at 100%, so it cannot compute any faster. The waiting time is added to every request, so both p50 and p99 get slower, and the requests that wait the longest hit the 2-second limit and become 504s.

Almost all new errors are timeouts, not 500s, so the model itself has not crashed. Rolling back would not help: the old model cannot keep up either. The first step is to add replicas, or to rate-limit (answer the extra requests right away with 429 "too busy" instead of letting everyone wait until they time out). Drift can make predictions worse, but it does not usually make the same model compute more slowly.
--- hints
- Compare "incoming" with "finished": how many per second is the difference? Where do those requests go?
- The new errors are 504, not 500: did the model fail, or did requests wait too long?

def psi(ref, live, bins=10, eps=1e-4):
    edges = torch.quantile(ref, torch.linspace(0, 1, bins + 1))[1:-1]     # edges from the training data only
    e = torch.bincount(torch.bucketize(ref, edges), minlength=bins) / len(ref)
    a = torch.bincount(torch.bucketize(live, edges), minlength=bins) / len(live)
    e, a = e.clamp_min(eps), a.clamp_min(eps)                            # an empty bin does not become log(0)
    return float(((a - e) * torch.log(a / e)).sum())

def ks_statistic(a, b):
    a = torch.sort(a).values                   # searchsorted needs sorted input
    b = torch.sort(b).values
    points = torch.cat([a, b])                 # the largest gap always sits at a data point
    cdf_a = torch.searchsorted(a, points, right=True) / len(a)    # share of a that is <= each point
    cdf_b = torch.searchsorted(b, points, right=True) / len(b)
    return float((cdf_a - cdf_b).abs().max())

from collections import deque

class ErrorRateAlert:
    def __init__(self, window_s=300, threshold=0.05, min_count=50):
        self.window_s = window_s
        self.threshold = threshold
        self.min_count = min_count
        self.events = deque()

    def record(self, t, is_error):
        self.events.append((t, bool(is_error)))

    def firing(self, now):
        while self.events and self.events[0][0] <= now - self.window_s:   # outside the window: drop from the left
            self.events.popleft()
        n = len(self.events)
        if n == 0 or n < self.min_count:                                 # too few samples: no verdict
            return False
        errors = sum(1 for _, is_error in self.events if is_error)
        return errors / n > self.threshold

def serve_with_shadow(x, prod, shadow, stats):
    with torch.inference_mode():
        pred = prod(x).argmax(dim=-1)          # the user's answer comes from prod only; prod errors go out as usual
        try:
            other = shadow(x).argmax(dim=-1)   # the try wraps only the shadow
        except Exception:
            stats["shadow_errors"] += 1        # record it, without affecting the user
        else:
            stats["rows"] += len(x)
            stats["disagree"] += int((pred != other).sum())
    return pred


def disagreement_rate(stats):
    if stats["rows"] == 0:
        return None
    return stats["disagree"] / stats["rows"]

def canary_decision(base_errors, base_n, canary_errors, canary_n, min_n=1000, z=2.0):
    if base_n < min_n or canary_n < min_n:
        return "wait"                                       # not enough samples: no verdict yet
    p_base = base_errors / base_n
    p_canary = canary_errors / canary_n
    se = math.sqrt(p_base * (1 - p_base) / base_n + p_canary * (1 - p_canary) / canary_n)
    if p_canary - p_base > z * se:                          # worse by much more than the noise: really worse
        return "rollback"
    return "promote"

def psi(ref, live, bins=10, eps=1e-4):
    edges = torch.quantile(ref, torch.linspace(0, 1, bins + 1))[1:-1]
    e = torch.bincount(torch.bucketize(ref, edges), minlength=bins) / len(ref)
    a = torch.bincount(torch.bucketize(live, edges), minlength=bins) / len(live)
    e, a = e.clamp_min(eps), a.clamp_min(eps)
    return float(((a - e) * torch.log(a / e)).sum())

from collections import deque

class ErrorRateAlert:
    def __init__(self, window_s=300, threshold=0.05, min_count=50):
        self.window_s = window_s
        self.threshold = threshold
        self.min_count = min_count
        self.events = deque()

    def record(self, t, is_error):
        self.events.append((t, bool(is_error)))

    def firing(self, now):
        while self.events and self.events[0][0] <= now - self.window_s:
            self.events.popleft()
        n = len(self.events)
        if n == 0 or n < self.min_count:
            return False
        errors = sum(1 for _, is_error in self.events if is_error)
        return errors / n > self.threshold
