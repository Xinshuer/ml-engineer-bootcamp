@@ concept
title: LoRA: keep W, add a small side path
--- body
Fine-tuning means taking a model someone else trained and training it a bit more on your own data. Full fine-tuning updates every parameter. A 7B model has 7 billion parameters, and fully fine-tuning it needs far more memory than a normal GPU has (the last card, "The memory bill", does the math).

LoRA (Low-Rank Adaptation) leaves the original weight `W` (shape `(out, in)`) untouched and adds a small side path next to it:

```
y = base(x) + (x @ A.T @ B.T) * scaling
```

- `A` has shape `(r, in)` and `B` has shape `(out, r)`.
- `r` is the rank. It is small: 4, 8 and 16 are common.
- `x @ A.T` squeezes x down to r numbers; `@ B.T` expands it back to out numbers. So the side path has the same shape as `base(x)`, and the two can be added.
- `B @ A` has shape `(out, in)`, as big as `W`, but it is built from only `r*in + out*r` numbers.

The code below does the math for a 4096×4096 layer: the original weight has 16,777,216 parameters; with r = 8, A and B together have only 65,536, which is 0.39%.
--- code
in_f, out_f, r = 4096, 4096, 8
full = in_f * out_f
lora = r * in_f + out_f * r
print("original weight parameters:", full)
print("A + B parameters:", lora)
print(f"ratio: {lora / full:.2%}")

# look at the shapes with small sizes
x = torch.randn(2, 16)     # 2 samples, in = 16
A = torch.randn(4, 16)     # (r, in)
B = torch.randn(8, 4)      # (out, r)
print("x @ A.T:", tuple((x @ A.T).shape))
print("x @ A.T @ B.T:", tuple((x @ A.T @ B.T).shape))

@@ concept
title: Three LoRA details: freeze, B = 0, alpha / r
--- body
Whether you write LoRA code or read someone else's, check these three things first. Getting any of them wrong raises no error; fine-tuning just works worse.

1. **Freeze the base**: `for p in base.parameters(): p.requires_grad_(False)`. A parameter with `requires_grad=False` still has `.grad == None` after backward, and the optimizer does not change it. Only A and B train. To check: count the trainable parameters. They should be exactly the size of A plus B.
2. **B starts at all zeros, A starts with small random numbers** (for example `normal_(0, 0.01)`). At the start `B @ A` is all zeros, the side path outputs 0, and the model gives exactly the same outputs as the original. Fine-tuning starts from the original model, not from "the original model plus random noise".
3. **scaling = alpha / r**: alpha is a hyperparameter (often 1 to 2 times r). Dividing by r means that when you change r, the size of the side path's output barely changes, so you do not have to re-tune the learning rate. With alpha = 8 and r = 4, scaling = 2.0.

New matrices must be wrapped in `nn.Parameter`. Only then does the module count them in `parameters()`, and only then does the optimizer update them.

The code also shows how the gradients flow at the first step: B gets a gradient (B's gradient is multiplied by `x @ A.T`, and A is not zero); A's gradient is zero (it is multiplied by B, and B is zero). After one update B is no longer zero, and then A gets gradients too.
--- code
torch.manual_seed(0)
base = nn.Linear(16, 8)
for p in base.parameters():
    p.requires_grad_(False)                      # 1) freeze the base
A = nn.Parameter(torch.randn(4, 16) * 0.01)      # 2) A: small random numbers
B = nn.Parameter(torch.zeros(8, 4))              #    B: all zeros
scaling = 8 / 4                                  # 3) alpha / r

x = torch.randn(3, 16)
y = base(x) + (x @ A.T @ B.T) * scaling
print("same output as the original model:", torch.allclose(y, base(x)))

y.sum().backward()
print("base.weight.grad:", base.weight.grad)
print("B has a gradient:", bool(B.grad.abs().sum() > 0))
print("A has a gradient:", bool(A.grad.abs().sum() > 0))

@@ concept
title: Merging LoRA: no extra cost at inference
--- body
After training, A and B no longer change. If you keep the side path in production, every layer does two extra matrix multiplications. You can instead "merge" the side path into the original weight.

You can move the brackets in a chain of matrix products, and `A.T @ B.T == (B @ A).T`, so:

```
x @ A.T @ B.T * s  ==  x @ (s * B @ A).T
```

Therefore:

```
W_merged = W + s * (B @ A)     # shape (out, in), same as W
the bias stays the same
```

The merged layer is a plain `nn.Linear`: the same number of parameters and the same speed as the original model. Mind the order: it is `B @ A`; `A @ B` has the wrong shape.

To write values into the parameters of an `nn.Linear`, use `.copy_()` inside `with torch.no_grad():`. Without it you get an error: a parameter that requires grad cannot be changed in place.
--- code
torch.manual_seed(0)
W = torch.randn(8, 16)
A, B, s = torch.randn(4, 16), torch.randn(8, 4), 2.0
x = torch.randn(3, 16)

two_paths = x @ W.T + (x @ A.T @ B.T) * s        # original weight + side path
W_merged = W + s * (B @ A)
print("shape of B @ A:", tuple((B @ A).shape))

lin = nn.Linear(16, 8, bias=False)
with torch.no_grad():
    lin.weight.copy_(W_merged)
print("same output after merging:", torch.allclose(lin(x), two_paths, atol=1e-4))
print("parameters after merging:", sum(p.numel() for p in lin.parameters()))

@@ concept
title: SFT labels: -100 means no loss
--- body
SFT (Supervised Fine-Tuning) trains a model on "question + good answer" pairs. One sample is the prompt's tokens followed by the answer's tokens, joined into one `input_ids`.

We want the model to learn to write the answer, not to repeat the question. So we build `labels` as long as `input_ids`: -100 over the prompt, a copy of `input_ids` over the answer.

- `F.cross_entropy` has an argument `ignore_index`, and its default is -100. A position whose label is -100 adds nothing to the loss, **and is not counted in the average's denominator**.
- labels must be `torch.long` (integers).
- "Token t predicts token t+1" needs a shift by one. Hugging Face language models do this shift inside their loss code, so you write labels aligned with input_ids.
- If you get it wrong (forget the mask, or mask the answer too), the code still runs and the loss still goes down, but the model learns the wrong thing. The only way to catch it is to print the labels.

Below, logits are the model's raw scores for every word (before softmax). The two losses should be the same.
--- code
torch.manual_seed(0)
input_ids = torch.tensor([11, 12, 13, 21, 22])   # first 3 are the prompt, last 2 the answer
labels = input_ids.clone()
labels[:3] = -100
print("labels:", labels.tolist())

logits = torch.randn(5, 30)                       # 5 positions, a score for each of 30 words
masked = F.cross_entropy(logits, labels)          # positions with -100 are skipped
answer_only = F.cross_entropy(logits[3:], input_ids[3:])
print("loss with -100:", round(masked.item(), 4))
print("loss of the answer only:", round(answer_only.item(), 4))

@@ concept
title: Chat templates: turning a conversation into text
--- body
A chat model was not trained on Python lists. It was trained on text with special markers. The rule that turns a `messages` list into that text is called the chat template. Each model family has its own. Fine-tuning and inference must both use the template the model was trained with; one missing newline can make the model answer nonsense.

Many models, Qwen among them, use the ChatML format. Each message becomes:

```
<|im_start|>{role}\n{content}<|im_end|>\n
```

- `<|im_start|>` and `<|im_end|>` are special tokens that mark where a message starts and ends.
- role is `system` (the setup instructions), `user` or `assistant` (the model).
- At inference time you append `<|im_start|>assistant\n` (the argument `add_generation_prompt=True`). It means "your turn". The model continues from there and stops when it writes `<|im_end|>`.
- For SFT you do not add it, because the assistant's answer is already in the data. The `prompt_len` of the previous card is the number of tokens before the text of the assistant's answer (including `<|im_start|>assistant\n`).

Printing a string with `repr()` shows the newline characters `\n`.
--- code
m = {"role": "user", "content": "1+1=?"}
one = f"<|im_start|>{m['role']}\n{m['content']}<|im_end|>\n"
print(one)
print(repr(one))
print(repr("<|im_start|>assistant\n"))

@@ concept
title: Gradient accumulation: small batches add up to a big one
--- body
Your GPU fits 8 samples at a time, but you want the effect of batch = 32? Feed 8 at a time, do forward + backward 4 times, and only then update the parameters. This is gradient accumulation.

It works because `.backward()` **adds** the gradient to `.grad` instead of overwriting it. That is why a normal training step starts with `zero_grad()`, and why gradient accumulation deliberately waits a few steps before clearing.

One trap: `F.cross_entropy` takes the **mean** over the batch by default. Adding up the means of 4 chunks gives 4 times the mean of the big batch. So divide each chunk's loss by the number of chunks `n_micro`:

```
model.zero_grad()
for each chunk (xb, yb):
    loss = F.cross_entropy(model(xb), yb) / n_micro
    loss.backward()          # the gradient is added to .grad
optimizer.step()             # one update after all the chunks
```

If you forget to divide, nothing crashes; the gradient is just n_micro times too big. With SGD that secretly multiplies the learning rate by n_micro, and gradient clipping and the printed loss are off too.
--- code
torch.manual_seed(0)
model = nn.Linear(3, 2)
xs, ys = torch.randn(8, 3), torch.randint(0, 2, (8,))

model.zero_grad()
F.cross_entropy(model(xs), ys).backward()           # all 8 at once
big = model.weight.grad.clone()

model.zero_grad()
F.cross_entropy(model(xs[:4]), ys[:4]).backward()   # first 4
F.cross_entropy(model(xs[4:]), ys[4:]).backward()   # last 4: the gradient is added
print("plain sum == big batch?", torch.allclose(model.weight.grad, big))
print("sum / 2 == big batch?", torch.allclose(model.weight.grad / 2, big))

@@ concept
title: Warmup + cosine: the learning rate goes up, then down
--- body
The learning rate (lr) does not stay the same for the whole run. The most common plan for training large models has three parts:

1. **Warmup**: over the first `warmup_iters` steps, the lr rises in a straight line from very small to `max_lr`. At the start the model and Adam's running statistics are unstable, and a big lr right away can blow up the training.
2. **Cosine decay**: then the lr falls along a cosine curve from `max_lr` to `min_lr`.
3. After `max_iters`, it stays at `min_lr`.

The formulas (`it` is the step number, starting at 0):

```
warmup:  lr = max_lr * (it + 1) / warmup_iters
cosine:  progress = (it - warmup_iters) / (max_iters - warmup_iters)   # 0 → 1
         coeff = 0.5 * (1 + cos(pi * progress))                        # 1 → 0
         lr = min_lr + coeff * (max_lr - min_lr)
```

Why `it + 1`: then step 0 does not have lr = 0 (a step with lr 0 is wasted), and the last warmup step, `it = warmup_iters - 1`, lands exactly on `max_lr`. At progress = 0.5 (the middle of the cosine part), coeff = 0.5, so the lr is exactly the average of max_lr and min_lr.
--- code
for progress in [0, 0.25, 0.5, 0.75, 1.0]:
    coeff = 0.5 * (1 + math.cos(math.pi * progress))
    print("progress", progress, "-> coeff", round(coeff, 3))

@@ concept
title: The memory bill: weights, gradients, optimizer states
--- body
During training, GPU memory holds four main things:

1. The parameters (weights)
2. The gradients: one per parameter
3. The optimizer states: AdamW keeps 2 numbers per parameter (`exp_avg`, the first moment, and `exp_avg_sq`, the second moment); SGD with momentum keeps 1; plain SGD keeps none
4. The activations: intermediate results of the forward pass that backward needs. They depend on the batch size and sequence length; we leave them out today

The first three depend only on the number of parameters, so you can compute them directly. In fp32 each number takes 4 bytes. AdamW stores "parameter + gradient + 2 states" = 4 copies, so 16 bytes per parameter (here 1 GB = 10^9 bytes):

- 1 billion (1B) parameters → 16 GB
- 7 billion (7B) parameters → 112 GB, more than one 80 GB GPU holds, before any activations

Where LoRA saves: the frozen base has no gradients and no optimizer states, only the parameters themselves. Gradients and optimizer states are kept only for A and B, which are less than 1% of the parameters.

In the code below, `step` is just a counter and takes almost no space; `exp_avg` and `exp_avg_sq` are each as big as the weight.
--- code
model = nn.Linear(100, 10)                       # 100*10 + 10 = 1010 parameters
opt = torch.optim.AdamW(model.parameters(), lr=1e-3)
model(torch.randn(4, 100)).sum().backward()
opt.step()                                       # the states are created at the first step

state = opt.state[model.weight]
print({k: tuple(v.shape) for k, v in state.items()})
n = sum(p.numel() for p in model.parameters())
print("parameters:", n)
print("parameters + gradients + 2 states:", n * 4 * 4, "bytes")
print("7B model:", 7_000_000_000 * 4 * 4 / 1e9, "GB")

--- prompt
Write `LoRALinear(base, r=4, alpha=8)`. It wraps an already-trained `nn.Linear` and adds a low-rank side path next to it.

In `__init__`:
- `self.base = base`, and freeze **all** of base's parameters (`requires_grad_(False)`)
- `self.A`: an `nn.Parameter` of shape `(r, in_features)`, initialised with `normal_(0, 0.01)`
- `self.B`: an `nn.Parameter` of shape `(out_features, r)`, **all zeros**
- `self.scaling = alpha / r`

`forward(x)`: return `base(x) + (x @ A.T @ B.T) * scaling`. x can have shape `(N, in)` or `(B, T, in)`.

You can read `in_features` and `out_features` from `base.in_features` and `base.out_features`.
--- starter

    def __init__(self, base: nn.Linear, r=4, alpha=8):
        super().__init__()
        # 1) keep base and freeze all its parameters
        # 2) A: (r, in_features), normal_(0, 0.01); B: (out_features, r), all zeros
        # 3) scaling = alpha / r
        raise todo()

    def forward(self, x):
        raise todo()
--- solution
class LoRALinear(nn.Module):
    def __init__(self, base: nn.Linear, r=4, alpha=8):
        super().__init__()
        self.base = base
        for p in self.base.parameters():
            p.requires_grad_(False)
        self.A = nn.Parameter(torch.empty(r, base.in_features).normal_(0, 0.01))
        self.B = nn.Parameter(torch.zeros(base.out_features, r))   # must be zeros
        self.scaling = alpha / r

    def forward(self, x):
        return self.base(x) + (x @ self.A.T @ self.B.T) * self.scaling

title: Merge the LoRA weights
level: 2

ref: day6
--- context
A trained LoRA is usually merged into the original weights before it goes to production (PEFT calls this merge_and_unload). The result is a plain Linear: inference is as fast as the original model, and the deployment does not need any LoRA code.
--- prompt
Write `merge_lora(m)`. It takes a trained `LoRALinear` (the class is already defined for you) and returns a **new** `nn.Linear` with:
- `weight = m.base.weight + m.scaling * (m.B @ m.A)`
- the same bias as `m.base.bias` (if base has no bias, the new layer has none either)
- the same output as `m(x)` for the same input (within 1e-5)
- only weight and bias; no A and B

Write values into the parameters with `.copy_(...)` inside `with torch.no_grad():`.
--- starter
def merge_lora(m: LoRALinear) -> nn.Linear:
    """Merge the LoRA back into a plain nn.Linear: W' = W + scaling * B @ A, bias unchanged."""
    raise todo()
--- solution
def merge_lora(m):
    out_f, in_f = m.base.out_features, m.base.in_features
    lin = nn.Linear(in_f, out_f, bias=m.base.bias is not None)
    with torch.no_grad():
        lin.weight.copy_(m.base.weight + m.scaling * (m.B @ m.A))
        if m.base.bias is not None:
            lin.bias.copy_(m.base.bias)
    return lin
--- tests
@check("Merge the LoRA weights")
def t04():
    seed(2)
    m = LoRALinear(nn.Linear(16, 8), r=4, alpha=8)
    with torch.no_grad():                      # a non-zero B, as if it had been trained
        m.B.normal_(0, 0.5)
    x = torch.randn(3, 16)
    merged = merge_lora(m)
    true(isinstance(merged, nn.Linear), "return a plain nn.Linear")
    eq(merged(x), m(x), tol=1e-5, msg="the output changed after merging: check the order of B @ A, the scaling and the bias")
    true(params(merged) == 16 * 8 + 8, "the merged layer should have only weight and bias, not A and B")
--- hints
- Start with a layer of the same size: `nn.Linear(m.base.in_features, m.base.out_features, bias=m.base.bias is not None)`.
- Check the shapes: `B` is `(out, r)`, `A` is `(r, in)`, so `B @ A` is `(out, in)`, the same as weight.

def lora_ratio(in_f, out_f, r):
    """Return LoRA's parameter count / the original weight's parameter count (no bias)."""

def lora_ratio(in_f, out_f, r):

--- prompt

- Clear the old gradients first. Then cut the big batch, in order, into `n_micro` equal chunks (each one is a micro-batch). For each chunk: forward, `F.cross_entropy`, backward.
- The accumulated gradients must equal the gradients of feeding all N samples at once (within 1e-5).

--- starter
def grad_accum_step(model, xs, ys, n_micro):
    """Cut the big batch into n_micro chunks and run forward/backward on each, so the accumulated
    gradients equal those of the big batch. Return {parameter name: grad.clone()}."""
    raise todo()
--- solution
def grad_accum_step(model, xs, ys, n_micro):
    model.zero_grad(set_to_none=True)
    n = xs.size(0) // n_micro
    for i in range(n_micro):
        xb, yb = xs[i * n:(i + 1) * n], ys[i * n:(i + 1) * n]
        # each chunk's loss is already a mean over the chunk; dividing by the number of chunks gives the overall mean
        (F.cross_entropy(model(xb), yb) / n_micro).backward()
    return {k: p.grad.clone() for k, p in model.named_parameters()}
