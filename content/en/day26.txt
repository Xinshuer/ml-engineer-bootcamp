title: The capstone: a six-step pipeline
ref: day26
--- body
Today you connect what you have learned into one line: a very small classifier, from making the data all the way to serving and monitoring.

The story: a machine has 8 sensor readings, and the model says whether it is `ok`, `overheat` (running too hot) or `vibration` (shaking). `make_data` builds the data from a fixed seed, so everyone gets exactly the same numbers. The model, `TinyNet`, is already written: `Linear(8, 32)` → ReLU → Dropout(0.1) → `Linear(32, 3)`.

Six steps, each one taken from earlier days:
1. Data + pre-training checks: reproducible data, a smoke test, overfitting one batch (days 14, 15, 16)
2. Training: a fixed seed, a second or two on a CPU, a clear drop in the loss (days 15, 17, 18)
3. Checkpoint: weights in safetensors, plus the optimizer and random-number state, so training can resume (day 20)
4. Export: `torch.onnx.export(..., dynamo=True)`, then compare with onnxruntime (day 21)
5. Service: FastAPI + pydantic validation, load once at start-up, warm up once (day 22)
6. Monitoring: latency p50 / p95 / p99 and a PSI drift check (days 19, 22, 25)

How the items work: each item asks you to write one piece of the pipeline. The item's hidden code contains **reference versions of every step**. The name you write is deleted first and replaced by your version, so the later steps call your code. You can go in order, or jump straight to the step you want to practise.

Item 13 puts the six steps together into one `capstone.py` that you run on your own machine (on the GPU if you have one) and paste back the summary line.

@@ concept
title: Step 1: data, smoke test, overfit
ref: day26
--- body
### Reproducible data
`make_data(n, seed)` draws its random numbers from its own `torch.Generator`. The same seed always gives the same data, and the global random state (the one `torch.manual_seed` sets) is not touched. So making data does not change the order in which training later draws its batches (day 18: reproducibility).

Labels must be `int64` (long); that is what `F.cross_entropy` accepts (day 16).

### Smoke test: one forward + backward before training
- Is the output shape right? It should be `(batch, 3)`.
- Any nan or inf? `torch.isfinite(logits).all()`.
- The first loss should be close to `ln 3 ≈ 1.099`: a freshly initialised model treats the 3 classes about equally (day 15). If it is far off, the scale of the initialisation or of the inputs is usually wrong.
- After backward, every trainable parameter needs a finite `.grad`. `grad is None` means that parameter is not connected to the computation at all (day 15).

### Overfit one batch
Train again and again on just 16 rows. The loss should fall close to 0. If it does not, the code has a bug; do not start tuning hyperparameters yet (day 14).
--- code
x, y = make_data(16, seed=0)
torch.manual_seed(0)
model = TinyNet()
print("first loss:", round(smoke_test(model, x, y), 3), "  ln 3 =", round(math.log(3), 3))
losses = overfit_one_batch(model, x, y, steps=200)
print("overfit 16 rows:", round(losses[0], 3), "->", round(losses[-1], 4))

@@ concept
title: Step 2: a fixed seed, a few seconds of training
ref: day26
--- body
The training loop (several day-15 traps live here):
- Each step draws 64 random rows with `torch.randint(0, len(x), (batch_size,))` → forward → `F.cross_entropy` → `opt.zero_grad()` → `loss.backward()` → `opt.step()`.
- Record `loss.item()`, not `loss` itself: a tensor keeps its whole computation graph in memory (day 19).
- Call `model.train()` first. `accuracy` switches the model to `eval()` (dropout off); if you do not switch back, the rest of training runs without dropout (day 17).
- The caller builds the optimizer and passes it in: when you resume, it is the one read back from the checkpoint.

A fixed seed: call `torch.manual_seed(0)`, then build the model and train, and the same code gives exactly the same losses every time. The "resume == uninterrupted" test in step 3 depends on this (day 18).

The example below takes a second or two on a CPU. The mean loss of the first 20 steps is about 0.75, of the last 20 steps about 0.18, and the validation accuracy is about 0.95. The three classes overlap, so no amount of training reaches 100%.
--- code
torch.manual_seed(0)
x_train, y_train = make_data(2000, seed=1)
x_val, y_val = make_data(500, seed=2)
model = TinyNet()
opt = torch.optim.AdamW(model.parameters(), lr=3e-3)
losses = train_steps(model, opt, x_train, y_train, steps=300)
print(f"mean loss, first 20 steps: {sum(losses[:20]) / 20:.3f}")
print(f"mean loss, last 20 steps:  {sum(losses[-20:]) / 20:.3f}")
print(f"val accuracy: {accuracy(model, x_val, y_val):.3f}")

@@ concept
title: Step 3: a checkpoint you can resume
ref: day26
--- body
Training can be interrupted: a machine restarts, or a cheap preemptible cloud GPU is taken back. A resumable checkpoint must make "save → load → keep training" give exactly the same weights as training in one go (day 20).

Save two files:
- `model.safetensors`: the weights only. Save with `save_file(model.state_dict(), path)`, load with `load_file(path)`. A safetensors file holds only tensors, no executable pickle, so loading someone else's file is safe. The service needs only this one file.
- `train_state.pt`: what only resuming needs: `{"opt": opt.state_dict(), "step": step, "rng": torch.get_rng_state()}`. Load it with `torch.load(path, weights_only=True)`: only tensors, numbers, lists and dicts are allowed, so no code hidden in the file can run.

What goes wrong when one piece is missing:
- No optimizer state: AdamW's two running averages (`exp_avg`, `exp_avg_sq`) start again from 0, so every step after the resume differs.
- No random-number state: the batches drawn after the resume, and the dropout masks, differ from the uninterrupted run.

Neither case raises an error, and the loss still goes down; the result just changes quietly. That is why a test must prove "resume == uninterrupted". Real projects also write to a temporary file first and then `os.replace` it, so a crash half-way through never leaves a broken file (day 20).
--- code
import os, tempfile
from safetensors.torch import load_file
torch.manual_seed(0)
x, y = make_data(2000, seed=1)
model = TinyNet()
opt = torch.optim.AdamW(model.parameters(), lr=3e-3)
train_steps(model, opt, x, y, steps=10)
folder = tempfile.mkdtemp()
save_checkpoint(folder, model, opt, step=10)
for name in sorted(os.listdir(folder)):
    print(name, os.path.getsize(os.path.join(folder, name)), "bytes")
print("weights:", list(load_file(os.path.join(folder, "model.safetensors")).keys()))
state = torch.load(os.path.join(folder, "train_state.pt"), weights_only=True)
print("train_state:", list(state.keys()), "  step =", state["step"])
print("AdamW state of fc1.weight:", list(state["opt"]["state"][0].keys()))

title: Step 4: export to ONNX and compare
ref: day26
--- body
In production you often do not ship the PyTorch training code. You export the model to an ONNX file and run it with onnxruntime (day 21):
```python
model.eval()                                # dropout off: export the inference graph
torch.onnx.export(model, (torch.randn(2, FEATURES),), "tinynet.onnx", dynamo=True,
                  input_names=["x"], output_names=["logits"],
                  dynamic_shapes={"x": {0: "batch"}},   # dimension 0 (the batch) may change
                  external_data=False,                  # weights go into the same file
                  verbose=False)                        # no progress messages
```
- The example input is only used to trace the graph. Its batch is 2; without `dynamic_shapes`, the exported file accepts batch 2 only.
- The keys of `dynamic_shapes` are the argument names of `forward`: the `x` in `TinyNet.forward(self, x)`.
- Without `external_data=False`, the weights go into a second file next to it, `.onnx.data`. Forget to copy it when you deploy, and the model will not load.
- Always compare after exporting: feed the same inputs to onnxruntime and to the model in eval mode, and take the largest absolute difference. In float32 it is usually 1e-6 or less; use a tolerance of 1e-4. Try several batch sizes (1, 5, 64) to prove the batch dimension really is dynamic.

Exporting traces the whole model and takes a few seconds: after you press Run on the example below, wait a moment. The two export items have a 120-second time limit.
--- code
import os, tempfile
import onnxruntime as ort
torch.manual_seed(0)
model = TinyNet()
path = export_onnx(model, os.path.join(tempfile.mkdtemp(), "tinynet.onnx"))
sess = ort.InferenceSession(path, providers=["CPUExecutionProvider"])
print("inputs: ", [(i.name, i.shape) for i in sess.get_inputs()])
print("outputs:", [(o.name, o.shape) for o in sess.get_outputs()])
for b in (1, 5, 64):
    x = torch.randn(b, FEATURES)
    with torch.inference_mode():
        want = model(x).numpy()
    got = sess.run(None, {"x": x.numpy()})[0]
    print(f"batch {b:2d}: max |onnx - torch| = {abs(got - want).max():.1e}")

@@ concept
title: Step 5: a FastAPI service
ref: day26
--- body
The shape of the service (day 22):
- **Load once at start-up**: `create_app(load_model)` calls `load_model()` right away and gets a `predict` function that every request then reuses. Loading the model on every request is the most common reason a service is slow.
- **Warm up once**: after loading, call `predict` once on a row of zeros. The first call is often much slower (memory allocation, initialisation); do not make your first user pay for it.
- `GET /health` returns `{"status": "ok"}`, for load balancers and monitoring.
- `POST /predict` takes `{"rows": [[8 numbers], ...]}`, sends all rows of one request to the model **at once** (one batch), and returns each row's label and its 3 class probabilities.

Input validation is pydantic's job:
```python
Row = Annotated[list[FiniteFloat], Field(min_length=FEATURES, max_length=FEATURES)]

class PredictRequest(BaseModel):
    rows: list[Row] = Field(min_length=1, max_length=MAX_ROWS)
```
- `FiniteFloat`: an ordinary float that rejects nan and inf.
- `Annotated[type, Field(...)]` adds limits to a type; `min_length` / `max_length` limit a list's length: exactly 8 numbers per row, 1 to 64 rows per request.
- Write the route's parameter as `req: PredictRequest` and FastAPI validates first. A bad request gets a **422** straight away: your function is never called and the model never runs.

Tests do not need a real server: `TestClient(app)` sends requests inside the same process.
--- code
from fastapi.testclient import TestClient
torch.manual_seed(0)
model = TinyNet()
client = TestClient(create_app(lambda: torch_predictor(model)))
print(client.get("/health").json())
x, _ = make_data(2, seed=5)
r = client.post("/predict", json={"rows": x.tolist()})
print(r.status_code, r.json()["labels"])
r = client.post("/predict", json={"rows": [[1.0] * 7]})
print(r.status_code, r.json()["detail"][0]["msg"])

@@ concept
title: Step 6: latency percentiles and PSI drift
ref: day26
--- body
### Latency: percentiles, not the mean
- Send a few warm-up requests first and do not time them (day 19).
- Time each request with `time.perf_counter()` before and after; multiply by 1000 for milliseconds.
- Count successful (200) requests only: a 422 comes back fast, and mixing them in makes latency look better than it is.
- Report p50 / p95 / p99: `np.percentile(times, 95)` is the time 95% of requests beat. A few slow requests pull the mean up and also hide inside it; the lag users notice lives in p95 / p99 (day 22).

### Drift: PSI
After launch, the input distribution can change slowly (a new sensor model, the seasons). PSI, the population stability index, compares one feature's distribution in the training data (expected) with the live data (actual) (day 25):
1. Cut 10 buckets at the quantiles of the training data, so each bucket holds exactly 10% of the training data.
2. Count the share of live data that falls into each bucket, a, and the share of training data, e.
3. `PSI = Σ (a − e) · ln(a / e)`. First raise any share of 0 to a small number eps, otherwise ln 0 = −∞.

Common rules of thumb: below 0.1, nothing much changed; 0.1 to 0.25, worth a look; above 0.25, a clear shift: find the cause and consider retraining.
--- code
times = [3.1, 2.9, 3.0, 3.2, 2.8, 3.0, 3.1, 2.9, 3.0, 25.0]
report = latency_report(times)
print("mean:", round(sum(times) / len(times), 2), " p50 / p95 / p99:", [round(report[k], 2) for k in ("p50", "p95", "p99")])
x_train, _ = make_data(5000, seed=1)
x_same, _ = make_data(5000, seed=2)
x_moved, _ = make_data(5000, seed=3, shift=1.0)

Write `make_data(n, seed=0, shift=0.0)`. It makes sensor data for n machines and returns `(x, y)`:
- First create your own generator `g`, seeded with `seed`; pass `generator=g` to both random draws below.

def make_data(n, seed=0, shift=0.0):
    g = torch.Generator().manual_seed(seed)                  # our own random numbers, not the global ones
    y = torch.randint(0, CLASSES, (n,), generator=g)          # labels first
    x = class_centers()[y] + torch.randn(n, FEATURES, generator=g) + shift
    return x, y

--- context
Finding out after two hours of training that the output shape is wrong, or that a layer was never connected, is painful. One second of forward + backward before training stops these mistakes at the door.
--- prompt
Write `smoke_test(model, x, y)`. Run one forward + backward on a small batch and check the 4 rules below, in order. If a rule fails, `raise AssertionError("...")` with a message that says which one; if all pass, return the first loss (a Python float).
1. `logits = model(x)` has shape `(len(x), CLASSES)`.
2. `logits` contains no nan or inf (`torch.isfinite`).
3. `loss = F.cross_entropy(logits, y)`; `loss.item()` is within 0.5 of `math.log(CLASSES)`.
4. After `loss.backward()`, every parameter with `requires_grad` True has a `.grad`, and all its values are finite. Use `model.named_parameters()` and put the parameter's name in the message.
--- starter
def smoke_test(model, x, y):
    """One forward + backward. 4 checks; raise AssertionError when one fails.
    If all pass, return the first loss (float)."""
    raise todo()
--- solution
def smoke_test(model, x, y):
    logits = model(x)
    if tuple(logits.shape) != (len(x), CLASSES):
        raise AssertionError(f"logits have shape {tuple(logits.shape)}, expected {(len(x), CLASSES)}")
    if not torch.isfinite(logits).all():
        raise AssertionError("logits contain nan / inf")
    loss = F.cross_entropy(logits, y)
    if abs(loss.item() - math.log(CLASSES)) > 0.5:
        raise AssertionError(f"first loss {loss.item():.3f} is far from ln 3 = {math.log(CLASSES):.3f}")
    loss.backward()
    for name, p in model.named_parameters():
        if p.requires_grad and (p.grad is None or not torch.isfinite(p.grad).all()):
            raise AssertionError(f"{name} got no finite gradient")
    return loss.item()

--- prompt
`overfit_one_batch(model, x, y, steps=200, lr=1e-2)` should train on the same `(x, y)` for `steps` steps and return the loss of every step (a list of Python floats). Right now it has 3 bugs:

--- starter
def overfit_one_batch(model, x, y, steps=200, lr=1e-2):
    model.train()
    opt = torch.optim.AdamW(model.parameters(), lr=lr)
    losses = []
    for _ in range(steps):
        probs = F.softmax(model(x), dim=-1)
        loss = F.cross_entropy(probs, y)
        loss.backward()
        opt.step()
        losses.append(loss)
    return losses
--- solution
def overfit_one_batch(model, x, y, steps=200, lr=1e-2):
    model.train()
    opt = torch.optim.AdamW(model.parameters(), lr=lr)
    losses = []
    for _ in range(steps):
        loss = F.cross_entropy(model(x), y)       # cross_entropy applies log_softmax itself
        opt.zero_grad(set_to_none=True)           # clear the previous step's gradients
        loss.backward()
        opt.step()
        losses.append(loss.item())                # store a float, not the graph
    return losses

def train_steps(model, opt, x, y, steps, batch_size=64):
    model.train()                                            # accuracy() may just have switched it to eval
    losses = []
    for _ in range(steps):
        idx = torch.randint(0, len(x), (batch_size,))        # global random state: reproducible with a seed
        loss = F.cross_entropy(model(x[idx]), y[idx])
        opt.zero_grad(set_to_none=True)
        loss.backward()
        opt.step()
        losses.append(loss.item())
    return losses

def save_checkpoint(folder, model, opt, step):
    folder = Path(folder)
    folder.mkdir(parents=True, exist_ok=True)
    save_file(model.state_dict(), folder / "model.safetensors")          # tensors only: safe to load

def load_checkpoint(folder, model, opt):
    folder = Path(folder)
    model.load_state_dict(load_file(folder / "model.safetensors"))
    state = torch.load(folder / "train_state.pt", weights_only=True)
    opt.load_state_dict(state["opt"])                                      # AdamW's running averages
    torch.set_rng_state(state["rng"])                                      # future batches and dropout masks

--- context
A common interview follow-up: "What is in your checkpoint, and what happens if something is missing?" You only really understand resuming when you can say what each piece is for.
--- prompt
Your `save_checkpoint` saves the model weights and the optimizer state but **not** `torch.get_rng_state()`. In a new process you load it, train 10 more steps, and compare with a run that was never interrupted. Which statement is true?
--- options
- Loading raises an error, because train_state.pt has no "rng" key
- No error, and the loss goes down normally; but the batches drawn and the dropout masks differ from the uninterrupted run, so the final weights do not match
- The results are identical: `make_data` always uses a fixed seed, so the random numbers are already fixed
- The results are identical: the optimizer state already contains the random state
answer: 2
--- explain
The global random state decides two things: which rows `train_steps` draws with `torch.randint` at each step, and which neurons dropout switches off. In the new process the random state is not what it was at the interruption, so every later step takes a different path. Training still works and the loss still goes down; the weights simply do not match the uninterrupted run.
- Option 1: `load_checkpoint` only reads the keys it saved, so nothing raises. That is exactly what makes this kind of bug dangerous.
- Option 3: `make_data` uses its own `torch.Generator` and never touches the global random state (item 1 was designed that way). The same data does not mean the same batch order.
- Option 4: `opt.state_dict()` holds only AdamW's running averages (`exp_avg`, `exp_avg_sq`), step counts and hyperparameters; no random state.

When you train on a GPU, also save `torch.cuda.get_rng_state_all()`: dropout on the GPU uses CUDA's own random numbers (the script in item 13 does this).

def measure_latency(client, payload, n=50, warmup=5):
    for _ in range(warmup):                                    # warm-up: not timed

--- prompt
Write `psi(expected, actual, bins=10, eps=1e-4)`: `expected` holds one feature's values in the training data, `actual` its values in the live data (both 1-D tensors). Return a Python float.
1. Turn both into 1-D float64: `torch.as_tensor(v, dtype=torch.float64).flatten()`.
2. Cut points: use `torch.quantile` to take the quantiles of expected at 0, 1/bins, 2/bins, …, 1 (`torch.linspace(0, 1, bins + 1, dtype=torch.float64)`), drop the first and the last, and keep the bins − 1 cut points `edges`.
3. Buckets: `torch.bucketize(v, edges)` gives each value a bucket number from 0 to bins − 1; `torch.bincount(bucket numbers, minlength=bins)` counts each bucket; divide by the number of values to get shares. The shares of expected are e, those of actual are a.
4. Raise every share in e and a to at least eps (`clamp_min`) and return `Σ (a − e) · ln(a / e)`.

def psi(expected, actual, bins=10, eps=1e-4):
    expected = torch.as_tensor(expected, dtype=torch.float64).flatten()
    actual = torch.as_tensor(actual, dtype=torch.float64).flatten()
    qs = torch.linspace(0, 1, bins + 1, dtype=torch.float64)
    edges = torch.quantile(expected, qs)[1:-1]                 # bins - 1 inner cut points
    e = torch.bincount(torch.bucketize(expected, edges), minlength=bins) / len(expected)
    a = torch.bincount(torch.bucketize(actual, edges), minlength=bins) / len(actual)
    e, a = e.clamp_min(eps), a.clamp_min(eps)                  # empty buckets: avoid ln 0
    return float(((a - e) * torch.log(a / e)).sum())

def smoke_test(model, x, y):
    logits = model(x)
    if tuple(logits.shape) != (len(x), CLASSES):
        raise AssertionError(f"logits have shape {tuple(logits.shape)}")
    if not torch.isfinite(logits).all():
        raise AssertionError("logits contain nan / inf")
    loss = F.cross_entropy(logits, y)
    if abs(loss.item() - math.log(CLASSES)) > 0.5:
        raise AssertionError(f"first loss {loss.item():.3f} is far from ln 3")
    loss.backward()
    for name, p in model.named_parameters():
        if p.requires_grad and (p.grad is None or not torch.isfinite(p.grad).all()):
            raise AssertionError(f"{name} got no finite gradient")
    return loss.item()

def onnx_predictor(path):

    actual = torch.as_tensor(actual, dtype=torch.float64).flatten()
    edges = torch.quantile(expected, torch.linspace(0, 1, bins + 1, dtype=torch.float64))[1:-1]
    e = torch.bincount(torch.bucketize(expected, edges), minlength=bins) / len(expected)
    a = torch.bincount(torch.bucketize(actual, edges), minlength=bins) / len(actual)
    e, a = e.clamp_min(eps), a.clamp_min(eps)
    return float(((a - e) * torch.log(a / e)).sum())

def save_checkpoint(folder, model, opt, step):
    folder = Path(folder)
    folder.mkdir(parents=True, exist_ok=True)
    save_file(model.state_dict(), folder / "model.safetensors")
    torch.save({"opt": opt.state_dict(), "step": step, "rng": torch.get_rng_state()},
               folder / "train_state.pt")


def load_checkpoint(folder, model, opt):
    folder = Path(folder)
    model.load_state_dict(load_file(folder / "model.safetensors"))
    state = torch.load(folder / "train_state.pt", weights_only=True)
    opt.load_state_dict(state["opt"])
    torch.set_rng_state(state["rng"])
    return state["step"]

def create_app(load_model):
    predict = load_model()
    predict(np.zeros((1, FEATURES), dtype=np.float32))
    app = FastAPI()

    @app.get("/health")
    def health():
