@@ concept
title: Train/serve skew: one preprocessing path for both
--- body
**Train/serve skew** means the model's input is prepared one way during training and evaluation, and another way in the live service. Nothing raises an error. The model just quietly gets worse in production.

The most common sources:

- The preprocessing was written in a training notebook, then written again by hand for the service, with small differences (order of steps, defaults, lowercasing)
- Normalisation statistics: computed on the training set during training, but recomputed from "the current batch of requests" in the service
- The tokenizer was upgraded, or the vocabulary changed order (next card)

There is one rule: **write the preprocessing once**, and import that code from both training and serving. The statistics it needs (means, standard deviations, the vocabulary) are computed once, on training data only (day 17 explains why never on test data). They are saved **in the same file** as the model weights and loaded together when the service starts. They are never recomputed.

As a class, it looks like this:

```
pre = Preprocessor().fit(train_x)          # training: fit on training data only
torch.save({"model": model.state_dict(), "pre": pre.state_dict()}, "bundle.pt")

bundle = torch.load("bundle.pt")           # service start-up
pre = Preprocessor()
pre.load_state_dict(bundle["pre"])         # load the statistics, no fit
x = pre.transform(request_x)
```

In the example below, the service gets a single request. If you compute the mean and standard deviation from that request alone, you get nan (one row minus its own mean is 0, its standard deviation is 0 too, and 0/0 = nan). The statistics saved at training time give the right answer.
--- code
torch.manual_seed(0)
train = torch.randn(100, 2) * torch.tensor([10.0, 0.1]) + torch.tensor([50.0, 3.0])
mean, std = train.mean(dim=0), train.std(dim=0)      # computed once, on training data
bundle = {"pre": {"mean": mean, "std": std}}         # saved in the same file as the weights

req = torch.tensor([[60.0, 3.1]])                    # one request arrives at the service
print("with the training statistics:", (req - mean) / std)
print("with the request's own stats:", (req - req.mean(dim=0)) / req.std(dim=0, correction=0))

@@ concept
title: The tokenizer has a version too: match it with a fingerprint
--- body
Row 17 of the model's embedding table learned "the token whose id was 17 during training". If the service loads a different vocabulary (an upgraded tokenizer, a rebuilt vocabulary, a different order), the same word gets a different id. Nothing raises an error, but the model reads a different sentence.

The fix: at training time, compute a **fingerprint** of the vocabulary (a short string that changes whenever anything in the vocabulary changes) and store it with the checkpoint. When the service starts, compute it again for the vocabulary it loaded. If they differ, refuse to start.

How to compute the fingerprint:

1. `json.dumps(vocab, sort_keys=True)` turns the dict into text. `sort_keys=True` sorts by key, so the result does not depend on the order the dict was built in
2. `hashlib.sha256(text.encode("utf-8")).hexdigest()` gives a digest of 64 hex characters; the first 16 are enough

Do not use Python's built-in `hash()`. For strings it changes every time Python starts (it is randomised on purpose, for security), so the training process and the serving process would never agree.
--- code
import hashlib
import json

def fingerprint(vocab):
    text = json.dumps(vocab, sort_keys=True)
    return hashlib.sha256(text.encode("utf-8")).hexdigest()[:16]

v1 = {"<pad>": 0, "hello": 1, "world": 2}
v2 = {"world": 2, "hello": 1, "<pad>": 0}     # the same vocabulary, built in another order
v3 = {"<pad>": 0, "world": 1, "hello": 2}     # the same words, but the ids are swapped
print(json.dumps(v2, sort_keys=True))
print("v1:", fingerprint(v1))
print("v2:", fingerprint(v2))
print("v3:", fingerprint(v3))

@@ concept
title: Two switches for inference: eval() and inference_mode()
--- body
Before inference you flip two switches. They control two different things:

- `model.eval()` changes **how layers behave**. Dropout stops dropping units. BatchNorm uses the running mean / var saved during training instead of the current batch's statistics (day 17 covers the details). It does not turn off gradients.
- `with torch.inference_mode():` turns off autograd's bookkeeping (no graph, no saved intermediate results for the backward pass). That saves memory and time. It does not change how any layer behaves.

So you need both. With only inference_mode, dropout is still dropping. With only eval, every request still builds a graph for nothing.

`torch.no_grad()` also turns off gradients. `inference_mode` goes further: tensors created inside it can never be used in a backward pass later (that raises an error), so use it only for pure inference. How much memory and time it saves is measured on day 19.

Two common traps:

- A freshly built (or freshly trained) model is in train mode. If the service forgets `eval()` after loading it, dropout stays on in production.
- A training loop calls `model.eval()` for validation at the end of each epoch and forgets `model.train()` when training resumes.
--- code
torch.manual_seed(0)
net = nn.Sequential(nn.Linear(4, 8), nn.Dropout(0.5), nn.Linear(8, 2))
x = torch.randn(1, 4)

with torch.inference_mode():
    a, b = net(x), net(x)
print("only inference_mode, same twice:", torch.equal(a, b))

net.eval()
c = net(x)
print("only eval, requires_grad =", c.requires_grad)

with torch.inference_mode():
    d, e = net(x), net(x)
print("both, same twice:", torch.equal(d, e), " requires_grad =", d.requires_grad)

@@ concept
title: Results must not depend on the batch
--- body
A service often groups several requests into one batch. The result for one request must not depend on which other requests it was grouped with, or on how big the batch was.

Common ways to break this:

- BatchNorm still in train mode: it normalises with the mean and variance of *the current batch*, so different batchmates give different results. (In train mode with a batch of 1 it even raises `Expected more than 1 value per channel when training`, which is often the first sign that someone forgot `eval()`.)
- Padding to the longest sequence in the batch, with a model that does not use an attention mask and so includes the padding in its computation
- Tiny floating-point differences: for a different batch size, the library may add numbers in a different order, and results differ by about 1e-7. That is normal; compare with a small tolerance (last card)

The check is called a **batch-invariance test**: run the same data once as one batch and once split up, and look at the largest difference. If it is below 1e-6, the result does not depend on the batch. Below, 5 rows are split into batches of 3 and 2.
--- code
torch.manual_seed(0)
net = nn.Sequential(nn.Linear(4, 8), nn.BatchNorm1d(8), nn.Linear(8, 2))
x = torch.randn(5, 4)

for mode in ["train", "eval"]:
    net.train(mode == "train")
    with torch.inference_mode():
        together = net(x)                                  # all 5 rows at once
        split = torch.cat([net(x[:3]), net(x[3:])])        # 3 rows, then 2 rows
    print(mode, "largest difference:", (together - split).abs().max().item())

@@ concept
title: Batched generation (1): why right padding breaks
ref: day18
--- body
A decoder-only model (the GPT / Llama family) generates text step by step: feed in the whole sequence, take the logits (the raw score the model gives each word in the vocabulary) at the **last position**, pick the best word, append it, repeat.

One prompt at a time is easy. To put prompts of different lengths into one batch, you must pad them to the same length. If you pad on the right (right padding):

```
[3, 7, 2, 9]
[5, 1, 0, 0]      <- 0 is the pad token
```

The "last position" of the second row is a pad. The model predicts what comes after the pads, which is wrong, and the new word is appended after the pads, leaving a gap of two.

With left padding, the last position of every row is that row's real last word:

```
[3, 7, 2, 9]
[0, 0, 5, 1]
```

Moving the pads to the left is not enough on its own, though. The next card covers the other two pieces.

The code below uses a tiny decoder-only model, `tiny_lm()` (token 0 is the pad token). `generate_one(model, prompt, n)` greedily generates n tokens for one prompt, with no padding at all; it is the "right answer".
--- code
model = tiny_lm()
prompts = [[3, 7, 2, 9], [5, 1]]
alone = [generate_one(model, p, 1)[0] for p in prompts]    # one at a time, no padding

right = torch.tensor([[3, 7, 2, 9], [5, 1, 0, 0]])         # right padding
with torch.inference_mode():
    batch = model(right)[:, -1].argmax(dim=-1).tolist()
print("one at a time:      ", alone)
print("right-padded batch: ", batch)

@@ concept
title: Batched generation (2): left padding + attention mask + position ids
ref: day18
--- body
After left padding, the model needs two more things:

1. **An attention mask**: which positions are real (1) and which are padding (0). Inside attention, the model blocks the padding columns, so real tokens cannot see the pads. Without it, the 5 and the 1 in the second row attend to the two pads on their left, and their results are polluted.
2. **Position ids**: the position of each token inside *its own* sequence. After left padding, the 5 in the second row sits in slot 2, but it is really token 0 of its sequence. The model tells order apart through its position embeddings, so wrong positions mean wrong results.

For `[[5, 6, 7], [8]]` with pad = 0:

```
input_ids      = [[5, 6, 7], [0, 0, 8]]
attention_mask = [[1, 1, 1], [0, 0, 1]]
position_ids   = [[0, 1, 2], [0, 0, 0]]
```

Build the mask from "was this position added as padding?", not from `ids != pad_id`. Many models (GPT-2, for example) use the eos token as the pad token, and a real eos would be masked out too.

Position ids come from the mask: `mask.cumsum(-1) - 1` is exactly 0, 1, 2, … at the real positions. At padding positions it is -1; `.clamp(min=0)` turns that into 0. Padding is masked anyway, so any value works there, but it must not be negative or the embedding lookup fails.

At every generation step, append the new token to `input_ids`, and also:

- append a column of 1s to `attention_mask` (the new token is real)
- append "each row's last position + 1" to `position_ids`

In Hugging Face this is `tokenizer.padding_side = "left"` plus passing `attention_mask` to `generate`; for many models, `generate` computes the position ids for you with the same cumsum trick.

Below, `left_pad(seqs, pad_id)` returns all three (you write it yourself in the practice items).
--- code
mask = torch.tensor([[1, 1, 1], [0, 0, 1]])
print(mask.cumsum(-1) - 1)
print((mask.cumsum(-1) - 1).clamp(min=0))

model = tiny_lm()
prompts = [[3, 7, 2, 9], [5, 1]]
ids, mask, pos = left_pad(prompts, pad_id=0)
print(ids)
with torch.inference_mode():
    logits = model(ids, attention_mask=mask, position_ids=pos)
print("one at a time:     ", [generate_one(model, p, 1)[0] for p in prompts])
print("left-padded batch: ", logits[:, -1].argmax(dim=-1).tolist())

@@ concept
title: Reproducibility: seeds and determinism switches
--- body
The same code run twice should give the same result. Only then can you reproduce a problem or compare two experiments fairly. Random numbers come from three places, each with its own seed:

- Python's `random`: `random.seed(seed)`
- NumPy: `np.random.seed(seed)`
- PyTorch: `torch.manual_seed(seed)` (seeds the CPU and every GPU; the `torch.cuda.manual_seed_all(seed)` line you see in older code does no harm)

`torch.manual_seed` does not touch the other two. Data augmentation often uses `random` and dataset splits often use NumPy, so seeding only torch still gives different runs.

Even with the same seed, GPU results can differ between runs. There are three more switches:

- `torch.backends.cudnn.benchmark = False`: when it is True, cuDNN times several convolution algorithms and picks the fastest. Different runs may pick different algorithms, and results differ in the last digits.
- `torch.backends.cudnn.deterministic = True`: convolutions use only deterministic algorithms.
- `torch.use_deterministic_algorithms(True)`: every operation must use a deterministic implementation; an operation without one raises an error instead of quietly giving different results. On a GPU you must also set the environment variable `CUBLAS_WORKSPACE_CONFIG=:4096:8` at the very start of the program (before any GPU work), or matrix multiplications raise an error.

These switches make the program slower. Turn them on for debugging, for tests, or when you need exact reproduction.

Also remember: a different GPU model, driver, PyTorch version or batch size can still change the last digits. So always compare two results with a tolerance.
--- code
import random
import numpy as np

torch.manual_seed(0)
a = (random.random(), np.random.rand(), torch.rand(1).item())
torch.manual_seed(0)
b = (random.random(), np.random.rand(), torch.rand(1).item())
print("random, numpy, torch the same twice:", [x == y for x, y in zip(a, b)])
print("cudnn.benchmark =", torch.backends.cudnn.benchmark)
print("deterministic algorithms on:", torch.are_deterministic_algorithms_enabled())

@@ concept
title: Precision and tolerances: fp32 / TF32 / bf16 / fp16
--- body
Four common floating-point formats. Mantissa bits set the precision (how small a difference you can see); exponent bits set the range (how big a number you can store). eps is the gap between 1 and the next bigger number:

- **fp32**: 23 mantissa bits, eps ≈ 1.2e-7, max about 3.4e38. PyTorch's default.
- **TF32**: not a storage format but a way NVIDIA GPUs (Ampere and later, such as the A100 and the RTX 30/40/50 series) compute fp32 matrix multiplications and convolutions: the inputs keep only 10 mantissa bits before multiplying, and the result is still stored as fp32. Much faster, but relative errors reach about 1e-3. Convolutions may use it by default (`torch.backends.cudnn.allow_tf32` is True); matrix multiplications do not by default, but many training scripts turn it on with `torch.set_float32_matmul_precision("high")`.
- **bf16**: 7 mantissa bits, eps ≈ 7.8e-3, coarse; but it has as many exponent bits as fp32, so it rarely overflows. Common for training and inference.
- **fp16**: 10 mantissa bits, eps ≈ 9.8e-4, finer than bf16; but its max is only 65504, and anything larger becomes inf.

When you compare two outputs (say a bf16 service output against an fp32 reference):

1. Convert both to fp32 before subtracting: `(got.float() - ref.float()).abs()`
2. Use an absolute tolerance atol and a relative tolerance rtol together: `|got - ref| <= atol + rtol * |ref|`. Relative error alone fails: where ref is close to 0, the relative error becomes huge (above 10 for bf16 in the example below). Absolute error alone fails too: large values naturally have larger rounding errors.
3. Pick the tolerance of the lower-precision side. Rough values for model outputs: about 1e-5 for fp32, 1e-2 for fp16, 5e-2 for bf16. A single operation can be held to tighter limits; `torch.testing.assert_close` has defaults per dtype. A real bug usually shows up as a difference of 0.1 or more, far above these tolerances.
4. Looser is not safer: comparing an fp32 output with the bf16 tolerance lets bugs through.
--- code
for dt in (torch.float32, torch.float16, torch.bfloat16):
    fi = torch.finfo(dt)
    print(f"{str(dt):15s} eps={fi.eps:.1e}  max={fi.max:.1e}")

torch.manual_seed(0)
a, b = torch.randn(64, 64), torch.randn(64, 64)
ref = a @ b                                    # fp32 reference
for dt in (torch.float16, torch.bfloat16):
    got = (a.to(dt) @ b.to(dt)).float()        # compute in low precision, compare in fp32
    diff = (got - ref).abs()
    print(dt, f"max abs error {diff.max():.3f}", f"max relative error {(diff / ref.abs()).max():.1f}")

--- context
When a model does worse in production than in offline evaluation, one of the most common causes is that the service prepares inputs differently from training. --- prompt
Write a class `Preprocessor` that standardises features: `(x - mean) / std`. x has shape `(N, D)`: N rows, D features each.

- `fit(x)`: on the training data, compute each feature's `mean = x.mean(dim=0)` and `std = x.std(dim=0)`, then `.clamp_min(1e-6)` the std (a constant column has std 0; this avoids dividing by 0). Store them as `self.mean` and `self.std`, then `return self`.

- `load_state_dict(d)`: restore `self.mean` and `self.std` from such a dict.

class Preprocessor:
    def __init__(self):
        self.mean = None
        self.std = None

    def fit(self, x):
        self.mean = x.mean(dim=0)
        self.std = x.std(dim=0).clamp_min(1e-6)     # constant column: std = 0, do not divide by 0
        return self

    def transform(self, x):
        if self.mean is None:
            raise RuntimeError("call fit() or load_state_dict() first")
        return (x - self.mean) / self.std           # always the stored statistics

    def state_dict(self):
        return {"mean": self.mean.clone(), "std": self.std.clone()}

    def load_state_dict(self, d):
        self.mean = d["mean"].clone()
        self.std = d["std"].clone()
        return self

import hashlib
import json


def vocab_fingerprint(vocab):
    text = json.dumps(vocab, sort_keys=True)       # sorted keys: insertion order does not matter
    return hashlib.sha256(text.encode("utf-8")).hexdigest()[:16]


def check_vocab(saved_fp, vocab):
    fp = vocab_fingerprint(vocab)
    if fp != saved_fp:
        raise ValueError(f"vocabulary mismatch: the checkpoint used {saved_fp}, the loaded one is {fp}")

--- solution
def left_pad(seqs, pad_id=0):
    T = max(len(s) for s in seqs)
    ids = torch.full((len(seqs), T), pad_id, dtype=torch.long)
    mask = torch.zeros((len(seqs), T), dtype=torch.long)
    for i, s in enumerate(seqs):
        ids[i, T - len(s):] = torch.tensor(s, dtype=torch.long)   # real tokens go to the right
        mask[i, T - len(s):] = 1
    pos = (mask.cumsum(dim=-1) - 1).clamp(min=0)                 # real positions 0, 1, 2, …; padding gets 0
    return ids, mask, pos

    ids, mask, pos = left_pad(prompts, pad_id)
    new = []
    with torch.inference_mode():
        for _ in range(n_new):
            logits = model(ids, attention_mask=mask, position_ids=pos)   # (B, T, V)
            nxt = [[logits[:, -1].argmax(dim=-1)]]
            new.append(nxt)
            ids = torch.cat([ids, [[nxt.unsqueeze(1)]]], dim=1)
            mask = torch.cat([mask, [[torch.ones_like(mask[:, :1])]]], dim=1)

    return torch.stack(new, dim=1).tolist()                               # B lists of n_new tokens each

    overflow = torch.tensor(70000.0).to(dt).isinf().item()   # does 70000 fit?
    print(str(dt).replace("torch.", ""), lost, overflow)
--- explain
Near 1, the gap between two neighbouring numbers is eps: about 1.2e-7 for fp32, 9.8e-4 for fp16, 7.8e-3 for bf16.

- 0.001 is bigger than fp16's gap, so in fp16 1 + 0.001 becomes 1.000977, which is not 1 (`False`).
- 0.001 is much smaller than bf16's gap, so it is rounded away and the result is still 1 (`True`).
- fp16 tops out at 65504, so 70000 becomes inf (`True`). bf16 has as many exponent bits as fp32, so 70000 fits; it is stored as 70144 (coarse, but no overflow).

So bf16 is "wide range, coarse precision" and fp16 is "finer precision, small range". Training in fp16 needs loss scaling (multiplying the loss so tiny gradients do not become 0); bf16 usually does not.

TOL = {                          # (rtol, atol), rough values for model outputs

    torch.float16: (1e-2, 1e-2),
    torch.bfloat16: (5e-2, 5e-2),

def outputs_match(ref, got):
    if ref.shape != got.shape:
        return False
    rtol, atol = TOL[got.dtype]                   # the tolerance of the lower-precision side
    ref32, got32 = ref.float(), got.float()       # compare in fp32
    ok = (got32 - ref32).abs() <= atol + rtol * ref32.abs()
    return bool(ok.all())                         # any comparison with nan is False

class Preprocessor:
    def __init__(self):
        self.mean = None
        self.std = None

    def fit(self, x):
        self.mean = x.mean(dim=0)
        self.std = x.std(dim=0).clamp_min(1e-6)
        return self

    def transform(self, x):
        if self.mean is None:
            raise RuntimeError("call fit() or load_state_dict() first")
        return (x - self.mean) / self.std

    def state_dict(self):
        return {"mean": self.mean.clone(), "std": self.std.clone()}

    def load_state_dict(self, d):
        self.mean = d["mean"].clone()
        self.std = d["std"].clone()
        return self

--- solution
def left_pad(seqs, pad_id=0):
    T = max(len(s) for s in seqs)
    ids = torch.full((len(seqs), T), pad_id, dtype=torch.long)
    mask = torch.zeros((len(seqs), T), dtype=torch.long)
    for i, s in enumerate(seqs):
        ids[i, T - len(s):] = torch.tensor(s, dtype=torch.long)
        mask[i, T - len(s):] = 1
    pos = (mask.cumsum(dim=-1) - 1).clamp(min=0)
    return ids, mask, pos
