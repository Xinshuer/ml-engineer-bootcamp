@@ concept
title: 生成分两段：prefill 和 decode
ref: day23
--- body
LLM 生成一段回答，分成两个阶段：

1. **prefill**（预填充）：把整个 prompt 一次送进模型，一次 forward 算完所有位置。顺手把每一层的 k、v 存进 KV cache（第 5 天讲过：旧 token 的 k/v 存起来，以后不再重算）。最后一个位置的 logits 给出第 1 个新 token。
2. **decode**（解码）：每一步只把上一步生成的 **1 个** token 送进模型，带上 KV cache，得到下一个 token。要 100 个新 token，就是 1 次 prefill（给出第 1 个）加 99 次 decode。

两个阶段的瓶颈不一样：

- prefill 一次处理几百、几千个 token，矩阵乘法很大，瓶颈是 GPU 的算力（compute-bound）。
- decode 每步只算 1 个 token，却要把全部权重和 KV cache 从显存里读一遍。算得少、读得多，瓶颈是显存带宽（memory-bound）。所以把很多请求的 decode 放在同一步里做很划算：权重读一遍，分给所有请求用。

用户能感觉到的两个延迟：

- **TTFT**（time to first token，首 token 延迟）：主要是 prefill 的时间。prompt 越长，越慢。
- **TPOT**（time per output token，每个输出 token 的时间）：decode 一步的时间，决定字「蹦出来」的速度。

总时间 ≈ TTFT + (输出 token 数 - 1) × TPOT。

今天的小模型 `TinyLM`（随机权重，词表 32 个 token）的接口是 `logits, cache = model(ids, cache)`：cache 传 `None` 就是 prefill；把上一次返回的 cache 传回去，就是 decode。`model.calls` 记下每次调用处理了几个 token。
--- code
model = make_tiny_lm()
prompt = torch.tensor([[12, 15, 21, 0, 3, 27]])          # 6 个 token 的 prompt
with torch.inference_mode():
    logits, cache = model(prompt)                        # prefill：6 个 token 一次算完
    tok = logits[0, -1].argmax().item()                  # 最后一个位置 -> 第 1 个新 token
    out = [tok]
    for _ in range(4):                                   # decode：每步只喂 1 个新 token
        logits, cache = model(torch.tensor([[tok]]), cache)
        tok = logits[0, -1].argmax().item()
        out.append(tok)
print("每次调用处理的 token 数:", model.calls)
print("生成的 5 个 token:", out)
print("第 0 层 cache 里 k 的形状:", tuple(cache[0][0].shape), "= (B, KV head 数, 已有 token 数, head_dim)")
n = sum(p.numel() for p in model.parameters())
print(f"每次调用都要把 {n} 个参数读一遍：prefill 分给 6 个 token 用，decode 只给 1 个 token 用")

@@ concept
title: KV cache 的显存账
ref: day23
--- body
KV cache 存的是：每一层、每个 KV head、每个已有 token 的 k 向量和 v 向量。所以它的大小就是几个数直接相乘：

```
字节数 = 2 × 层数 × KV head 数 × head_dim × 序列长度 × batch × 每个数的字节数
```

- 开头的 2：K 和 V 各存一份。
- KV head 数：用了 GQA 的模型（第 5 天：几个 q head 共用一组 k/v），这里是 KV head 的个数，不是 q head 的个数。
- 每个数的字节数：fp32 是 4，fp16 / bf16 是 2，fp8 / int8 是 1。PyTorch 里 `torch.float16.itemsize` 直接给出 2。

算两个真实模型（fp16，每个数 2 字节；1 KiB = 1024 字节，1 GiB = 1024³ 字节）：

- Llama-2-7B：32 层，32 个 KV head，head_dim 128。每个 token 占 2 × 32 × 32 × 128 × 2 = 524,288 字节 = 512 KiB。一条 4096 token 的序列就是 2 GiB，同时服务 8 条就是 16 GiB。
- Llama-3-8B：也是 32 层、head_dim 128，但只有 8 个 KV head（GQA）。每个 token 128 KiB，只有前者的 1/4。

这就是为什么 KV cache 常常比权重更早把显存吃光：权重大小是固定的，KV cache 随「同时服务的请求数 × 长度」一起涨。一张卡能同时服务几条序列，基本就是「放完权重后剩下的显存 ÷ 每条序列的 KV cache」。
--- code
def per_token_bytes(layers, kv_heads, head_dim, bytes_per_number):
    return 2 * layers * kv_heads * head_dim * bytes_per_number

llama2 = per_token_bytes(32, 32, 128, torch.float16.itemsize)
llama3 = per_token_bytes(32, 8, 128, torch.float16.itemsize)
print("Llama-2-7B:", llama2 // 1024, "KiB / token，4096 个 token:", llama2 * 4096 / 1024**3, "GiB")
print("Llama-3-8B:", llama3 // 1024, "KiB / token，4096 个 token:", llama3 * 4096 / 1024**3, "GiB")

model = make_tiny_lm()                                   # 2 层，2 个 KV head，head_dim 8，fp32
with torch.inference_mode():
    _, cache = model(torch.randint(0, 32, (3, 5)))       # batch 3，每条 5 个 token
real = sum(k.numel() * k.element_size() + v.numel() * v.element_size() for k, v in cache)
print("TinyLM 的 cache 实际占:", real, "字节；公式:", 2 * 2 * 2 * 8 * 5 * 3 * torch.float32.itemsize, "字节")

@@ concept
title: 流式输出：生成器一次吐一个 token
--- body
聊天界面里，字是一个一个「蹦」出来的：服务每生成一个 token 就马上发给用户，不等整段写完。用户等第一个字只要 TTFT，不用等整段回答。

Python 里写这种「边算边交」的函数，用**生成器**（generator）：函数体里只要有 `yield`，调用它就不会马上执行，而是得到一个生成器对象。

- 每次 `next(gen)`（或者 `for` 循环取下一个），函数从上次停下的地方接着跑，跑到下一个 `yield` 交出一个值，然后暂停。
- 函数 `return` 了（或者跑到结尾），循环就结束。
- 调用方不取，它就不算。用户断开连接、不再取了，生成就停了，不浪费 GPU。

FastAPI 的 `StreamingResponse` 可以直接接收这样一个生成器，每 yield 一段就发一段给浏览器（服务本身是第 22 天的内容）。

生成循环一定要有两个停止条件：

1. **eos**（end of sequence，结束 token）：模型生成它，表示「我说完了」。eos 本身不发给用户。
2. **max_new_tokens**：最多生成几个新 token。这是硬上限：模型一直不生成 eos，也不能让一个请求永远占着 GPU。

OpenAI 风格的 API 会在结束时告诉你是哪一种：`finish_reason` 是 `"stop"`（遇到了 eos 或 stop 字符串）还是 `"length"`（到了 max_new_tokens）。

还有一个细节：生成器里要关掉梯度，就把 `@torch.inference_mode()` 当装饰器写在函数定义上面。不要在函数体里写 `with torch.inference_mode():` 再 yield：生成器暂停的时候，这个模式会「漏」到调用方的代码里。下面的代码两种都试了一下。
--- code
def count_up(n):
    print("  (函数体开始跑了)")
    for i in range(n):
        print(f"  算出 {i}")
        yield i
    print("  (函数体跑完了)")

gen = count_up(3)
print("调用之后，函数体还没跑，得到的是:", type(gen).__name__)
print("取第一个:", next(gen))
for x in gen:                                            # 接着上次停下的地方跑
    print("for 取到:", x)

@torch.inference_mode()
def good():
    yield torch.is_grad_enabled()

def leaky():
    with torch.inference_mode():
        yield torch.is_grad_enabled()

for name, make in [("装饰器", good), ("函数体里用 with", leaky)]:
    g = make()
    inside = next(g)
    print(f"{name}: 生成器里记梯度吗 {inside}；它暂停时，调用方记梯度吗 {torch.is_grad_enabled()}")
    g.close()                                            # 关掉生成器，with 这才退出

title: stop 字符串会跨 token
--- body
第三种停止条件是 **stop 字符串**：比如「生成到 `\nUser:` 就停」（聊天模板里，这是下一轮用户发言的开头，不停的话模型会替用户说话）。

难点在于：模型吐的是 token，不是字符。一个 stop 字符串常常被切在好几个 token 里，比如 `"\n"`、`"User"`、`":"`。所以只看「这一个 token 是不是 stop」，永远抓不到它。

正确做法：把已经生成的文字拼起来，在**拼起来的文字**里找 stop。找到了，只要 stop 前面的部分，stop 本身不要。有好几个 stop 时，谁在文字里最先出现，就按谁截。

流式输出还多一个麻烦：字发给用户了，就收不回来。假设已经发出了 `"Bye.\n"`，接下来来了 `"User"` 和 `":"`，这时才发现那个 `\n` 是 stop 的开头，可它已经在用户屏幕上了。

办法是**先扣住一小段**：每次拼好文字，看末尾有没有一段「可能是某个 stop 的开头」。有，就先扣住这段不发，前面的照常发出去。等下一段文字来了再看：

- 凑成了完整的 stop：扣住的丢掉，结束。
- 凑不成了（比如 `"\n"` 后面来的是 `"Thanks"`）：扣住的和新文字一起发出去。
- 流结束了还扣着一段：它不是 stop，发出去。

扣住的最多是「stop 长度 - 1」个字符，用户几乎感觉不到。下面代码里的 `held(text, stop)` 就是在算「末尾要扣住几个字符」。
--- code
pieces = ["Sure", "!", " Bye", ".\n", "User", ":", " next"]
stop = "\nUser:"
print("有哪一段正好等于 stop:", any(p == stop for p in pieces))

def held(text, stop):
    """text 末尾最长的、可能是 stop 开头的那一段有几个字符"""
    for k in range(min(len(stop) - 1, len(text)), 0, -1):
        if text.endswith(stop[:k]):
            return k
    return 0

text = ""
for p in pieces:
    text += p
    if stop in text:
        print(f"拼上 {p!r} 后找到了 stop，最后返回 {text[:text.find(stop)]!r}")
        break
    print(f"拼上 {p!r:8} 末尾要扣住 {held(text, stop)} 个字符")

@@ concept
title: 采样参数：先校验，再上 GPU
--- body
temperature、top-k、top-p 各自做什么，第 5 天讲过。服务端要多做一件事：**请求里的参数，进 GPU 之前先检查**。坏参数往往不会让服务崩溃，而是悄悄变成怪结果，或者让一个请求一直占着 GPU：

- `temperature = 0` 如果直接拿去除 logits，得到的是 inf 和 nan。0 应该当成「贪心」（直接取 argmax）单独处理。负数和特别大的数都不合理，常见的合法范围是 0 到 2。
- `top_p` 必须在 (0, 1] 里。`top_p = 0` 会把所有 token 都过滤掉。
- `top_k` 是非负整数，0 表示不用 top-k。
- `max_new_tokens` 是正整数，而且「prompt 长度 + max_new_tokens」不能超过模型的上下文长度（context length），不然生成到一半就会出错或者被截断。

Python 里有两个坑：

1. **NaN**：Python 的 `json.loads` 能读出 `NaN` 和 `Infinity`。NaN 和任何数比较都是 False，所以 `if t < 0 or t > 2` 拦不住它。要先用 `math.isfinite(t)` 挡掉 NaN 和 inf（或者写成「合法条件」`if not (0 <= t <= 2)`，NaN 让整个条件为 False，也会被挡住）。
2. **bool 也是 int**：`isinstance(True, int)` 是 True，JSON 里的 `true` 会被当成 1。要写 `isinstance(x, int) and not isinstance(x, bool)`。

还有一个：拼错的参数名（`"temprature": 0.2`）如果被默默忽略，用户以为自己设了温度，其实用的是默认值。不认识的参数名要报错。

校验失败时，把所有错误一次告诉用户（HTTP 400 或 422），不要只报第一个，让用户改一次、错一次。
--- code
import json
t = json.loads('{"temperature": NaN}')["temperature"]
print("json.loads 读出了:", t)
print("nan < 0:", t < 0, "  nan > 2:", t > 2, "  -> t < 0 or t > 2 放过了它")
print("math.isfinite(nan):", math.isfinite(t))
print("isinstance(True, int):", isinstance(True, int))
logits = torch.tensor([2.0, 1.0, 0.5])
print("temperature=0 直接相除再 softmax:", (logits / 0.0).softmax(-1).tolist())
print("temperature=0 当成贪心:", logits.argmax().item())

@@ concept
title: continuous batching：谁做完谁走
ref: day23
--- body
一张 GPU 同时只能 decode 有限几条序列（KV cache 的显存有限）。我们把这些位置叫做 **slot**（槽位）。请求很多时，怎么排？

**静态 batching**：凑齐一批（比如 4 条）一起生成，要等这一批里最长的那条做完，才一起返回，再开始下一批。问题是：

- 一批的时间由最长的那条决定。只要 3 个 token 的短请求，也得陪着要 500 个 token 的长请求等。
- 短的做完以后，它的 slot 就空着，可队列里还有人在等。

**continuous batching**（连续批处理，也叫 iteration-level scheduling；vLLM、TGI 这些推理框架都用它）：按「每一个 decode 步」来调度。

1. 每一步开始时，有空 slot 且队列里有人，就让排在最前面的请求进来。
2. 这一步里，slot 里的每个请求各生成 1 个 token。
3. 谁生成够了，谁就马上离开、返回结果；空出来的 slot 下一步就给别人用。

结果：短请求很快就能返回，slot 几乎不空转，总步数也更少。

今天的模拟做了两个简化：时间只按 decode 的步数算，每一步不管 slot 里有几个请求，都算 1 个单位时间（decode 的瓶颈是显存带宽，这个近似还不错）；新请求进来时的 prefill 不算时间。

下面的 `continuous_timeline` 打印每一步 slot 里是谁；`simulate_continuous` 和 `simulate_static` 返回每个请求在第几步做完。
--- code
lengths = [4, 1, 1, 3]                                   # 每个请求要生成几个 token
for step, running, waiting, finished in continuous_timeline(lengths, n_slots=2):
    print(f"第 {step} 步: slot 里 {running}  排队 {waiting}  做完 {finished}")
print("continuous，每个请求在第几步返回:", simulate_continuous(lengths, 2))
print("静态 batching，每个请求在第几步返回:", simulate_static(lengths, 2))

title: 扩散模型：步数就是延迟
ref: day23
--- body
扩散模型（第 8、9 天）生成一张图，要把去噪网络调用很多次：采样有多少步，就调用多少次。所以延迟大致是：

```
总时间 ≈ 固定开销 + 步数 × 每步时间 × (用 CFG 时再 × 2)
```

- **固定开销**：和步数无关的部分。比如文字编码器处理 prompt，VAE 把 latent 解码成图片。
- **每步时间**：去噪网络 forward 一次的时间。分辨率越高、batch 越大，越慢。
- **CFG**（classifier-free guidance，第 9 天）：每一步要算「有条件」和「无条件」两次（或者拼成 batch 2 算一次），粗略按 2 倍估。

服务有延迟预算时（比如「一张图 2 秒内返回」），就反过来算：预算减去固定开销，再除以每步的时间，就是最多能跑几步。步数少了画质会降，所以要配合少步数也能出好图的采样器（比如第 9 天的 DDIM）。连 1 步都放不下时，只能换更小的分辨率、更小的模型，或者拒绝这个请求。

下面的代码真的计时。小网络每一步都很快，每次运行的数字也会有些不同，但能看出步数翻倍，时间也差不多翻倍。CFG 那一列多出来的时间可能远不到一倍：网络太小，每次调用的固定开销占了大头，batch 从 1 变成 2 多花的时间不多。大模型、高分辨率时，就接近 2 倍了。
--- code
import time
torch.manual_seed(0)
net = TinyDenoiser().eval()
x = torch.randn(1, 4, 32, 32)

def sample_ms(steps, cfg):
    t0 = time.perf_counter()
    with torch.inference_mode():
        z = x
        for _ in range(steps):
            if cfg:                                      # 有条件 + 无条件拼成 batch 2（这个小网络没有条件输入，只为计时）
                e = net(torch.cat([z, z]))
                eps = e[1:] + 3.0 * (e[:1] - e[1:])
            else:
                eps = net(z)
            z = z - 0.1 * eps
    return (time.perf_counter() - t0) * 1000

sample_ms(5, False)                                      # 先热身一次：第一次调用总是偏慢
for steps in (10, 20, 40):
    print(f"{steps:2d} 步: {sample_ms(steps, False):6.1f} ms    加 CFG: {sample_ms(steps, True):6.1f} ms")

title: GPU 推理镜像的 Dockerfile
--- body
Docker 把「代码 + 依赖 + 系统库」打包成一个**镜像**（image），在任何装了 Docker 的机器上都能一模一样地跑起来。镜像跑起来就是一个**容器**（container）。镜像由一个叫 `Dockerfile` 的文本文件描述，每行一条指令：

- `FROM`：从哪个现成的镜像开始，比如装好了 PyTorch 和 CUDA 的官方镜像。
- `WORKDIR`：之后的命令在哪个目录里执行。
- `COPY`：把本机的文件拷进镜像。`RUN`：build 时执行一条命令，比如 `pip install`。
- `ENV`：设置环境变量。`USER`：之后用哪个用户运行。
- `EXPOSE`：说明服务用哪个端口。`CMD`：容器启动时执行的命令。

GPU 推理镜像的四条规矩：

1. **版本写死。** `FROM pytorch/pytorch:latest` 今天和下个月可能是两个不同的镜像：CUDA 版本变了，可能和机器上的显卡驱动不配；PyTorch 变了，数值也可能变。写成具体的 tag，比如 `pytorch/pytorch:2.7.0-cuda12.8-cudnn9-runtime`；`requirements.txt` 里每个包都写 `==版本号`。
2. **模型文件不进镜像。** 几个 GB 的权重 COPY 进镜像，镜像又大又慢，换一次模型就要重新 build、重新推送。代码进镜像；权重在运行时用 `docker run -v 本机目录:/models:ro` 挂进去。`:ro` 是只读，服务改不了、也删不了模型文件。
3. **不用 root 运行。** 容器里默认是 root。服务万一被攻破，root 能做的事多得多。先建一个普通用户（`RUN useradd ...`），再用 `USER` 切过去。
4. **一张 GPU 一个 worker。** `uvicorn --workers 4` 会起 4 个进程，每个进程都加载一份完整的模型、各自占一份 KV cache 的显存，4 个进程抢同一张卡。正确做法：一个容器一个进程（`--workers 1`），用 `docker run --gpus device=0` 只给它一张卡；并发靠进程内部的 batching（比如今天的 continuous batching）。要用两张卡，就起两个容器。

下面的代码检查一个「反面教材」Dockerfile，把违反规矩的行挑出来。
--- code
dockerfile = """FROM pytorch/pytorch:latest
WORKDIR /app
COPY requirements.txt server.py ./
COPY weights/ /app/weights/
RUN pip install -r requirements.txt
CMD ["uvicorn", "server:app", "--host", "0.0.0.0", "--workers", "4"]"""

lines = dockerfile.splitlines()
for line in lines:
    if line.startswith("FROM") and (":" not in line or line.endswith(":latest")):
        print("版本没写死      ->", line)
    if line.startswith("COPY") and "weights" in line:
        print("权重进了镜像    ->", line)
    if '"--workers", "4"' in line:
        print("一张卡 4 个进程 ->", line)
print("有 USER 指令吗:", any(l.startswith("USER") for l in lines), "-> 没有的话，容器用 root 运行")

--- options

- decode 每步只算 1 个 token，却要把全部权重和 KV cache 读一遍，瓶颈通常是显存带宽

title: 流式生成：prefill 一次，之后每步一个 token

--- context
每个 LLM 推理服务的核心都是这个循环：prefill 一次，然后一个 token 一个 token 地 decode，每出一个就马上交给用户，遇到 eos 或者到了上限就停。写对它，就把 TTFT、KV cache 和流式输出串起来了。
--- prompt
写**生成器** `stream_tokens(model, prompt_ids, max_new_tokens, eos_id)`，用贪心解码（每步取 logits 最大的 token），一个一个地 yield 新 token。

- `prompt_ids`：(1, T) 的 long 张量。`model` 的接口和 `TinyLM` 一样：`logits, cache = model(ids, cache)`，logits 的形状是 (1, 这次喂的 token 数, V)。
- 第一次调用：把整个 prompt 喂进去，cache 传 `None`（prefill）。之后每次只喂上一步生成的那 1 个 token（形状 (1, 1)），带上 cache（decode）。
- 下一个 token 看 `logits[0, -1]`（最后一个位置）。yield 的是 Python int（用 `.item()`），因为要转成 JSON 发给用户。
- 生成出 `eos_id` 就停，eos 本身不 yield。最多 yield `max_new_tokens` 个。
- 不做多余的 forward：最后一个 token yield 出去之后，不要再调用模型。`max_new_tokens=0` 时一次都不调用。

--- solution
@torch.inference_mode()                                  # 装饰器写法：生成器暂停时不影响调用方
def stream_tokens(model, prompt_ids, max_new_tokens, eos_id):
    ids, cache = prompt_ids, None
    for _ in range(max_new_tokens):
        logits, cache = model(ids, cache)                # 第一次：prefill 整个 prompt；之后：decode 1 个 token
        tok = logits[0, -1].argmax().item()              # 贪心：取最大的；.item() 变成 Python int
        if tok == eos_id:
            return                                       # eos 不发给用户
        yield tok
        ids = torch.tensor([[tok]], device=prompt_ids.device)   # 下一步只喂这 1 个新 token

        keep = 0                                         # 末尾最长的「可能是某个 stop 开头」的一段
        for s in stops:
            for k in range(min(len(s) - 1, len(buf)), 0, -1):
                if buf.endswith(s[:k]):
                    keep = max(keep, k)
                    break
        if len(buf) > keep:                              # 前面的都安全，发出去
            yield buf[:len(buf) - keep]
            buf = buf[len(buf) - keep:]
    if buf:
        yield buf                                        # 流结束了：扣着的不是 stop，发出去

def validate_sampling(params, prompt_len, context_len):
    def is_number(x):                                    # bool 也是 int，要单独排除
        return isinstance(x, (int, float)) and not isinstance(x, bool)

    def is_int(x):
        return isinstance(x, int) and not isinstance(x, bool)

    errors = []
    for key in params:
        if key not in ("temperature", "top_p", "top_k", "max_new_tokens"):
            errors.append(f"{key}: unknown parameter")
    if "temperature" in params:
        t = params["temperature"]
        if not (is_number(t) and math.isfinite(t) and 0 <= t <= 2):     # isfinite 挡住 NaN 和 inf
            errors.append(f"temperature: must be a number from 0 to 2, got {t!r}")
    if "top_p" in params:
        p = params["top_p"]
        if not (is_number(p) and math.isfinite(p) and 0 < p <= 1):
            errors.append(f"top_p: must be a number in (0, 1], got {p!r}")
    if "top_k" in params:
        k = params["top_k"]
        if not (is_int(k) and k >= 0):
            errors.append(f"top_k: must be an integer >= 0, got {k!r}")
    if "max_new_tokens" in params:
        n = params["max_new_tokens"]
        if not (is_int(n) and n >= 1):
            errors.append(f"max_new_tokens: must be an integer >= 1, got {n!r}")
        elif prompt_len + n > context_len:
            errors.append(f"max_new_tokens: prompt ({prompt_len}) + {n} > context length {context_len}")
    return errors

时间按 decode 步数算，从第 1 步开始。每一步：

1. 有空 slot 且队列里有人，就按队列顺序把请求放进 slot，直到 slot 满了或者队列空了。
2. slot 里的每个请求各生成 1 个 token。
3. 生成够 `lengths[i]` 个 token 的请求，这一步做完，离开 slot。空出来的 slot 从下一步开始可以用。

例子：`lengths = [8, 2, 3, 2, 6, 1]`，2 个 slot → `[8, 2, 5, 7, 13, 9]`。（静态 batching 是 `[8, 8, 11, 11, 17, 17]`，一共 17 步。）

def simulate_continuous(lengths, n_slots):
    queue = list(range(len(lengths)))                    # 排队的请求（按顺序）
    slots = []                                           # 正在生成的请求
    made = [0] * len(lengths)                            # 每个请求已经生成了几个 token
    finish = [0] * len(lengths)
    step = 0
    while queue or slots:
        step += 1
        while queue and len(slots) < n_slots:            # 1. 有空 slot 就放人进来
            slots.append(queue.pop(0))
        for i in slots:                                  # 2. 每个请求生成 1 个 token
            made[i] += 1
        done = [i for i in slots if made[i] == lengths[i]]
        for i in done:                                   # 3. 做完的这一步离开
            finish[i] = step
        slots = [i for i in slots if i not in done]
    return finish

def pick_steps(budget_ms, step_ms, overhead_ms, cfg, max_steps=50):
    per_step = step_ms * (2 if cfg else 1)                     # CFG：每步算两次
    steps = math.floor((budget_ms - overhead_ms) / per_step)   # 剩下的时间放得下几步（向下取整）
    return int(max(0, min(max_steps, steps)))                  # 不超过上限，也不能是负数

--- prompt
一台机器有 1 张 24 GB 的 GPU，模型权重 14 GB。下面哪些说法是**对的**？（可多选）
--- options
- 把 uvicorn 改成 `--workers 4`，吞吐就能变成 4 倍
- 权重不进镜像、运行时挂载：换模型不用重新 build，镜像小，推送和拉取都快
- `FROM pytorch/pytorch:latest` 最省心：永远是最新版，不会有兼容问题
- 容器里用普通用户运行：服务万一被攻破，攻击者能做的事更少
answer: 2,4
--- explain
第 1 个不对：每个 worker 是一个独立的进程，都要加载一份 14 GB 的权重。4 份就是 56 GB，这张 24 GB 的卡直接 OOM。就算放得下，每个进程也只剩很少的显存给 KV cache，还要抢同一张卡。正确做法是一个进程占一张卡，并发靠进程内部的 batching。

第 3 个不对：`latest` 会变。下个月重新 build，CUDA 或 PyTorch 的版本可能就变了：可能和驱动不配，数值也可能变，出了问题还很难查。

第 2、4 个是今天的规矩。
--- hints
- 每个 worker 都是一个独立的进程。它们会共用 GPU 上的同一份权重吗？
- `latest` 指向的镜像，下个月还是同一个吗？

--- prompt
写生成器 `stream_tokens(model, prompt_ids, max_new_tokens, eos_id)`：贪心解码，一个一个地 yield 新 token（Python int）。

- `prompt_ids`：(1, T) long。模型接口：`logits, cache = model(ids, cache)`。
- 第一次把整个 prompt 喂进去（cache 为 `None`），之后每次只喂上一个新 token（形状 (1, 1)）并带上 cache。
- 生成出 `eos_id` 就停，eos 不 yield；最多 yield `max_new_tokens` 个；最后一个 token 之后不再调用模型（`max_new_tokens=0` 时一次都不调用）。

--- solution
@torch.inference_mode()                                  # 装饰器写法：生成器暂停时不影响调用方
def stream_tokens(model, prompt_ids, max_new_tokens, eos_id):
    ids, cache = prompt_ids, None
    for _ in range(max_new_tokens):
        logits, cache = model(ids, cache)                # 第一次：prefill 整个 prompt；之后：decode 1 个 token
        tok = logits[0, -1].argmax().item()              # 贪心：取最大的；.item() 变成 Python int
        if tok == eos_id:
            return                                       # eos 不发给用户
        yield tok
        ids = torch.tensor([[tok]], device=prompt_ids.device)   # 下一步只喂这 1 个新 token

@check("max_new_tokens 是硬上限")
def _():
    model = ScriptedLM([3])                              # 永远不生成 eos
    out = list(stream_tokens(model, PROMPT, 4, eos_id=0))
    true(out == [3, 3, 3, 3], f"max_new_tokens=4：应该正好 4 个 token，你的是 {out}")
    model = ScriptedLM([3])
    out = list(stream_tokens(model, PROMPT, 0, eos_id=0))
    true(out == [] and model.calls == [], f"max_new_tokens=0：什么都不生成，也不调用模型。你得到 {out}，调用记录 {model.calls}")
